# 21-评论功能与一对多关系

> "一篇文章可以有 N 条评论，一条评论属于一篇文章和一个用户——这就是数据库中最常见的'一对多'关系。本章你不仅要写出评论接口，还要理解这种关系背后的设计哲学：为什么用外键？什么时候用 JOIN？评论被删了文章还在吗？文章被删了评论怎么办？这些问题看似简单，但答错一个，就可能让你的数据库变成'孤儿院'。"

---

## 一、目标与完成效果

**一句话目标**：创建评论 CRUD 接口，理解一对多关系的外键设计，掌握 JOIN 查询和级联删除，让文章和评论正确关联、安全共存。

**完成后的可观测效果**：
- `POST /api/articles/:id/comments` — 登录用户可以为任意文章发表评论，返回 201。
- `GET /api/articles/:id/comments` — 获取某篇文章的所有评论，每条评论带评论者用户名，按时间倒序排列。
- `DELETE /api/comments/:id` — 评论作者可以删除自己的评论，返回 204。
- 获取文章列表时，每篇文章自动带上 `comment_count`（评论数）。
- 删除文章时，该文章的所有评论也被自动删除（级联删除）。
- 你用 Thunder Client 测试了全部流程：创建评论 → 查看文章带评论数 → 查看评论列表 → 删除评论 → 删除文章后评论也消失。

## 三、分步操作

### 步骤 1：理解"一对多关系"——餐厅比喻

在餐厅里：

- **一张桌子**可以有**多个客人**（一对多）。
- **一个客人**只能坐在**一张桌子**上（反过来是"多对一"）。
- 客人点菜时，服务员会记录"这张菜是哪个桌的客人点的"——这就是**外键**。

在博客系统中：

| 关系 | 一方 | 多方 | 外键在哪 |
|------|------|------|----------|
| 文章 ↔ 评论 | 一篇文章 | 多条评论 | 评论表（`article_id`） |
| 用户 ↔ 评论 | 一个用户 | 多条评论 | 评论表（`user_id`） |

```
┌──────────┐       ┌──────────────┐       ┌──────────┐
│  users   │       │   comments   │       │ articles │
├──────────┤       ├──────────────┤       ├──────────┤
│ id       │◄──────│ user_id (FK) │       │ id       │◄──┐
│ username │       │ article_id   │──────►│ title    │  │
│ ...      │       │ content      │       │ ...      │  │
└──────────┘       │ created_at   │       └──────────┘  │
                   └──────────────┘                     │
                    user_id 指向 users.id ──────────────┘
                    article_id 指向 articles.id ────────┘
```

> 🔥 **魔鬼细节**：外键（Foreign Key，简称 FK）永远放在"多方"表里。因为一条评论只能属于一篇文章，所以 `article_id` 放在 `comments` 表——而不是在 `articles` 表里存一个"评论列表"。这是数据库设计的基本原则：**不要在"一方"存"多方"的列表**。

### 步骤 3：POST /api/articles/:id/comments——创建评论

```javascript
// POST /api/articles/:id/comments — 创建评论（需登录）
router.post('/articles/:id/comments', authenticate, (req, res) => {
    const { content } = req.body;
    const articleId = req.params.id;
    const userId = req.user.id;

    // 1. 验证评论内容不为空
    if (!content || content.trim() === '') {
        throw new AppError('评论内容不能为空', 400);
    }

    // 2. 验证评论长度（防止恶意灌水）
    if (content.length > 1000) {
        throw new AppError('评论内容不能超过 1000 字', 400);
    }

    // 3. 检查文章是否存在
    const article = db.prepare('SELECT id FROM articles WHERE id = ?').get(articleId);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    // 4. 插入评论
    const now = new Date().toISOString();
    const result = db.prepare(`
        INSERT INTO comments (content, article_id, user_id, created_at)
        VALUES (?, ?, ?, ?)
    `).run(content.trim(), articleId, userId, now);

    // 5. 查询刚插入的评论（带用户名）
    const newComment = db.prepare(`
        SELECT 
            comments.id,
            comments.content,
            comments.article_id,
            comments.user_id,
            comments.created_at,
            users.username AS author
        FROM comments
        INNER JOIN users ON comments.user_id = users.id
        WHERE comments.id = ?
    `).get(result.lastInsertRowid);

    res.status(201).json({
        success: true,
        data: newComment
    });
});
```

**关键点解析**：

| 步骤 | 在做什么 | 为什么 |
|------|----------|--------|
| `authenticate` 中间件 | 要求登录 | 只有登录用户才能评论 |
| `content.trim() === ''` | 空字符串检查 | 防止用户发纯空格评论 |
| `content.length > 1000` | 长度限制 | 后端安全防线——前端限制只是提示，后端限制才是真正的保护 |
| 先查文章是否存在 | 检查 `article_id` 有效性 | 防止评论指向不存在的文章（外键约束也会报错，但 404 更友好） |
| 插入后立即查询 | 带出 `author` 字段 | 返回完整评论信息给前端 |

> 🔥 **魔鬼细节**：`req.user.id` 来自 JWT 中间件（`middleware/auth.js`）解析后的结果。第 17 章你写了 `authenticate` 中间件，它会验证 Token 并把解析出的用户信息挂到 `req.user` 上。`req.user.id` 就是当前登录用户的 ID——**永远不要从请求体中获取 `user_id`**，否则任何人都可以冒充别人发评论。

### 步骤 4：GET /api/articles/:id/comments——获取评论列表

```javascript
// GET /api/articles/:id/comments — 获取文章的所有评论
router.get('/articles/:id/comments', (req, res) => {
    const articleId = req.params.id;

    // 先检查文章是否存在
    const article = db.prepare('SELECT id FROM articles WHERE id = ?').get(articleId);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    // 查询评论（带用户名，按时间倒序）
    const comments = db.prepare(`
        SELECT 
            comments.id,
            comments.content,
            comments.article_id,
            comments.user_id,
            comments.created_at,
            users.username AS author
        FROM comments
        LEFT JOIN users ON comments.user_id = users.id
        WHERE comments.article_id = ?
        ORDER BY comments.created_at DESC
    `).all(articleId);

    res.json({
        success: true,
        data: {
            article_id: parseInt(articleId),
            total: comments.length,
            comments: comments
        }
    });
});
```

**关键点**：

**为什么用 LEFT JOIN 而不是 INNER JOIN？**

| JOIN 类型 | 行为 | 适用场景 |
|-----------|------|----------|
| `INNER JOIN` | 只有在两边都有匹配时才返回行 | 文章和作者——每篇文章肯定有作者 |
| `LEFT JOIN` | 左边的表（comments）全部返回，右边没匹配就填 `NULL` | 评论和用户——用户可能被删除了，但评论应该保留 |

**场景模拟**：用户 `小明` 发了 3 条评论后账号被删除。用 `INNER JOIN` → 小明的 3 条评论全部消失（因为 `users` 表中找不到 `小明`）。用 `LEFT JOIN` → 小明的 3 条评论还在，只是 `author` 字段为 `null`。

> 🔥 **魔鬼细节**：`LEFT JOIN` 是"以左表为准"——`comments LEFT JOIN users` 意味着：把 `comments` 的所有行都拿出来，去 `users` 表里找匹配的。找不到就填 `NULL`。换成 `users LEFT JOIN comments` 意思就完全变了——变成"列出所有用户，有评论的带上评论"。

### 步骤 5：DELETE /api/comments/:id——删除评论

```javascript
// DELETE /api/comments/:id — 删除评论（只能删自己的）
router.delete('/comments/:id', authenticate, (req, res) => {
    const commentId = req.params.id;
    const userId = req.user.id;

    // 1. 查出评论
    const comment = db.prepare('SELECT * FROM comments WHERE id = ?').get(commentId);
    if (!comment) {
        throw new AppError('评论不存在', 404);
    }

    // 2. 检查归属：只有评论的作者才能删除
    if (comment.user_id !== userId) {
        throw new AppError('只能删除自己的评论', 403);
    }

    // 3. 删除
    db.prepare('DELETE FROM comments WHERE id = ?').run(commentId);

    res.status(204).send();
});
```

**关键点**：

- 路由路径是 `/comments/:id`，而不是 `/articles/:id/comments/:commentId`。因为删除评论不需要知道它属于哪篇文章——评论 ID 本身就是唯一的。
- `comment.user_id !== userId`：类型比较。`req.user.id` 来自 JWT 解析，`comment.user_id` 来自数据库。在 SQLite 中都是整数，`===` 安全。

> 🤔 **想多一点**：为什么删除评论的路由是 `DELETE /api/comments/:id` 而不是 `DELETE /api/articles/:articleId/comments/:commentId`？两种设计都可以，但本教程选择前者，因为：
> 1. 评论 ID 是全局唯一的，不需要 `articleId` 来定位。
> 2. 路由更短，调用更方便。
> 3. 如果你选择嵌套路由（后者），也完全正确——RESTful 设计中，嵌套资源路径更明确地表达了"这个评论属于那篇文章"。

### 步骤 7：获取文章时同时返回评论数

打开 `routes/articles.js`，修改 `GET /` 的 SQL 查询：

```javascript
// GET /api/articles — 获取所有文章（支持分页）
router.get('/', (req, res) => {
    const page = parseInt(req.query.page) || 1;
    const limit = parseInt(req.query.limit) || 10;
    const offset = (page - 1) * limit;

    const selectArticles = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author,
            (SELECT COUNT(*) FROM comments WHERE comments.article_id = articles.id) AS comment_count
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        ORDER BY articles.created_at DESC
        LIMIT ? OFFSET ?
    `);

    const articles = selectArticles.all(limit, offset);

    const { total } = db.prepare('SELECT COUNT(*) AS total FROM articles').get();

    res.json({
        success: true,
        data: {
            page: page,
            limit: limit,
            total: total,
            articles: articles
        }
    });
});
```

**新增的关键代码**：

```sql
(SELECT COUNT(*) FROM comments WHERE comments.article_id = articles.id) AS comment_count
```

这是一个**子查询（Subquery）**——在 SELECT 中嵌套一个 SELECT。对于每一篇文章，它都会去 `comments` 表里数一下该文章有多少条评论。

> 🤔 **想多一点**：为什么不用 `LEFT JOIN + GROUP BY`？两种方式都可以，但子查询更直观——"每一行附带一个子查询的结果"。`GROUP BY` 需要把所有字段都放进 `GROUP BY` 子句，代码会更长，且容易出错。对于"附加统计数"这种场景，子查询是更好的选择。

### 步骤 8：删除文章时级联删除评论

打开 `routes/articles.js`，修改 `DELETE /:id`：

```javascript
// DELETE /api/articles/:id — 删除文章
router.delete('/:id', authenticate, (req, res) => {
    const { id } = req.params;
    const userId = req.user.id;

    // 1. 检查文章是否存在且属于当前用户
    const article = db.prepare('SELECT * FROM articles WHERE id = ?').get(id);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    if (article.author_id !== userId) {
        throw new AppError('只能删除自己的文章', 403);
    }

    // 2. 先删除文章的所有评论（级联删除）
    db.prepare('DELETE FROM comments WHERE article_id = ?').run(id);

    // 3. 再删除文章本身
    db.prepare('DELETE FROM articles WHERE id = ?').run(id);

    res.status(204).send();
});
```

**关键点**：

**为什么先删评论，再删文章？**
因为外键约束——`comments.article_id` 引用了 `articles.id`。如果先删文章，数据库会报错 `FOREIGN KEY constraint failed`（因为还有评论指着这篇文章）。先删评论，解除外键引用，再删文章就不会报错。

> 🔥 **魔鬼细节**：这种"手动先删子记录再删父记录"的方式叫**应用层级联删除**。另一种方式是在建表时给外键添加 `ON DELETE CASCADE`，让数据库自动完成。本教程用手动方式，因为：
> 1. 更明确——你清楚地知道"删除文章时评论也会被删"。
> 2. 更安全——你可以在删除前做额外检查（如记录日志、通知用户）。
> 3. 数据库自动级联删除是"静默"的——删了文章后评论也消失了，你可能根本没意识到。

> 🚨 **重要提醒**：如果你在 `database/schema.js` 中给 `comments` 表的外键已经加了 `ON DELETE CASCADE`，那么数据库会自动删除评论——你不需要手动执行 `DELETE FROM comments WHERE article_id = ?`。但手动删除也不会有副作用（因为评论已经被自动删了，`DELETE` 语句的 `changes` 为 0）。本教程采用手动方式，如果你的 `schema.js` 已有 `ON DELETE CASCADE`，也可以保留手动删除代码——双重保险。

### 🤔 想多一点：为什么不在 `articles` 表里存评论列表？

新手常见的想法："在 `articles` 表里加一个 `comments` 字段，存 JSON 数组不就行了？"

```json
// ❌ 错误设计
{
    "id": 1,
    "title": "文章标题",
    "comments": [
        { "user": "小明", "content": "好文章！" },
        { "user": "小红", "content": "学到了" }
    ]
}
```

**为什么这不行？**

| 问题 | 说明 |
|------|------|
| 查询困难 | "找出小明所有的评论"——需要扫描所有文章的 `comments` JSON 字段，无法用索引 |
| 更新困难 | "修改一条评论"——需要读出整篇文章的 JSON，修改后写回，并发时会互相覆盖 |
| 删除用户 | "用户小明注销了，他的评论怎么办？"——需要遍历所有文章，修改 JSON |
| 数据冗余 | 评论信息（用户头像、时间等）全部内嵌，无法独立管理 |
| 数据量 | 一篇文章有 10000 条评论？JSON 字段会变得巨大，严重影响性能 |

**外键设计的优势**：每个实体（文章、评论、用户）独立存储，通过外键关联。查询、修改、删除都只需要操作对应的表——这就是**关系型数据库的核心理念**。

### ❌ 常见错误 → ✅ 解决方案

| 错误信息 / 现象 | 原因 | 解决 |
|-----------------|------|------|
| `POST /api/articles/1/comments` 返回 401 | 没传 Token 或 Token 过期 | 先登录获取新 Token，在请求头中加 `Authorization: Bearer <Token>` |
| 返回 `FOREIGN KEY constraint failed` | `article_id` 或 `user_id` 指向不存在的记录 | 确认文章 ID 和用户 ID 存在；`req.user.id` 是否来自正确的 JWT 解析 |
| `GET /api/articles/1/comments` 返回 `author: null` | 评论的用户已被删除，LEFT JOIN 未找到匹配 | 正常现象——这是 LEFT JOIN 的预期行为。前端判断 `author` 为 `null` 时显示"已注销用户" |
| 评论内容为空也能创建 | 只检查了 `!content`，没检查 `content.trim()` | 加上 `content.trim() === ''` 的检查 |
| 删除评论后，`GET /api/articles` 的 `comment_count` 没变 | 你可能忘了刷新页面，或者 `comment_count` 子查询没生效 | 确认 `GET /` 的 SQL 中包含了子查询，重启服务器后重试 |
| 删除文章时返回 `FOREIGN KEY constraint failed` | 没有先删评论就删文章 | 在 `DELETE /articles/:id` 中先执行 `DELETE FROM comments WHERE article_id = ?` |

```javascript
const express = require('express');
const router = express.Router();
const { db } = require('../database/db');
const { authenticate } = require('../middleware/auth');
const AppError = require('../utils/AppError');

// ========== 评论接口 ==========

// POST /api/articles/:id/comments — 创建评论（需登录）
router.post('/articles/:id/comments', authenticate, (req, res) => {
    const { content } = req.body;
    const articleId = req.params.id;
    const userId = req.user.id;

    // 验证评论内容不为空
    if (!content || content.trim() === '') {
        throw new AppError('评论内容不能为空', 400);
    }

    // 验证评论长度
    if (content.length > 1000) {
        throw new AppError('评论内容不能超过 1000 字', 400);
    }

    // 检查文章是否存在
    const article = db.prepare('SELECT id FROM articles WHERE id = ?').get(articleId);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    // 插入评论
    const now = new Date().toISOString();
    const result = db.prepare(`
        INSERT INTO comments (content, article_id, user_id, created_at)
        VALUES (?, ?, ?, ?)
    `).run(content.trim(), articleId, userId, now);

    // 查询刚插入的评论（带用户名）
    const newComment = db.prepare(`
        SELECT 
            comments.id,
            comments.content,
            comments.article_id,
            comments.user_id,
            comments.created_at,
            users.username AS author
        FROM comments
        INNER JOIN users ON comments.user_id = users.id
        WHERE comments.id = ?
    `).get(result.lastInsertRowid);

    res.status(201).json({
        success: true,
        data: newComment
    });
});

// GET /api/articles/:id/comments — 获取文章的所有评论
router.get('/articles/:id/comments', (req, res) => {
    const articleId = req.params.id;

    // 检查文章是否存在
    const article = db.prepare('SELECT id FROM articles WHERE id = ?').get(articleId);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    // 查询评论（带用户名，按时间倒序）—— LEFT JOIN 防止用户被删后评论丢失
    const comments = db.prepare(`
        SELECT 
            comments.id,
            comments.content,
            comments.article_id,
            comments.user_id,
            comments.created_at,
            users.username AS author
        FROM comments
        LEFT JOIN users ON comments.user_id = users.id
        WHERE comments.article_id = ?
        ORDER BY comments.created_at DESC
    `).all(articleId);

    res.json({
        success: true,
        data: {
            article_id: parseInt(articleId),
            total: comments.length,
            comments: comments
        }
    });
});

// DELETE /api/comments/:id — 删除评论（只能删自己的）
router.delete('/comments/:id', authenticate, (req, res) => {
    const commentId = req.params.id;
    const userId = req.user.id;

    // 查出评论
    const comment = db.prepare('SELECT * FROM comments WHERE id = ?').get(commentId);
    if (!comment) {
        throw new AppError('评论不存在', 404);
    }

    // 检查归属
    if (comment.user_id !== userId) {
        throw new AppError('只能删除自己的评论', 403);
    }

    // 删除
    db.prepare('DELETE FROM comments WHERE id = ?').run(commentId);

    res.status(204).send();
});

module.exports = router;
```

### `blog-backend/routes/articles.js`（本章修改：`comment_count` 子查询 + 级联删除）

```javascript
const express = require('express');
const router = express.Router();
const { db } = require('../database/db');
const { authenticate } = require('../middleware/auth');
const AppError = require('../utils/AppError');

// ========== 文章 CRUD 接口（数据库版） ==========

// GET /api/articles — 获取所有文章（支持分页，带评论数）
router.get('/', (req, res) => {
    const page = parseInt(req.query.page) || 1;
    const limit = parseInt(req.query.limit) || 10;
    const offset = (page - 1) * limit;

    const selectArticles = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author,
            (SELECT COUNT(*) FROM comments WHERE comments.article_id = articles.id) AS comment_count
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        ORDER BY articles.created_at DESC
        LIMIT ? OFFSET ?
    `);

    const articles = selectArticles.all(limit, offset);

    const { total } = db.prepare('SELECT COUNT(*) AS total FROM articles').get();

    res.json({
        success: true,
        data: {
            page: page,
            limit: limit,
            total: total,
            articles: articles
        }
    });
});

// GET /api/articles/:id — 获取单篇文章
router.get('/:id', (req, res) => {
    const { id } = req.params;

    const selectArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author,
            (SELECT COUNT(*) FROM comments WHERE comments.article_id = articles.id) AS comment_count
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `);

    const article = selectArticle.get(id);

    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    res.json({
        success: true,
        data: article
    });
});

// POST /api/articles — 创建文章（需登录）
router.post('/', authenticate, (req, res) => {
    const { title, content } = req.body;

    if (!title || !content) {
        throw new AppError('标题和内容为必填字段', 400);
    }

    const author_id = req.user.id;
    const now = new Date().toISOString();

    const insertArticle = db.prepare(`
        INSERT INTO articles (title, content, author_id, created_at, updated_at)
        VALUES (?, ?, ?, ?, ?)
    `);

    const result = insertArticle.run(title, content, author_id, now, now);

    const newArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `).get(result.lastInsertRowid);

    res.status(201).json({
        success: true,
        data: newArticle
    });
});

// PUT /api/articles/:id — 更新文章（只能改自己的）
router.put('/:id', authenticate, (req, res) => {
    const { id } = req.params;
    const { title, content } = req.body;
    const userId = req.user.id;

    if (!title || !content) {
        throw new AppError('标题和内容为必填字段', 400);
    }

    // 检查文章归属
    const article = db.prepare('SELECT * FROM articles WHERE id = ?').get(id);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }
    if (article.author_id !== userId) {
        throw new AppError('只能修改自己的文章', 403);
    }

    const now = new Date().toISOString();

    const updateArticle = db.prepare(`
        UPDATE articles 
        SET title = ?, content = ?, updated_at = ?
        WHERE id = ?
    `);

    const result = updateArticle.run(title, content, now, id);

    if (result.changes === 0) {
        throw new AppError('文章不存在', 404);
    }

    const updatedArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `).get(id);

    res.json({
        success: true,
        data: updatedArticle
    });
});

// DELETE /api/articles/:id — 删除文章（只能删自己的，级联删除评论）
router.delete('/:id', authenticate, (req, res) => {
    const { id } = req.params;
    const userId = req.user.id;

    // 检查文章是否存在且属于当前用户
    const article = db.prepare('SELECT * FROM articles WHERE id = ?').get(id);
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    if (article.author_id !== userId) {
        throw new AppError('只能删除自己的文章', 403);
    }

    // 先删除文章的所有评论（级联删除）
    db.prepare('DELETE FROM comments WHERE article_id = ?').run(id);

    // 再删除文章本身
    db.prepare('DELETE FROM articles WHERE id = ?').run(id);

    res.status(204).send();
});

module.exports = router;
```

## 六、小结表格

| 学到的东西 | 一句话解释 |
|-----------|-----------|
| 一对多关系 | 一个实体（文章/用户）拥有多个子实体（评论），用外键关联 |
| 外键（Foreign Key） | 放在"多方"表的字段，指向"一方"表的主键；如 `comments.article_id` 指向 `articles.id` |
| `INNER JOIN` vs `LEFT JOIN` | INNER JOIN 两边都有才返回；LEFT JOIN 以左表为准，右表没匹配也返回（填 NULL） |
| 子查询（Subquery） | 在 SELECT 中嵌套另一个 SELECT，用于附加统计信息（如评论数） |
| 级联删除（Cascade Delete） | 删除父记录时同时删除子记录；本教程用手动方式（先删评论再删文章） |
| 嵌套资源路由 | URL 结构体现资源层级：`/articles/:id/comments` 明确表达"某文章的评论" |
| 评论归属检查 | 删除评论前验证 `comment.user_id === req.user.id`，防止越权 |
| 前后端双重验证 | 前端限制长度是用户体验，后端限制长度才是安全防线 |

## 七、术语附录

| 术语 | 英文 | 通俗解释 | 本章出现位置 | 字面陷阱 |
|------|------|----------|-------------|----------|
| 一对多关系 | One-to-Many | 一个 A 对应多个 B。如：一篇文章有多条评论，一个用户有多条评论。 | 步骤 1 | 不是"A 和 B 之间只有一种关系"——是"A 的一条记录对应 B 的多条记录"这个方向的描述。 |
| JOIN | — | 把两张表"拼"在一起查询。根据匹配条件，从两张表中取出相关列。 | 步骤 4 | 不是"连接数据库"——是"连接两张表的数据"。 |
| LEFT JOIN | — | 以左表为基准，左表所有行都返回。右表没匹配的填 NULL。 | 步骤 4 | 不是"只取左边的数据"——左边全取，右边有的就带上，没有的填空。 |
| 嵌套资源 | Nested Resource | URL 中用小层级表示资源归属：`/articles/1/comments` 表示"第 1 篇文章的评论"。 | 步骤 3 | 不是"把资源嵌套在一起存储"——只是 URL 路径上的层级表达。 |
| 级联删除 | Cascade Delete | 删除父记录时，自动删除所有关联的子记录。 | 步骤 8 | 不是"级联"= 一级一级删——数据库可以一次性删掉所有关联行。 |
| 子查询 | Subquery | 在一条 SQL 语句中嵌套另一条 SELECT 查询。 | 步骤 7 | 不是"查询的子集"——是"查询中的查询"，内层查询的结果被外层查询使用。 |
| 外键约束 | Foreign Key Constraint | 数据库强制要求：外键列的值必须在父表的主键中存在。防止"孤儿记录"。 | 步骤 8 | 不是"外部的键"——是"指向另一张表主键的键"。 |

## 八、已知坑点与禁止事项

1. **`LEFT JOIN` 和 `INNER JOIN` 别搞混**：查评论时用 `LEFT JOIN`（因为用户可能被删），查文章时用 `INNER JOIN`（因为文章必须有作者）。口诀：**数据可能缺失的用 LEFT JOIN，数据一定存在的用 INNER JOIN**。

2. **`req.user.id` 来自 JWT，不要从请求体获取**：`POST /api/articles/:id/comments` 的 `user_id` 必须从 `req.user.id`（JWT 解析结果）获取，绝对不能从 `req.body.user_id` 获取。否则任何人都可以冒充别人发评论。

3. **删除文章前必须先删评论**：除非你在建表时加了 `ON DELETE CASCADE`。如果忘了，外键约束会阻止删除文章。

4. **评论内容长度限制**：前端限制（`maxlength`）只防君子不防小人。后端验证才是真正的安全防线——任何人都可以用 Thunder Client 或 curl 绕过前端限制。

5. **子查询的性能**：`(SELECT COUNT(*) FROM comments WHERE article_id = articles.id)` 在少量数据时没问题，但评论数很大时每篇文章都执行一次子查询会很慢。后续可以优化为缓存或定时统计。

6. **`req.params.id` 是字符串**：在 `comments.article_id = ?` 比较时，SQLite 自动转换类型所以没问题。但 `article_id: parseInt(articleId)` 在返回 JSON 时转为数字，保持和 `articles` 表一致。
