## 37a.1 单体 → 微服务：网络的根本变化

### 单体应用时代

```
一个 Java/Python/Node 进程，代码全在里面：
┌──────────────────────────────────┐
│  用户模块 → 订单模块 → 支付模块    │
│  函数调用（同一进程内，不经过网络）   │
└──────────────────────────────────┘
```

模块之间是**函数调用**——在同一个进程内，传参数、等返回值，不经过网络，延迟 ≈ 纳秒级。

### 微服务时代

```
拆成独立进程：
┌──────────┐  网络调用  ┌──────────┐  网络调用  ┌──────────┐
│ 用户服务  │──────────→│ 订单服务  │──────────→│ 支付服务  │
└──────────┘            └──────────┘            └──────────┘
    ↑ 网络调用
┌──────────┐
│ 网关/前端  │
└──────────┘
```

模块之间变成**网络调用**——跨进程、跨机器，TCP 握手 → HTTP 请求 → 等响应。延迟 ≈ 毫秒级，还可能遇到网络超时、服务不可用、DNS 解析失败。

**本质变化**：函数调用（确定性高、几乎不失败）→ 网络调用（不确定性高、可能失败、有延迟）。

### 新挑战

1. **服务地址管理**：10 个服务、每个 3 个实例、IP 随时变化（容器重启、弹性伸缩）——怎么知道"订单服务"现在在哪个 IP 上？
2. **客户端调用复杂**：前端/客户端要调 10 个服务，每个服务的地址、协议、认证方式都不同——前端怎么管得过来？
3. **横切关注点**：认证、限流、日志、监控——每个服务都要做一遍？还是有统一的地方做？

前两个问题由**服务发现**解决，第三个问题由 **API 网关**解决。

## 37a.2 先定义：南北流量 vs 东西流量

这是进入微服务网络之前**必须**先搞清楚的基础概念。做微服务不谈南北/东西流量，就像打球不说进攻/防守。

### 南北流量（North-South Traffic）

**客户端 ↔ 服务器**之间的流量。方向：从外部进入系统（进）或从系统出去（出）。

**比喻**：一栋大楼的正门。访客从外面进来穿过这个门，办完事从同一个门出去。

**举例**：
- 浏览器请求 `api.example.com`
- 手机 App 调用后端接口
- 第三方系统回调你的 Webhook

### 东西流量（East-West Traffic）

**服务器 ↔ 服务器**之间的流量。方向：系统内部水平流动。

**比喻**：大楼里面，A 房间的人走到 B 房间找人办事。外人看不到，但内部很频繁。

**举例**：
- 订单服务调用用户服务（查用户信息）
- 支付服务调用订单服务（查订单金额）
- 通知服务调用消息推送服务

### 一张图说清楚

```
              互联网（外部）
                  │
        南北流量  │  ↑ 南北流量
         （进入）  │  │  （出去）
                  ↓  │
        ┌──────────────────┐
        │   API 网关/反向代理  │  ← 大楼正门
        └────────┬──────────┘
                 │
    ┌────────────┼────────────┐
    │            │            │
    ↓            ↓            ↓
┌───────┐  ←──→  ┌───────┐  ←──→  ┌───────┐
│用户服务│  东西   │订单服务│  东西   │支付服务│
│       │  流量   │       │  流量   │       │
└───────┘        └───────┘        └───────┘
    微服务内部的东西流量（水平方向，服务间互相调用）
```

💡 **想多一点：大型互联网公司的东西流量远超南北流量**

一个电商请求的典型链路：用户搜商品（南北进）→ 商品服务查详情 → 商品服务查库存服务 → 商品服务查价格服务 → 返回（南北出）。这一路，南北流量只有 2 次进出，但内部东西流量可能多达几十次。在大型微服务集群中，**东西流量是南北流量的 5-10 倍**。

## 37a.3 服务注册与发现

### 问题

在微服务中，服务实例的 IP 和端口是动态变化的：

- 容器重启 → IP 变了
- 弹性扩缩容 → 实例数变了（从 3 个变 5 个，又变回 2 个）
- 滚动更新 → 新版本启动在新 IP 上，老版本逐步下线

你如果硬编码"用户服务在 `192.168.1.10:8080`"，那每次变动都要改代码、重启服务——微服务最基本的"弹性"就没意义了。

### 解决方案：服务注册与发现

```
① 服务启动时：
   用户服务实例A 启动 → 向注册中心登记："我是用户服务，我在 10.0.0.1:8080"
   用户服务实例B 启动 → 向注册中心登记："我是用户服务，我在 10.0.0.2:8080"

② 调用方发请求时：
   订单服务说："我要调用用户服务"
   订单服务 → 问注册中心："用户服务在哪？"
   注册中心 → 返回列表：[10.0.0.1:8080, 10.0.0.2:8080]

③ 订单服务从列表里选一个（负载均衡），发请求。

④ 实例下线时：
   用户服务实例A 关闭前 → 向注册中心注销
   或：注册中心定期心跳检测 → 发现 A 没回应 → 自动剔除
```

### 注册中心产品分类

注册中心不是只有一种。以下是主流产品，按能力分为两类：

**类别一：服务发现核心（核心功能是注册+发现）**

| 产品 | 出身 | 特点 |
|------|------|------|
| **Eureka** | Netflix/Spring Cloud | AP 系统（优先可用性），自我保护模式。与 Spring Cloud 深度集成，适合 Java 生态 |
| **Consul** | HashiCorp | CP 系统（优先一致性），自带健康检查、KV 存储、多数据中心支持，功能最全面 |
| **Nacos** | 阿里巴巴 | AP + CP 可切换，同时支持服务发现和配置管理，阿里云开源，国内流行 |

**类别二：分布式 KV + DNS 发现（底层基础设施）**

| 产品 | 出身 | 特点 |
|------|------|------|
| **Etcd** | CoreOS | 强一致的分布式 KV 存储，Kubernetes 用它存所有集群状态。本身不是注册中心，但很多注册中心（如 CoreDNS）基于它构建 |
| **CoreDNS** | CNCF | DNS 服务器，从 Etcd/K8S API 读取服务信息，转成 DNS 记录。调用方通过 `用户服务.svc.cluster.local` 这种 DNS 名即可访问服务 |

**一句话区分**：Eureka/Consul/Nacos 是"注册中心"（主动注册+发现），Etcd 是"分布式数据库"（被注册中心用作底层存储），CoreDNS 是"DNS 服务器"（用 DNS 协议做服务发现）。

## 37a.4 API 网关：微服务的统一入口

### 问题

服务发现解决了"服务在哪"的问题。但新问题又来了：

你有 10 个微服务，前端就要调 10 个地址。每个服务的认证方式不同（有的用 JWT、有的用 API Key、有的用 OAuth），限流策略不同，协议也不同（有的 HTTP、有的 gRPC、有的 WebSocket）。

**让前端直接面对 10 个服务 → 前端疯掉。**

### 解决方案：API 网关

在前端和微服务之间加一层 **API 网关**（API Gateway），所有外部请求统一走网关：

```
老方案（前端直连服务）：              新方案（经网关）：
前端 ──→ 用户服务                     前端 ──→ API网关 ──→ 用户服务
前端 ──→ 订单服务                              ├──→ 订单服务
前端 ──→ 支付服务                              ├──→ 支付服务
前端 ──→ 通知服务                              ├──→ 通知服务
前端 ──→ 商品服务                              └──→ 商品服务
前端：我要记住 5 个地址！               前端：我只知道网关一个地址！
```

### API 网关的核心能力

| 能力 | 说明 | 回引 |
|------|------|------|
| **路由转发** | 根据 URL 路径转发到不同服务（`/users/` → 用户服务，`/orders/` → 订单服务） | 类似 Nginx 的 `proxy_pass`（Ch36） |
| **认证鉴权** | 在网关层统一验证 JWT/OAuth Token，后端服务不用关心认证 | — |
| **限流** | 限制每个用户/IP 每秒请求数，防止恶意刷接口 | — |
| **日志/监控** | 在统一入口记录所有请求日志、耗时、状态码 | — |
| **协议转换** | 对外提供 HTTP/REST，对内转成 gRPC/Dubbo 等 | — |
| **WebSocket 代理** | 网关处理 WebSocket 升级（回顾 Ch26），后端专注业务 | Ch26 |
| **负载均衡** | 网关本身就是一层 L7 负载均衡（回顾 Ch35） | Ch35 |

### API 网关产品分类

| 产品 | 出身/生态 | 特点 |
|------|----------|------|
| **Kong** | 开源/Lua | 插件体系丰富（认证、限流、日志等数百个插件），高性能，社区活跃 |
| **Zuul** | Netflix/Spring Cloud | Java 生态首选，与 Eureka/Ribbon 等无缝集成。Zuul1 同步阻塞，Zuul2 异步非阻塞 |
| **Spring Cloud Gateway** | Spring 官方 | 基于 Spring WebFlux（响应式），替代 Zuul 的新一代网关，性能更好 |
| **Traefik** | 开源/Go | 专为容器/K8S 设计，自动发现服务并配置路由，零配置 |
| **Nginx + Lua/OpenResty** | 自建方案 | 灵活度最高，但需要自己写 Lua 脚本实现认证/限流逻辑 |

### API 网关是南北流量入口

回顾 37a.2 的定义。API 网关的工作范围：**南北流量**。它站在系统边界上，负责：
- 接收外部请求（南北进）
- 返回外部响应（南北出）
- 把请求分发给合适的后端服务

网关**不管**内部服务之间的互相调用（东西流量）。那是 Service Mesh 的事（下一章）。

## 37a.5 完整架构图——把拼图拼起来

```
                          互联网
                            │
                    南北流量 ↓ ↑
                   ┌────────────────┐
                   │   API 网关      │  ← 南北流量入口
                   │  (Kong/Zuul/   │     统一认证、限流、路由
                   │   Spring       │
                   │   Gateway)     │
                   └───────┬────────┘
                           │
            ┌──────────────┼──────────────┐
            │              │              │
    东西流量 ↓              ↓              ↓
      ┌──────────┐   ┌──────────┐   ┌──────────┐
      │ 用户服务   │←→│ 订单服务   │←→│ 支付服务   │
      │ :8080     │   │ :8081     │   │ :8082     │
      └─────┬─────┘   └─────┬─────┘   └─────┬─────┘
            │               │               │
            └───────────────┼───────────────┘
                            │   ①启动时注册
                            ↓   ②定期心跳
                   ┌────────────────┐
                   │   注册中心       │
                   │  (Consul/      │
                   │   Nacos/       │
                   │   Eureka)      │
                   └────────────────┘
                            ↑
                            │ ③查询服务地址列表
                   ┌────────┴────────┐
                   │  API 网关/服务   │
                   └─────────────────┘
```

**请求流程**：

1. 外部请求 → API 网关（南北流量入口）
2. 网关 → 注册中心："订单服务有哪些实例？"
3. 注册中心 → 返回列表 `[订单服务A:8081, 订单服务B:8081]`
4. 网关选一个实例，转发请求
5. 订单服务处理过程中 → 需要查用户信息 → 问注册中心 → 得到用户服务地址 → 调用用户服务（东西流量）
6. 所有服务处理完 → 响应原路返回

## 37a.6 API 网关和 Service Mesh 的区别（预告）

学习微服务的人最常搞混的概念之一——"API 网关和 Service Mesh 有什么区别？能不能用网关替代 Mesh？"

| 维度 | API 网关 | Service Mesh |
|------|---------|-------------|
| 管理流量 | 南北流量（外部↔内部） | 东西流量（服务↔服务） |
| 位置 | 系统边界（集中式） | 每个服务旁边（Sidecar，分散式） |
| 处理内容 | 认证、限流、路由、协议转换 | 服务间通信、mTLS、重试、超时、可观测性 |
| 代表产品 | Kong、Zuul、Spring Cloud Gateway | Istio、Linkerd、Consul Connect |
| 比喻 | 大楼正门的保安 | 每层楼走廊的管理员 |

**绝不能互相替代**——它们是互补的。网关管"进门"，Mesh 管"楼内走动"。下一章详细展开 Service Mesh。

❌ **常见错误**："我们已经有 API 网关（Kong/Zuul）做路由和限流了，不需要 Service Mesh。"

✅ **正确认知**：API 网关只管外部用户进来的南北流量。你的订单服务内部调用用户服务（东西流量），网关根本看不到——这个调用直接在 Pod 之间走，不经过网关。如果在网关做服务间调用的治理（重试、超时、加密），那网关很快就变成"一切流量的瓶颈"。正确的架构是：网关管南北，Mesh 管东西，各司其职。

## 术语表

| 术语 | 解释 |
|------|------|
| **南北流量** | 客户端与服务器之间的流量，方向为"进"和"出"系统边界 |
| **东西流量** | 服务器与服务器（服务与服务）之间的流量，方向为系统内部水平流动 |
| **服务注册（Service Registration）** | 服务实例启动时向注册中心登记自己的 IP、端口和健康状态 |
| **服务发现（Service Discovery）** | 调用方从注册中心查询目标服务的地址列表 |
| **注册中心** | 存储所有服务实例地址和状态的中心化组件，如 Consul/Nacos/Eureka |
| **API 网关（API Gateway）** | 微服务统一入口，处理认证、限流、路由等横切关注点 |
| **心跳（Heartbeat）** | 服务实例定期向注册中心发送"我还活着"的信号，超时未收到则判定宕机 |
| **Etcd** | 分布式强一致性 KV 存储，Kubernetes 的核心依赖，常被注册中心用作底层存储 |
| **CoreDNS** | DNS 服务器，通过 DNS 协议实现服务发现（如 `服务名.svc.cluster.local`） |
