# 20-文章归属：只能改自己的文章

> "第 19 章加了认证中间件——未登录的人被挡在门外。但还有一个漏洞：用户 A 登录后，可以修改用户 B 的文章。因为 PUT 和 DELETE 接口只检查了'是否登录'，没检查'文章是不是你的'。这一章修补这个漏洞：在更新和删除文章前，先查归属——不是你的文章？403 Forbidden。同时改造 GET 接口，返回每篇文章的作者信息，让前端知道'这篇文章是谁写的'。做完之后，注册两个用户互相测试——用户 A 对着用户 B 的文章点修改，被 403 无情拒绝。"

---

## 一、目标与完成效果

**一句话目标**：在 PUT 和 DELETE 接口中加入归属检查（`article.author_id !== req.user.userId` → 403），改造 GET 接口返回作者信息，让前端能区分每篇文章是谁写的，用两个用户互相测试验证归属保护。

**完成后的可观测效果**：
- `PUT /api/articles/:id` 和 `DELETE /api/articles/:id` 在修改/删除前检查文章是否属于当前用户。
- 不是自己的文章 → 403 Forbidden（`"无权修改此文章"`）。
- 自己的文章 → 正常修改/删除。
- `GET /api/articles` 和 `GET /api/articles/:id` 返回的每篇文章都包含 `author: { id, username }`（嵌套对象格式）。
- 你注册了两个用户，用户 A 创建文章，用户 B 尝试修改 → 403。
- 用户 A 创建的文章，用户 A 自己修改 → 200 成功。

## 三、分步操作

### 步骤 1：问题演示——"用户 A 能改用户 B 的文章"

首先，确认当前的漏洞确实存在。

1. 用 Thunder Client 注册用户 A（如 `alice_new`），登录拿到 token_A。
2. 用 token_A 创建一篇文章：`POST /api/articles` → 201，文章 ID 比如是 7。
3. 注册用户 B（如 `bob_new`），登录拿到 token_B。
4. 用 token_B 尝试修改用户 A 的文章：`PUT /api/articles/7` → **200 成功！**

**这就是漏洞**：用户 B 登录后，可以修改用户 A 的文章。虽然第 19 章的认证中间件确保了"登录了才能写"，但没检查"写的是不是自己的"。

> **餐厅比喻**：第 19 章加了门卫，检查你有没有会员卡。但你没检查"这张桌子是不是你预定的"——你拿着会员卡进了餐厅，就可以改别人桌上的菜。归属检查就是："先生，这张桌子是那位客人预定的，您的桌子在那边。"

### 步骤 2：更新文章前检查归属

打开 `routes/articles.js`，修改 `PUT /:id` 接口：

```javascript
// PUT /api/articles/:id — 更新文章（需要登录 + 是自己的文章）
router.put('/:id', authenticate, (req, res) => {
    const { id } = req.params;
    const { title, content } = req.body;

    if (!title || !content) {
        throw new AppError('标题和内容为必填字段', 400);
    }

    // 1. 先查出文章
    const article = db.prepare('SELECT * FROM articles WHERE id = ?').get(id);

    // 2. 检查文章是否存在
    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    // 3. 检查归属：文章的作者是不是当前登录用户？
    if (article.author_id !== req.user.userId) {
        throw new AppError('无权修改此文章', 403);
    }

    // 4. 通过检查，执行更新
    const now = new Date().toISOString();

    const updateArticle = db.prepare(`
        UPDATE articles 
        SET title = ?, content = ?, updated_at = ?
        WHERE id = ?
    `);

    const result = updateArticle.run(title, content, now, id);

    if (result.changes === 0) {
        throw new AppError('文章不存在', 404);
    }

    const updatedArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `).get(id);

    res.json({
        success: true,
        data: updatedArticle
    });
});
```

**关键变更**：

| 步骤 | 做什么 | 状态码 |
|------|--------|--------|
| 1 | `SELECT * FROM articles WHERE id = ?` | — |
| 2 | `!article` → 文章不存在 | 404 |
| 3 | `article.author_id !== req.user.userId` → 不是你的文章 | **403** |
| 4 | 通过检查，执行 UPDATE | 200 |

> 🔥 **魔鬼细节**：检查顺序不能乱——**先 404（文章是否存在），再 403（是否属于你）**。如果反过来，先检查归属，对于不存在的文章也会返回 403，攻击者可以通过"403 vs 404"推断哪些文章 ID 是存在的（信息泄露）。

> 🔥 **魔鬼细节**：更新前需要先 SELECT 查出文章——这意味着 PUT 接口现在会执行**两次数据库查询**（一次 SELECT，一次 UPDATE）。这是必要的代价——安全校验不能省。

### 步骤 4：改造 GET 接口——返回作者信息

目前 `GET /api/articles` 返回的每篇文章有 `author` 字段（通过 `INNER JOIN` 带出的 `username`），但格式是扁平的：

```json
{
  "id": 1,
  "title": "...",
  "author": "alice",    // ← 只是一个字符串
  "author_id": 1
}
```

前端需要知道更多作者信息（比如作者的 ID，用于"点击作者名跳转到作者主页"）。改造为嵌套格式：

```json
{
  "id": 1,
  "title": "...",
  "author": {
    "id": 1,
    "username": "alice"
  }
}
```

修改 `GET /` 和 `GET /:id` 的返回格式：

```javascript
// GET /api/articles — 获取所有文章（公开）
router.get('/', (req, res) => {
    const page = parseInt(req.query.page) || 1;
    const limit = parseInt(req.query.limit) || 10;
    const offset = (page - 1) * limit;

    const selectArticles = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.id AS author_id_joined,
            users.username AS author_username
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        ORDER BY articles.created_at DESC
        LIMIT ? OFFSET ?
    `);

    const rows = selectArticles.all(limit, offset);

    // 把扁平数据转换为嵌套格式
    const articles = rows.map(row => ({
        id: row.id,
        title: row.title,
        content: row.content,
        author: {
            id: row.author_id_joined,
            username: row.author_username
        },
        created_at: row.created_at,
        updated_at: row.updated_at
    }));

    const { total } = db.prepare('SELECT COUNT(*) AS total FROM articles').get();

    res.json({
        success: true,
        data: {
            page: page,
            limit: limit,
            total: total,
            articles: articles
        }
    });
});
```

`GET /:id` 同样改造：

```javascript
// GET /api/articles/:id — 获取单篇文章（公开）

    const { id } = req.params;

            articles.updated_at,

    `);

    const row = selectArticle.get(id);

    if (!row) {
        throw new AppError('文章不存在', 404);
    }

    const article = {
        id: row.id,
        title: row.title,
        content: row.content,
        author: {
            id: row.author_id_joined,

        success: true,
        data: article
    });
});
```

> **为什么用嵌套格式？** 扁平格式 `author: "alice"` 前端拿到后只知道作者名，不知道作者 ID。如果前端要做"点击作者名跳转到作者主页"或"高亮当前用户的文章"，就需要 `author: { id: 1, username: "alice" }` 这种格式。同时去掉 `author_id` 顶层字段——它已经在 `author.id` 里了。

### 🤔 想多一点：404 和 403 的顺序为什么重要？

如果先检查 403 再检查 404：

```javascript
// ❌ 错误顺序
if (article.author_id !== req.user.userId) {
    throw new AppError('无权修改此文章', 403);
}
if (!article) {
    throw new AppError('文章不存在', 404);
}
```

**问题**：对于不存在的文章，`article` 是 `undefined`，`article.author_id` 会报错（`Cannot read properties of undefined`）。

**即使加了空值检查**：

```javascript
// ❌ 仍然不好
if (article && article.author_id !== req.user.userId) {
    throw new AppError('无权修改此文章', 403);
}
if (!article) {
    throw new AppError('文章不存在', 404);
}
```

**问题**：攻击者可以通过"403 vs 404"推断文章是否存在。正确的做法是——不管谁请求，不存在的文章永远返回 404。只有文章确实存在时，才检查归属。

---

### ❌ 常见错误 → ✅ 解决方案

| 错误信息 / 现象 | 原因 | 解决 |
|-----------------|------|------|
| `Cannot read properties of undefined (reading 'author_id')` | 先检查了归属再检查存在性——`article` 是 `undefined` | 先 `if (!article)` 检查 404，再检查归属 |
| 用户 A 自己改自己的文章也返回 403 | `req.user.userId` 和数据库中的 `author_id` 类型不一致（一个字符串一个数字） | 确认 JWT Payload 中 `userId` 是数字，或比较时用 `!=`（宽松比较）而不是 `!==` |
| `GET /api/articles` 返回的 `author` 是 `null` | `author_id_joined` 对应的用户不存在 | 确认所有文章的 `author_id` 都对应存在的用户 |
| 带有效 token 更新文章返回 404 而不是 403 | 文章 ID 不存在 | 先确认文章确实存在（用 `GET /api/articles` 查看） |
| `author_id` 在响应中重复出现 | 同时保留了顶层 `author_id` 和嵌套 `author.id` | 去掉顶层 `author_id`，只保留 `author: { id, username }` |

```javascript
        throw new AppError('文章不存在', 404);
    }

    res.status(204).send();
});

module.exports = router;
```

## 八、已知坑点与禁止事项

1. **404 和 403 的检查顺序不能乱**：先 `if (!article)` → 404，再 `if (article.author_id !== req.user.userId)` → 403。反过来会导致信息泄露（攻击者通过 403 推断文章存在）。

2. **`req.user.userId` 和 `author_id` 的类型要一致**：JWT Payload 中的 `userId` 通常是数字，SQLite 的 `author_id` 也是数字。但如果你在 JWT 签发时用了字符串，比较时可能不匹配。确认类型一致，或用 `!=` 宽松比较。

3. **PUT 和 DELETE 接口现在需要两次数据库查询**：第一次 SELECT 查文章（用于归属检查），第二次 UPDATE/DELETE。这是必要的安全代价。

4. **GET 接口返回的 `author` 是嵌套对象**：前端需要知道作者 ID，所以用 `author: { id, username }` 格式。不要同时保留顶层 `author_id`——信息重复且冗余。

5. **`POST /api/articles` 创建文章时不需要归属检查**：因为是创建新文章，`author_id` 直接设为 `req.user.userId`，不存在"归属冲突"的问题。

6. **seed 脚本创建的文章归属 alice（id=1）**：如果你用 seed 用户测试，注意这些文章的 `author_id = 1`。通过注册接口创建的用户 ID 从 3 开始（alice=1, bob=2）。
