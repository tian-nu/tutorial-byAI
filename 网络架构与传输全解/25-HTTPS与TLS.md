## 25.1 HTTP 在裸奔

回想第 11、12 章讲的 HTTP 协议——请求和响应全是明文，任何人都能看懂。HTTP 报文在网络传输过程中经过路由器、交换机、运营商骨干网，途经的任何一个节点都可以：

- **偷看**：你输入的密码 `123456`，中间路由器的管理员如果抓包，一眼就能看到
- **篡改**：你请求 `bank.com`，中间人可以把响应替换成假页面，甚至篡改转账金额
- **冒充**：你连到 WiFi `Starbucks-Free`，实际上是一个钓鱼热点，它伪装成 `bank.com` 返回假的登录页面

这三项合起来就是信息安全的"三要素"被打破——**机密性（Confidentiality）**、**完整性（Integrity）**、**身份认证（Authentication）**全部泡汤。

HTTPS 就是在 HTTP 下面加了 **TLS**（Transport Layer Security，传输层安全协议）层。TCP 三次握手之后，先走 TLS 建立加密连接，然后才在这个加密隧道里传输 HTTP 报文。

```
HTTPS = HTTP + TLS + TCP + IP
         ↑
    加密这一层插在 HTTP 和 TCP 之间
```

用信封打比喻最好理解：纯 HTTP 就是一张明信片——邮递员、分拣员、中转站都能看；HTTPS 就是先把信放进加密信封，谁在路上截获都是一堆乱码，只有收件人拆得开。

## 25.2 加密基础：直觉比公式重要

加密分两种，我们先不用数学，用比喻理解了再给术语。

### 对称加密 — 同一把钥匙，开门也用它，锁门也用它

你和朋友约好一个暗号（钥匙），你用它把消息加密，朋友用它解密。加密和解密用**同一把密钥**。

- 优点：**快**，几千行代码瞬间加密解密
- 致命缺陷：你和朋友怎么安全交换这把钥匙？你如果通过不安全的通道把钥匙发给朋友，被截获就全完了。**钥匙分发问题**是最难的问题。

### 非对称加密 — 公钥加密，私钥解密

你有一对钥匙：**公钥（任何人都能拿到）**和**私钥（只有你知道）**。

- 用公钥加密的内容，必须用对应的私钥才能解。反过来也行：用私钥签名，公钥可以验证。
- 比喻：公钥就像你的**邮箱地址**，谁都知道，谁都能往里投信；私钥是**邮箱钥匙**，只有你能打开看到内容。
- 完美解决了钥匙分发：你把公钥公开给全世界，别人用公钥加密发给你的消息，只有你有私钥能打开。公钥被截获也没关系——它本来就是公开的。
- 缺点：**慢**，比对称加密慢几百到几千倍。

### 实际方案：两者结合

真实世界的 HTTPS 是这样用的：

```
1. 客户端和服务器先用非对称加密（交换一个"会话密钥"的安全通道）
2. 双方安全拿到同一个临时密钥后，切换到对称加密进行数据传输

先用非对称（安全但慢）建立信任，再用对称（快但需要钥匙）传数据。
```

这个"握手——交换密钥——对称加密"的过程，就是 **TLS 握手**要做的事。

## 25.3 TLS 1.3 握手全过程

TLS 1.3（2018 年发布）是当前最新版，它把握手精简到了极致。我们一步步走一遍：

```
客户端 (Client)                             服务器 (Server)
    │                                            │
    │───① Client Hello ───────────────────────→│
    │    "我支持 TLS 1.3，这些加密算法堆"         │
    │                                           │
    │←──② Server Hello ────────────────────────│
    │    "我选 TLS 1.3 + AES_256_GCM 作为套件"     │
    │    附：服务器证书（含公钥）                      │
    │    附：签名验证                           │
    │                                           │
    │───③ 客户端验证证书，彼此都算会话密钥 ────────│
    │───④ Finished ───────────────────────────→│
    │    "握手完成，接下来纯数据"                     │
    │                                           │
    │←──④ Finished ────────────────────────────│
    │    "收到"                                   │
    │                                           │
    ═══ 加密通信开始 ═══                          │
```

### 每一步在做什么？

**① Client Hello**：客户端说"你好，我支持 TLS 1.3，这些是我能用的加密套件（Cipher Suites）"。TLS 1.3 还多了个"密钥共享"——客户端直接把自己的公钥参数（DH 密钥协商算法的公钥部分）带上，省去了往返。

**② Server Hello**：服务器挑一个自己支持的加密套件（比如 `TLS_AES_256_GCM_SHA384`），发回自己的公钥参数，顺带附上**服务器证书**。证书里是服务器公钥 + 域名 + CA 签名。

**③ 验证 & 计算会话密钥**：客户端验证证书（检查域名匹配、检查 CA 签名是否可信、检查是否过期）。验证通过后，客户端用服务器发来的公钥参数，加上自己的私钥参数，算出**会话密钥**。服务器也同样算出相同的会话密钥。

**④ Finished**：双方各发一条 `Finished` 消息（包括之前所有交互的哈希），既是"礼貌地告诉对方握手完成"，也是验证——如果双方 Finished 消息能互相解对，说明会话密钥一致，中间没有篡改。

之后所有应用数据（HTTP 请求和响应）都走这个会话密钥做对称加密。

## 25.4 TLS 1.2 vs TLS 1.3：为什么 1.3 更快？

| 对比维度 | TLS 1.2（2008） | TLS 1.3（2018） |
|----------|----------------|----------------|
| 最低往返次数 | 2-RTT | **1-RTT**（首次连接）/ 0-RTT（复用连接跳过握手） |
| 握手步骤 | Client Hello → Server Hello → Certificate → Client Key Exchange → Finished | 合并 Client Hello 和密钥交换，一个往返搞定 |
| 加密套件数量 | 几百种（很多是过时的、有漏洞的） | 5 种精选版本，去掉所有弱算法 |
| 首次加密时机 | 要等到 Client Key Exchange 之后 | 从 Server Hello 之后就开始加密大部分握手消息 |
| 向前安全 | 支持（取决于套件） | **强制启用**——所有套件都具备向前安全性 |

向前安全性（Forward Secrecy，本章末尾术语表会解释）是什么意思？简单说：就算某天黑客拿到了你服务器的私钥，也无法解密**过去**的通信记录。TLS 1.3 强制要求这一点，TLS 1.2 则可以选。

💡 **想多一点**：TLS 1.3 的 0-RTT 复用模式虽然快（完全不握手指直接传数据），但有一个安全代价——重放攻击（Replay Attack）。攻击者可以截获你的加密数据，然后原封不动地重新发给服务器（比如重复下单）。所以关键操作（支付、修改密码）不推荐用 0-RTT，服务器也可以限制 0-RTT 的路由范围。

## 25.5 加密套件拆解——不再一头雾水

你打开任何 HTTPS 网站，点锁→证书→详细信息，就能看到"加密套件"（Cipher Suite）。它看起来像天书：

```
TLS_AES_256_GCM_SHA384
```

拆开来其实很简单，只有三段：

| 段 | 内容 | 含义 |
|----|------|------|
| `TLS` | 协议 | TLS 1.3 的套件 |
| `AES_256_GCM` | 对称加密算法 | **AES-256**（工业标准对称加密，256位密钥）+ **GCM** 模式（加密的同时还做认证，防篡改） |
| `SHA384` | 哈希算法 | **SHA-384**（安全哈希，用于完整性校验——确保数据中途没被改过） |

所以 `TLS_AES_256_GCM_SHA384` 翻译成人话就是：**TLS 1.3 协议，用 AES-256 加密数据，GCM 模式保证数据完整性，用 SHA-384 做校验哈希。**

这比 TLS 1.2 时代的 `ECDHE-RSA-AES256-GCM-SHA384` 这种又臭又长的名字好记多了。TLS 1.3 简化了命名，去掉了很多冗余。

## 25.6 证书链：从"可信的人"一路担保到你

### 问题：我怎么知道收到的公钥真是百度的？

你输入 `baidu.com`，服务器给你发了一个公钥，说"我就是百度，用这个公钥加密就能安全地和我通信"。但你怎么确定它没有冒充？

证书就是解决这个问题的。它就像身份证——你可以造假，但如果身份证是由**公安局**（大家相信的根 CA）签发的，你能通过公安系统验证。

### 证书链

```
根 CA 证书（Root CA）
    ↓ 签名
中间 CA 证书（Intermediate CA）
    ↓ 签名
服务器证书（baidu.com）
```

- **根 CA 证书**：就是操作系统/浏览器**出厂时预装**的那几十个全球公认的权威证书机构。它们是"信任的起点"，不需要任何人担保。
- **中间 CA 证书**：根 CA 不直接发服务器证书（太危险，根 CA 私钥泄露就完了全景），而是授权中间 CA 去签发。
- **服务器证书**：你拿到的最终证书，由中间 CA 签发，证明"这个公钥确实属于 baidu.com"。

你的浏览器验证链时，从下往上走：检查服务器证书是否由中间 CA 签发→中间 CA 是否由根 CA 签发→根 CA 是否在"可信根"列表。**全部通过才算可靠。**

## 25.7 中间人攻击——为什么证书验证这么重要

### 没有证书时，攻击长这样

```
你                 攻击者（公共WiFi）             真正的百度
│                     │                            │
│──给服务器公钥─────→│                            │
│                     │←我拦截了你───────→│
│                     │  换成我自己的假公钥           │
│←──假公钥───────────│                            │
│                     │                            │
│──用假公钥加密数据───→│                            │
│                     │  解密→偷看→用真公钥加密→│
│                     │                            │
```

攻击者在中间**透明代理**——你以为是和真百度通信，其实先连到了攻击者，攻击者再连真百度。你发的东西攻击者都能看到，所有加密像白做一样。

### 证书怎么防

攻击者想冒充百度，就也要伪造一份证书。但伪造证书**必须由一个被你浏览器信任的 CA 签名**才能不被发现。如果攻击者没本事入侵根 CA（基本不可能），他的假证书就会被浏览器弹个"不安全"的红屏——`NET::ERR_CERT_AUTHORITY_INVALID`。

**你偶尔见到这个红屏的原因**：公司的内网监控系统、学校网络、某些杀毒软件——它们会自己签发一个中间 CA 证书，对本设备上的所有连接上做中间人检查。这本质上是"合法的中间人"：公司 IT 部门先在自己机器上安了自签 CA 证书，然后所有流量走代理检查。

## 25.8 实战：用 `openssl` 看 HTTPS 证书

### Windows

```powershell
# 如果没有 openssl，先装：
# winget install OpenSSL.Light
# 或者用 Git Bash 自带的

# 查看 baidu.com 的证书链
openssl s_client -connect baidu.com:443 -servername baidu.com -showcerts
```

### Linux / macOS

```bash
# 详细输出
openssl s_client -connect baidu.com:443 -servername baidu.com

# 只看证书信息（更清爽）
openssl s_client -connect baidu.com:443 -servername baidu.com </dev/null 2>/dev/null | openssl x509 -text -noout | head -30
```

macOS 注意：`</dev/null` 改成 `</dev/null` 或者直接用管道的方式。

运行后你会看到：
- 证书的 **Subject**（发给谁的，比如 `baidu.com`）
- **Issuer**（谁签发的，比如 `GlobalSign RSA OV SSL CA`）
- **Validity**（有效期）
- 证书链中的每一级

## 25.9 小结

| 概念 | 要点 |
|------|------|
| **HTTPS = HTTP + TLS** | TCP 之上先握手加密，再在隧道里传输 HTTP 报文 |
| **对称加密** | 加密解密用同一把钥匙，快速但有交换问题 |
| **非对称加密** | 公钥加私钥解，解决钥匙交换但慢，实际对称+非对称结合 |
| **TLS 1.3 握手** | 1-RTT 完成，比 TLS 1.2 的 2-RTT 快了一倍 |
| **加密套件** | `TLS_AES_256_GCM_SHA384`：AES-256加密 + GCM模式 + SHA-384哈希校验 |
| **证书链** | 根 CA→中间 CA→服务器证书，浏览器逐级向上验证信任 |
| **中间人攻击** | 劫持通信冒充服务器，证书验证防的就是这个 |

## 术语表

| 术语 | 解释 |
|------|------|
| **TLS (Transport Layer Security)** | 传输层安全协议，HTTPS 的加密层，在 TCP 之上、HTTP 之下 |
| **对称加密（Symmetric Encryption）** | 加密和解密用同一把密钥，速度快，但密钥安全交换是难题 |
| **非对称加密（Asymmetric Encryption）** | 公钥加密、私钥解密，解决了密钥交换问题但运算慢 |
| **公钥 / 私钥** | 非对称加密的密钥对，公钥可公开分发，私钥必须保密 |
| **证书 (Certificate)** | CA 机构签发的凭证，证明某个公钥确实属于特定域名 |
| **CA (Certificate Authority)** | 证书机构，负责验证身份并签发数字证书，是信任体系的根基 |
| **证书链 (Certificate Chain)** | 根 CA → 中间 CA → 服务器证书 的信任传递链 |
| **中间人攻击 (Man-in-the-Middle Attack)** | 攻击者在通信双方之间拦截、窃听或篡改数据的攻击方式 |
| **加密套件 (Cipher Suite)** | 规定一次 TLS 连接使用的加密算法组合（对称加密 + 密钥交换 + 哈希） |
| **会话密钥 (Session Key)** | TLS 握手后生成的临时对称密钥，用于本次连接的数据加密 |
| **向前安全性 (Forward Secrecy)** | 即使服务器私钥泄露，过去已完成的通信也不会被解密 |

## 验证方法

1. 打开 Chrome，访问 `https://baidu.com`，点地址栏左侧的🔒锁按钮。
2. 点击"连接是安全的"→"证书有效"→"证书详细信息"。

   - 证书发给谁（Subject：`baidu.com`）
   - 谁签发的（Issuer：比如 `DigiCert` 或 `GlobalSign`）

   ```bash
   openssl s_client -connect baidu.com:443 -servername baidu.com
   ```
   如果能看懂输出的摘要信息，说明你理解了本章。

## 最可能出错的地方及原因

1. **自签证书用于生产环境**：本机开发时 `openssl req -x509` 生成的自签证书浏览器不认，生产如果用自签，用户会看到大红屏警告，直接流失用户。生产环境必须买 CA 签发的证书或使用 Let's Encrypt。

2. **HTTPS 页面引用 HTTP 资源（Mixed Content）**：页面本身用 HTTPS 打开，但图片 `<img src="http://...">` 或请求走 HTTP。浏览器会拦截或至少给个警告（"不安全内容"），因为 HTTP 资源不受加密保护，会泄露到整页安全级别。解决：所有内部资源用 `https://` 或省略协议 `//use.relative.url`。

3. **以为 HTTPS 能防一切安全**：HTTPS 防的是**传输过程中的窃听和篡改**，不能防 XSS、SQL 注入、CSRF 这些应用层攻击。加密通道的两端（浏览器和服务器）本身如果被攻破，HTTPS 保不了。
