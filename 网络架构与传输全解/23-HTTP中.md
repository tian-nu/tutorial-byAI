# 23 — HTTP（中）：HTTP/2 与 HTTP/3 的革命

## 学习目标
- 理解 HTTP/1.1 的三大痛点，以及 HTTP/2 如何逐一解决
- 理解二进制分帧的动机——为什么"抛弃文本"是必要的一步
- 理解多路复用的原理，能说出它和 HTTP/1.1 管道化的本质区别
- 了解 HPACK 头部压缩的基本思路（静态表 + 动态表）
- 理解 HTTP/3 为什么抛弃 TCP 选择 QUIC，以及 0-RTT 和连接迁移的含义
- 能在浏览器 DevTools 中识别 h2 和 h3 连接

---

## 23.1 再好的补丁也打不过架构缺陷

第 22 章见识了 HTTP/1.1 的多项改进：持久连接、Host 头、分块传输……但不管怎么优化，HTTP/1.1 始终戴着三副镣铐：

**镣铐一：队头阻塞。** 第 19 章讲过，TCP 的可靠有序传输注定了队头阻塞——一个包丢了，后面所有包都得等它重传。HTTP/1.1 的管道化试图在应用层绕过这个问题，但因为响应必须按序返回，根本没绕过去。浏览器只能靠"多开 TCP 连接"来缓解（一个域名开 6~8 个连接），但这带来了第二个问题。

**镣铐二：Header 重复传输。** 第 22 章的 curl 输出里你看到了，每个请求都要带一整套 Header：`Host`、`User-Agent`、`Accept`、`Cookie`……这些头在同一个网站的不同请求中几乎完全相同，但每次都要原样发送一遍。如果你的 Cookie 有 2KB，发 100 个请求就重复传了 200KB 的冗余数据——全是浪费。

**镣铐三：并发连接数天花板。** 浏览器对同一域名的 TCP 连接数有限制（通常 6~8 个）。再多就得排队。而且每个 TCP 连接都要独立完成三次握手、慢启动、拥塞控制——6 个连接意味着 6 倍的连接开销。

这三个问题在 HTTP/1.1 的架构下都**无法根治**，因为它们根植于两个设计决定：① 文本协议，② 依赖 TCP 的单一有序字节流。HTTP/2 和 HTTP/3 分别对这两个决定做了"革命性修正"。

---

## 23.2 HTTP/2 的核心思想：不换传输层，换表达方式

HTTP/2 做了一个大胆但克制的决定：**保留 HTTP 的语义（方法、状态码、Header），但彻底改变编码方式——从文本变成二进制。**

你没看错。HTTP/2 并没有改变 HTTP 的"语言"——还是用 `GET`、`POST`、`200 OK`、`Content-Type` 这些概念。它改变的是"怎么写这些字"——从人类可读的 ASCII 文本，变成了机器友好的二进制帧。

> 文本对人友好但机器解析慢、容易出错、占空间。二进制是机器的母语——每条信息有固定的结构，直接按偏移量读取，不需要逐字节扫描换行符、不需要处理大小写歧义、不需要做字符串比较。

---

## 23.3 改进一：二进制分帧

在 HTTP/1.1 中，请求和响应就是一整块文本：

```
GET /index.html HTTP/1.1\r\n
Host: example.com\r\n
User-Agent: Mozilla/5.0\r\n
\r\n
```

服务器收到后要**逐字节扫描**：找 `\r\n` 分割行的位置，找空行分割 Header 和 Body 的位置，解析 Header 字段名时还要处理 `Host:` 和 `host:` 是不是同一个东西（根据 RFC，Header 名不区分大小写，但 HTTP/1.1 没强制，导致实现差异）。

HTTP/2 的做法：**把所有通信分解为一个个二进制帧（Frame）**。一个请求-响应不再是一块文本，而是多个帧的组合：

```
HTTP/2 连接 = 一个 TCP 连接
  ├── Stream 1: GET /index.html
  │     ├── HEADERS 帧（包含 method、path、headers 的二进制编码）
  │     └── DATA 帧（如果有请求体）
  ├── Stream 3: GET /style.css
  │     ├── HEADERS 帧
  │     └── 服务器的 HEADERS 帧 + DATA 帧
  └── Stream 5: POST /api/login
        ├── HEADERS 帧
        ├── DATA 帧（请求体）
        └── 服务器的 HEADERS 帧 + DATA 帧
```

每个帧有统一的结构：9 字节帧头（长度 + 类型 + 标志 + 流 ID）+ 可变长度的负载。解析器只需要读 9 个字节就知道这个帧是什么类型、属于哪个流、有多长——不需要扫描换行符，不需要做文本解析。

## 23.4 改进二：多路复用——真正的并发

这是 HTTP/2 最核心的改进。

回想 HTTP/1.1 的并发策略：开 6 个 TCP 连接，每个连接上串行发请求。这 6 个连接之间互不干扰——连接 1 上的阻塞不会影响连接 2。但代价是 6 倍的连接开销。

HTTP/2 的 **多路复用（Multiplexing）** 只用一个 TCP 连接，但在连接内部维护多个**相互独立的流（Stream）**：

```
HTTP/1.1 的"伪并行"（6 个 TCP 连接）：

TCP连接1: [请求A]......................[响应A]......................
TCP连接2: [请求B].........[响应B]...................................
TCP连接3: [请求C]....[响应C]........................................
（每个连接内部仍然串行，合起来看着像并行）

HTTP/2 的多路复用（1 个 TCP 连接，多个流交错传输）：

TCP连接:
[A帧1][B帧1][C帧1][A帧2][B帧2][A帧3][C帧2][B帧3][C帧3]
  Stream A ──────────────────────────────────────
  Stream B ──────────────────────────
  Stream C ────────────────
（A、B、C 的帧交错发送，互不等待）
```

这就好比 HTTP/1.1 是在 6 条单车道上各跑一辆车，HTTP/2 是在 1 条高速公路的不同车道上同时跑多辆车——路的总宽度差不多，但调度效率天差地别。

### 与应用层队头阻塞说再见（暂时）

HTTP/1.1 管道化的队头阻塞是在**应用层**的——请求 1 的响应卡住了，请求 2 的响应就算准备好了也发不出来。

HTTP/2 的多路复用彻底解决了应用层队头阻塞：流 A 丢了一个帧？没关系，流 B 和流 C 的帧照常交付。接收方按流 ID 分拣各自的帧，互不影响。

**但 TCP 层面的队头阻塞还在。** HTTP/2 底层用的还是一个 TCP 连接——如果 TCP 层面丢了一个包，整个连接的窗口都会卡住，所有流的数据都被阻塞。这个问题要到 HTTP/3 才能解决。

## 23.5 改进三：HPACK 头部压缩

第 22 章提到，HTTP/1.1 的 Header 大量重复传输。HTTP/2 用 **HPACK** 算法专门解决这个问题。

HPACK 的核心思路：**既然每次请求的 Header 都差不多，那我只传"和上次不一样的地方"就行了。**

具体做法是维护两张表：

### 静态表（Static Table）

HTTP/2 规范预置了一张包含 61 个最常见 Header 的静态表。比如：

| 索引 | Header 名 | Header 值 |
|------|----------|-----------|
| 1 | `:authority` | （空） |
| 2 | `:method` | `GET` |
| 3 | `:method` | `POST` |
| …… | …… | …… |
| 32 | `content-type` | `text/html; charset=utf-8` |

如果你要发的 Header 碰巧在静态表里，发送方只传一个**索引号**（比如 `32`），接收方查表就知道是 `content-type: text/html; charset=utf-8`。原本要传几十个字节，现在只传一个不超过 7 位的数字。

### 动态表（Dynamic Table）

静态表只有 61 条，涵盖不了所有 Header。动态表是在连接过程中**实时构建**的——每发一个新的 Header 组合，双方都把这条记录加到自己的动态表里。下次再发同样的 Header，只传动态表的索引。

```
第一次请求：
HEADERS 帧：{ :method: GET, :path: /index.html, cookie: session=abc123... }
→ 动态表加入: [62] cookie: session=abc123...

第二次请求：
HEADERS 帧：{ :method: GET, :path: /style.css, cookie: 索引62 }
→ cookie 只传一个索引号，省了几十字节
```

> 💡 **想多一点**：HPACK 的静态表其实包含了所有 HTTP/2 伪头（如 `:method`、`:path`、`:status`）的常见组合——`GET`、`POST`、`200`、`404` 这些高频值全都在静态表里。也就是说，大部分请求的 `:method: GET` 根本不需要传输，一个索引号就搞定了。这就是"把常见情况做快"（optimize for the common case）的经典设计。

### 为什么不是 gzip？

你可能会想：为什么不直接对 Header 做 gzip 压缩？HTTP/1.1 确实有 `Content-Encoding: gzip`，但那是对 Body 的。Header 不直接用 gzip 有两个原因：

1. **安全风险**：2012 年的 CRIME 攻击正是利用了 TLS + gzip 压缩来逐字节推测 Cookie 内容。HPACK 使用了专门的编码方式，避免了这种侧信道攻击。
2. **流间依赖**：gzip 是有状态的——必须按顺序解压。HTTP/2 的流是交错的，如果用 gzip 压缩整个连接的数据，一个流的丢包会导致所有流无法解压。HPACK 允许每个流独立压缩/解压。

## 23.6 改进四：Server Push（已式微）

HTTP/2 还定义了一个叫 **Server Push** 的功能：服务器可以"预判"客户端接下来会要什么，在客户端请求之前就把资源推送过去。

```
客户端：GET /index.html
服务器：200 OK + 给你 index.html，另外我还主动推送 style.css 和 app.js
```

理论上是好事——减少一次往返。但实际上非常难用对：
- 服务器很难准确预判客户端的缓存（可能客户端已经有 style.css 了，服务器还是推了一遍）
- 推送的资源会浪费带宽
- Chrome 在 2022 年已经**移除了 HTTP/2 Server Push 的支持**

现在这个功能被 `<link rel="preload">` 等前端声明式方案替代了——由前端告诉浏览器"这个资源很重要，请提前加载"，而不是服务器"替客户端做决定"。

❌ **常见混淆**：把 HTTP/2 Server Push 和 WebSocket 当成一回事。Server Push 是服务器在响应 HTML 时顺带推几个静态资源（CSS/JS），推完就完了，不是持久通道。WebSocket 是客户端和服务器之间建立的一条**全双工长连接**，双方随时可以互发消息。Server Push 像快递员送货时顺便多放了一个包裹在你门口；WebSocket 像你和朋友一直通着电话。

✅ **正确理解**：Server Push = HTTP 的一次性"预判推送"，WebSocket = 持久双向通信通道。两者解决的问题完全不同。

## 23.7 HTTP/3：不要 TCP 了，换 QUIC

HTTP/2 解决了很多问题，但有一个问题它解决不了：**TCP 层面的队头阻塞。**

第 19 章讲过，TCP 是可靠有序传输——丢了一个包，后面的包都得等着。HTTP/2 在应用层通过多路复用解决了应用层的队头阻塞，但底层 TCP 丢包时，连接上**所有流**的数据都无法交付。

```
HTTP/2 在 TCP 丢包时的表现：

Stream A: [帧A1][帧A2][...丢包...❌][帧A4]
Stream B: [帧B1][帧B2][帧B3]
Stream C: [帧C1][帧C2]

TCP 层面：帧A3 丢了 → 整个 TCP 连接被阻塞
→ 帧A4、帧B2、帧C1 全都在 TCP 接收缓冲区等着，无法交付给应用层
```

这就是 **TCP 层面的队头阻塞**——应用层再聪明也绕不过去。

### QUIC：在 UDP 上重建"可靠"

HTTP/3 的决定非常激进：**不用 TCP 了，改用 QUIC 协议（基于 UDP）。**

QUIC 由 Google 开发，它的核心思想是：**既然 TCP 的队头阻塞改不了（TCP 实现在操作系统内核里，改不动），那就在 UDP 之上重新实现一套"可靠的、加密的、多路复用的"传输层。**

回忆第 19 章 UDP 的特性——无连接、无确认、无重传、无流控。QUIC 在 UDP 之上自己实现了所有这些功能，但做对了一件事 TCP 没做对的：

> **在 QUIC 中，每个流是独立的。流 A 丢了一个包，只有流 A 被阻塞；流 B 和流 C 的数据照常交付。**

```
HTTP/3 (QUIC) 在丢包时的表现：

UDP 数据报: [流A-包1][流B-包1][流C-包1][流A-包2❌丢了][流B-包2][流C-包2][流A-包3]

→ 流 A：包2 丢了，等重传（只有流A卡住）
→ 流 B：包1、包2 都到了 ✅ 继续
→ 流 C：包1、包2 都到了 ✅ 继续
```

这就是 HTTP/3 对 HTTP/2 最关键的提升。

### 0-RTT 连接建立

TCP + TLS 建立安全连接至少需要 2 个 RTT（TCP 三次握手 + TLS 握手，第 15 章和第 25 章详解）。QUIC 把传输和加密合并成一个过程：

- **首次连接（1-RTT）**：QUIC 握手和 TLS 1.3 握手合并，一个往返搞定
- **再次连接（0-RTT）**：如果你之前连过同一个服务器，QUIC 可以**直接发送数据**——0 个往返延迟

0-RTT 的意思是：客户端在发出第一个包的时候，就已经在包里面携带了应用数据。这在移动网络（4G/5G 延迟动辄 100ms+）上的收益非常显著。

### 连接迁移：WiFi 切 4G 不中断

这是 QUIC 最酷的特性之一。TCP 用 **四元组（源 IP + 源端口 + 目的 IP + 目的端口）** 标识一个连接——如果你的 IP 变了（WiFi 切 4G），四元组就变了，TCP 连接就断了，必须重新握手。

QUIC 不使用四元组，而是用 **Connection ID** 来标识连接。不管你的 IP 怎么变，只要 Connection ID 不变，连接就不断。你从家里出门，手机从 WiFi 切换到 4G——QUIC 连接无缝继续，不需要重建。

## 23.8 实操：在浏览器中看到 h2 和 h3

打开 Chrome 或 Edge，按 `F12` → **Network（网络）** 标签 → 刷新页面。在请求列表的表头右键 → 勾选 **Protocol（协议）**。你会看到：

```
Name              Protocol
index.html        h2
style.css         h2
app.js            h2
api/getUser       h3
```

- `h2` 表示 HTTP/2
- `h3` 表示 HTTP/3（QUIC）

如果看到 `http/1.1`，说明这个网站还没升级到 HTTP/2 或 HTTP/3。

> 💡 **想多一点**：HTTP/3 的普及率已经很高了。Google、YouTube、Facebook、Cloudflare 全线支持 h3。国内大厂的 CDN 也在快速跟进。不过因为 QUIC 走 UDP，某些企业网络和公共 WiFi 可能会封 UDP 端口导致降级到 HTTP/2——这是目前 HTTP/3 最大的落地障碍。

## 23.9 小结

| 概念 | 要点 |
|------|------|
| HTTP/1.1 三大痛点 | 队头阻塞、Header 重复传输、并发连接数天花板 |
| HTTP/2 二进制分帧 | 文本 → 二进制，机器解析更快更准更省空间；统一 9 字节帧头 |
| 多路复用（Multiplexing） | 一个 TCP 连接上多条流交错传输，互不阻塞，解决应用层队头阻塞 |
| 流（Stream） | HTTP/2 连接内独立传输通道，按 Stream ID 分拣帧 |
| HPACK | Header 压缩算法，静态表（61 条预置）+ 动态表（连接中学习到的） |
| TCP 层队头阻塞 | HTTP/2 仍在 TCP 之上，丢包时全部流被阻塞——需 HTTP/3 解决 |
| QUIC | 基于 UDP 的新传输协议，集成可靠传输 + TLS + 多路复用 |
| 0-RTT | QUIC 支持恢复连接时直接发送数据，零往返延迟 |
| 连接迁移 | QUIC 用 Connection ID 替代四元组，IP 变化不断连 |
| HTTP/3 | 基于 QUIC 的 HTTP，彻底解决 TCP 队头阻塞 |
| Server Push | HTTP/2 服务器主动推送资源，已式微（Chrome 移除），不要和 WebSocket 混淆 |

## 术语表

| 术语 | 解释 |
|------|------|
| **二进制分帧（Binary Framing）** | HTTP/2 核心机制：将 HTTP 消息拆分为二进制帧传输，取代文本解析 |
| **帧（Frame）** | HTTP/2 最小传输单元，9 字节帧头 + 负载 |
| **多路复用（Multiplexing）** | 单 TCP 连接上同时传输多个请求/响应的流，各自独立，互不阻塞 |
| **流（Stream）** | HTTP/2 连接内的独立双向字节流，按 Stream ID 标识 |
| **HPACK** | HTTP/2 的 Header 压缩算法，使用静态表 + 动态表 + Huffman 编码 |
| **静态表（Static Table）** | HPACK 预置的 61 条常见 Header 映射，如 `:method: GET` → 索引 2 |
| **动态表（Dynamic Table）** | HPACK 连接过程中逐步建立的 Header 索引，变动的 Header（如 Cookie）在首次发送后入表 |
| **Server Push** | HTTP/2 服务器主动推送资源的能力，Chrome 已移除，实际使用少 |
| **QUIC（Quick UDP Internet Connections）** | Google 开发、基于 UDP 的传输协议，集成可靠传输、TLS 1.3 加密和多路复用 |
| **0-RTT** | QUIC 特性：恢复连接时第一包即可携带应用数据，零往返延时 |
| **连接迁移（Connection Migration）** | QUIC 特性：用 Connection ID 标识连接，客户端 IP 变化（WiFi → 4G）时连接不中断 |
| **HTTP/3** | 基于 QUIC 的 HTTP 版本，彻底消除 TCP 层面的队头阻塞 |
