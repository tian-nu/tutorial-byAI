## 22.1 一个网页的背后

你在浏览器地址栏敲下 `baidu.com`，回车。

第 20 章告诉你 DNS 怎么把域名变成 IP。第 15 章讲过 TCP 三次握手怎么建立连接。现在，TCP 连接建立了——接下来呢？

你需要告诉服务器："请把首页发给我。" 服务器收到后说："好的，这是你要的页面。" 这段对话用的语言，就是 **HTTP（HyperText Transfer Protocol，超文本传输协议）**。

> 把 HTTP 想象成**餐厅的点餐协议**：你是顾客（客户端），服务员是 HTTP，后厨是服务器。你递给服务员一张点餐单（请求）："一份红烧肉、一碗米饭。" 服务员拿去后厨，把菜端回来给你（响应）。你不会关心后厨的炉灶型号、有几口锅——你只关心点了什么、端回来什么。HTTP 要的就是这个效果：**让浏览器和服务器只用一套简单的"菜单语言"就能通信，不必关心下层细节。**

## 22.2 HTTP 最核心的四个特征

在深入技术细节之前，先把 HTTP 的"性格"搞清楚：

### 特征一：请求-响应模型

永远是你（客户端）先开口，服务器再回答。服务器不会主动给你发消息（WebSocket 和 Server-Sent Events 是后来加的扩展，不是 HTTP 本身的能力）。

```
你：GET /index.html  （我要首页）
服务器：200 OK，给你  （这是首页的HTML）

你：不开口      （沉默）
服务器：        （也沉默——服务器不会主动说话）
```

### 特征二：无状态

HTTP 天然是"失忆"的——每个请求都是独立的，服务器不记得你上一次请求了什么。

```
请求1：GET /login，带上用户名密码 → 服务器说"登录成功"
请求2：GET /my-profile              → 服务器说"你是谁？我不记得你登录过"
```

这就是为什么需要 **Cookie** 和 **Session**——通过额外机制让无状态的 HTTP 变得"有记忆"。Cookie 本质上就是服务器在你身上贴了个号码牌："下次来，出示这个号码牌，我就知道你是谁了。"

> 💡 **想多一点**：HTTP 的"无状态"不是 Bug，而是刻意的设计选择。如果 HTTP 默认有状态，服务器就要为每个客户端维护连接状态——一台服务器同时处理几十万个客户端时，内存早就爆了。无状态意味着服务器可以"转身就忘"，极大降低了服务端的复杂度。Cookie 把状态存储的负担转移给了客户端，这是 RESTful 架构的核心理念之一。

### 特征三：基于 TCP

HTTP/1.x 和 HTTP/2 都运行在 TCP 之上。这意味着 HTTP 的可靠性、拥塞控制、流量控制都交给了 TCP（第 15~18 章）。HTTP 本身只关心"说什么"，不关心"怎么可靠地送到"。HTTP/3 改用了基于 UDP 的 QUIC（第 23 章），但 1.x 和 2 都还是 TCP 的"租客"。

### 特征四：可扩展

HTTP 通过 Header 扩展功能——缓存控制、认证、压缩、跨域……几乎所有 HTTP 的高级功能都是通过添加 Header 字段来实现的，不需要改协议本身。

## 22.3 版本简史：三十年进化

HTTP 从 1991 年诞生至今，经历了四个主要版本：

```
1991  HTTP/0.9  →  只支持 GET，没有 Header，没有状态码，返回纯 HTML（一句说完）
1996  HTTP/1.0  →  加了 Header、状态码、POST、Content-Type（有了"表单"）
1997  HTTP/1.1  →  持久连接、Host 头、管道化、分块传输（一个连接传多文件）
2015  HTTP/2    →  二进制分帧、多路复用、头部压缩（大幅提速，第 23 章）
2022  HTTP/3    →  基于 QUIC/UDP，0-RTT，连接迁移（彻底解决 TCP 队头阻塞，第 23 章）
```

如果把 HTTP 的进化比作快递行业：
- **0.9** 是"只送信，一次一封信，送完就走，没有任何签收确认"
- **1.0** 是"加了快递单（Header），能写寄件人、收件人、物品类型、签收状态"
- **1.1** 是"同一辆货车（TCP 连接）可以送多个包裹，不用每送一个就重新发动一次车"
- **2** 是"货车里的包裹可以同时装卸，不用排队"
- **3** 是"不要货车了，用无人机（UDP），每个包裹独立飞"

## 22.4 HTTP/1.1 的四大核心特性

### 特性一：持久连接（Keep-Alive）

**HTTP/1.0 的痛**：每请求一个文件，就要建一次 TCP 连接（三次握手），用完了马上关闭（四次挥手）。一个网页通常由几十个文件组成（HTML + CSS + JS + 图片），每下载一个文件就要握手挥手一次——光连接建立和拆除的时间就占了总耗时的 30% 以上。

**HTTP/1.1 的解法**：默认开启 **持久连接**（也叫 Keep-Alive）。同一个 TCP 连接可以复用——下载完 HTML 后，连接不关，继续下载 CSS、JS、图片……全部下完了再关。

```
HTTP/1.0（短连接）：
TCP连接1: GET index.html    → 关闭
TCP连接2: GET style.css     → 关闭
TCP连接3: GET app.js        → 关闭
TCP连接4: GET logo.png      → 关闭
（每文件一次握手+挥手，浪费巨大）

HTTP/1.1（持久连接）：
TCP连接1: GET index.html → GET style.css → GET app.js → GET logo.png → 关闭
（一次握手，传四个文件，一次挥手）
```

### 特性二：管道化（Pipelining）

持久连接解决了一个问题：不用重复握手了。但还有一个问题：**请求还是要排队**。

在持久连接上，HTTP/1.1 引入了**管道化**——不等上一个响应回来，就可以连续发送下一个请求。

```
非管道化：
客户端：[发请求1] ............等待响应1........... [发请求2] ...........等待响应2...........
服务器：          [处理][回响应1]                              [处理][回响应2]

管道化：
客户端：[发请求1][发请求2][发请求3]
服务器：[处理1][回响应1][处理2][回响应2][处理3][回响应3]
```

理想很美好，但现实中有个致命问题——**队头阻塞（Head-of-Line Blocking）**。

第 19 章讲过，队头阻塞是 TCP 可靠有序传输的副作用：如果前面一个数据包丢了，后面所有数据包都必须等着。管道化在这里也遇到了类似的问题：如果请求 1 的响应特别慢（比如请求的是一个大文件），请求 2 和请求 3 的响应就算已经准备好了，也被堵在后面出不来——因为 **HTTP/1.1 要求响应必须按请求顺序返回**。

❌ **常见误解**：以为管道化能真正实现并发。实际上因为队头阻塞，几乎所有主流浏览器（Chrome、Firefox、Safari）都**默认关闭或从未真正启用** HTTP/1.1 管道化。真正解决并发问题的是 HTTP/2 的多路复用（第 23 章）。

✅ **正确理解**：HTTP/1.1 的实际做法是**开多个 TCP 连接**（浏览器的做法是同时对同一个域名开 6~8 个连接），每个连接上串行发请求——用"多个串行"模拟出"伪并行"。

### 特性三：Host 头

这是 HTTP/1.1 最不起眼但最重要的改进。在 HTTP/1.0 中，请求行只包含路径：

```
GET /index.html HTTP/1.0
```

服务器一看：你要 `/index.html`。但如果这台服务器上托管了两个网站（`example.com` 和 `example.org`），服务器怎么知道你要的是哪个网站的 `/index.html`？答案：**不知道**。HTTP/1.0 时代，一个 IP 只能绑一个域名。

HTTP/1.1 加了一个 `Host` 请求头：

```
GET /index.html HTTP/1.1
Host: www.example.com
```

服务器看到 `Host` 头，就知道你要的是 `www.example.com` 的 `/index.html`，而不是同一台服务器上 `www.example.org` 的。**一个 IP 可以托管无限多个域名**，这就是"虚拟主机"（Virtual Host）的基础——也是现代互联网能容纳数亿网站的关键技术之一。

### 特性四：分块传输（Chunked Transfer Encoding）

有时候服务器在开始发响应时，还不知道整个响应体有多大——比如动态生成一个超大的报表，数据还在从数据库里往外流，服务器没法提前算好文件大小。

HTTP/1.0 的做法：必须在响应头里先写 `Content-Length: 12345`，告诉客户端"我要发 12345 字节"，然后再发。如果大小不确定，就只能等全部生成完才知道——客户端一直干等着。

HTTP/1.1 的分块传输：不写 `Content-Length`，而是写 `Transfer-Encoding: chunked`，然后把数据切成一块一块地发，每块前面标这一块的大小。最后一个块大小标 `0`，表示"发完了"。

```
HTTP/1.1 200 OK
Transfer-Encoding: chunked

1A\r\n              ← 这一块 26 字节
<html><head><title> ← 26 字节数据
1B\r\n              ← 这一块 27 字节
Example Domain</ti  ← 27 字节数据
0\r\n               ← 大小 0，表示结束
\r\n
```

客户端收到 `0\r\n` 就知道数据发完了。这样服务器可以**边生成边发送**，客户端也能**边接收边渲染**。

> 💡 **想多一点**：你平时看的视频网站（B 站、YouTube）虽然用的是 HTTP 协议，但视频流本身不是分块传输——太慢了。视频传输用的是专门的流媒体协议（如 HLS、DASH），它们把视频切成几百个小段（几秒一段），每个小段是一个独立的 HTTP 请求。这样用户可以随时快进、切换清晰度——"分块"思想在应用层用得更灵活。

## 22.5 请求方法：不只 GET 和 POST

HTTP 定义了多种请求方法（也叫"动词"），每种表达一种意图：

| 方法 | 含义 | 幂等？ | 安全？ | 典型用途 |
|------|------|--------|--------|----------|
| **GET** | 获取资源 | ✅ 幂等 | ✅ 安全 | 访问网页、搜索、API 查询 |
| **POST** | 创建资源 / 提交数据 | ❌ 不幂等 | ❌ | 提交表单、上传文件、登录 |
| **PUT** | 替换资源（全量更新） | ✅ 幂等 | ❌ | REST API 更新用户信息 |
| **DELETE** | 删除资源 | ✅ 幂等 | ❌ | REST API 删除数据 |
| **HEAD** | 只取响应头（不要 Body） | ✅ 幂等 | ✅ 安全 | 检查文件是否存在 |
| **OPTIONS** | 询问服务器支持哪些方法 | ✅ 幂等 | ✅ 安全 | CORS 预检请求 |

### 幂等性：同一个操作做多次，结果一样

**幂等（Idempotent）** 是 HTTP 中最容易被忽略但最重要的概念之一。它来自数学术语，原意是 `f(f(x)) = f(x)`，在 HTTP 语境中的意思是：

> **同一个请求执行一次和执行多次，服务器的最终状态是一样的。**

举个例子：
- 你点了一份外卖（POST），不小心点多了——重复点了 3 次，后厨给你做了 3 份。状态变了：从 0 份变成了 3 份。**POST 不幂等**。
- 你问服务员"3 号桌在哪"（GET），问了 3 遍，3 号桌没变——餐厅里还是那 3 号桌。**GET 幂等**。
- 你用银行卡取了 500 元（POST），不小心操作了两遍——余额少了 1000。你这是在**创建两笔取款记录**，不是幂等的。
- 你把银行卡余额**设置为** 0 元（PUT），操作了两遍——第一遍变成 0，第二遍还是 0。**PUT 幂等**。

为什么幂等性重要？因为它决定了**出了错能不能安全重试**：
- GET 请求没收到响应？直接重试，不会有副作用。
- POST 请求没收到响应？**不能盲目重试**——可能扣了两次钱、下了两个订单。
- PUT 和 DELETE 可以安全重试——执行一遍和两遍效果一样。

### GET 和 POST 的重要区别（不止幂等）

| 维度 | GET | POST |
|------|-----|------|
| 参数位置 | URL 的 Query String（`?key=value`） | 请求体（Request Body） |
| 长度限制 | URL 有限制（浏览器 2KB~8KB） | 理论上无限制 |
| 缓存 | 可被浏览器/代理缓存 | 默认不缓存 |
| 书签 | 可收藏 | 不可收藏 |
| 幂等 | ✅ | ❌ |

## 22.6 curl -v 实操：亲手看 HTTP 对话

现在我们用 `curl -v` 来亲眼看一次完整的 HTTP 交互。`curl` 是命令行下的 HTTP 客户端，Windows 10 1803 以上、macOS、Linux 都自带。

我们用 `httpbin.org` ——一个专门用来测试 HTTP 的免费服务。

```bash
curl -v http://httpbin.org/get
```

输出如下（加了注释解读）：

```
*   Trying 54.89.253.173:80...              ← DNS 解析 + TCP 连接
* Connected to httpbin.org (54.89.253.173) port 80

> GET /get HTTP/1.1                          ← 请求行：方法 + 路径 + 版本
> Host: httpbin.org                          ← 请求头：目标域名
> User-Agent: curl/8.x                       ← 请求头：客户端身份
> Accept: */*                                ← 请求头：接受任何类型
>                                            ← 空行，请求头结束

< HTTP/1.1 200 OK                            ← 响应行：版本 + 状态码 + 短语
< Date: Sat, 08 Jun 2026 10:00:00 GMT       ← 响应头：服务器时间
< Content-Type: application/json             ← 响应头：响应体是 JSON
< Content-Length: 258                        ← 响应头：响应体 258 字节
< Connection: keep-alive                     ← 响应头：连接保持
< Server: gunicorn/19.9.0                     ← 响应头：服务器软件
< Access-Control-Allow-Origin: *             ← 响应头：允许跨域
<                                            ← 空行，响应头结束

{                                            ← 响应体开始
  "args": {},
  "headers": {
    "Accept": "*/*",
    "Host": "httpbin.org",
    "User-Agent": "curl/8.x"
  },
  "origin": "你的公网IP",
  "url": "http://httpbin.org/get"
}                                            ← 响应体结束
```

逐段解读：

**① `> ` 开头的行 → 请求（客户端发给服务器）**

- `GET /get HTTP/1.1`：请求行。我是一名要通过 `GET` 获取 `/get` 这个资源，用的 HTTP/1.1 协议。
- 后面的 `Host:`、`User-Agent:`、`Accept:` 都是请求头（Header），告诉服务器额外信息。
- 空行（单独一个 `>`）：请求头到此为止。如果有请求体（POST 时），空行后面接着 Body。

**② `< ` 开头的行 → 响应（服务器回给客户端）**

- `HTTP/1.1 200 OK`：响应行。协议版本、状态码 200（成功）、人类可读的描述"OK"。
- `Content-Type: application/json`：告诉客户端，响应体是 JSON 格式（客户端就知道该用什么解析器）。
- `Content-Length: 258`：响应体有 258 字节。
- 空行后：响应体——JSON 数据。httpbin.org 很贴心地把你的请求信息原样返回了。

### 实战其他方法

```bash
# POST 请求（不幂等！）
curl -v -X POST http://httpbin.org/post -d "name=zhangsan&age=25"

# PUT 请求（幂等）
curl -v -X PUT http://httpbin.org/put -d "{\"name\":\"lisi\"}"

# DELETE 请求（幂等）
curl -v -X DELETE http://httpbin.org/delete

# HEAD：只看头，不要体
curl -v -I http://httpbin.org/get
```

```powershell
# Windows PowerShell 中，curl 可能被别名为 Invoke-WebRequest
# 用 curl.exe 明确调用真正的 curl
curl.exe -v http://httpbin.org/get
```

## 22.7 HTTP 状态码速览

你没有必要背全部状态码，但以下这些你一定会遇到：

| 范围 | 含义 | 最常见 |
|------|------|--------|
| **1xx** | 信息性 | `101 Switching Protocols`（WebSocket 升级用） |
| **2xx** | 成功 | `200 OK`、`201 Created`、`204 No Content` |
| **3xx** | 重定向 | `301` 永久、`302` 临时、`304 Not Modified`（缓存用） |
| **4xx** | 客户端错误 | `400 Bad Request`、`401 Unauthorized`、`403 Forbidden`、`404 Not Found`、`405 Method Not Allowed` |
| **5xx** | 服务器错误 | `500 Internal Server Error`、`502 Bad Gateway`、`503 Service Unavailable`、`504 Gateway Timeout` |

## 22.8 小结

| 概念 | 要点 |
|------|------|
| HTTP 是什么 | 应用层协议，请求-响应模型，无状态，基于 TCP（1.x/2） |
| 请求-响应模型 | 永远是客户端先开口，服务器不主动发消息 |
| 无状态 | 每个请求独立，服务器"转身就忘"；通过 Cookie/Session 补充状态 |
| HTTP/1.0 → 1.1 四大改进 | 持久连接（复用 TCP）、Host 头（虚拟主机）、管道化（理论上不等响应）、分块传输（边生成边发送） |
| 持久连接（Keep-Alive） | 一个 TCP 连接传多个文件，省去重复握手挥手 |
| 管道化 | 不等响应就发下一个请求，但因队头阻塞（回见第 19 章），浏览器几乎不用 |
| Host 头 | 一个 IP 托管多域名的基础，没有它就没有现代虚拟主机 |
| 分块传输 | Transfer-Encoding: chunked，服务器不知道文件总大小时也能开始发送 |
| 幂等性 | 同一操作执行多次结果一样：GET/PUT/DELETE 幂等，POST 不幂等 |
| 安全重试 | 幂等方法可以放心重试，POST 需要额外机制（幂等键）防重复 |

## 术语表

| 术语 | 解释 |
|------|------|
| **HTTP（HyperText Transfer Protocol）** | 超文本传输协议，应用层协议，浏览器和服务器之间通用的"菜单语言" |
| **请求-响应模型** | 客户端先发请求，服务器再回响应；服务器不主动推送 |
| **无状态（Stateless）** | HTTP 的本性：每个请求独立，服务器不记得之前的请求 |
| **Cookie** | 弥补 HTTP 无状态的机制：服务器在客户端存一个标识牌，下次请求自动带上 |
| **持久连接（Keep-Alive）** | HTTP/1.1 默认：一个 TCP 连接可复用多次请求/响应，不用每次都三次握手 |
| **管道化（Pipelining）** | 不等上一个响应就发下一个请求，但因队头阻塞实际很少用 |
| **Host 头** | HTTP/1.1 必须字段，告诉服务器你想访问哪个域名（一台服务器托管多个网站的基础） |
| **分块传输（Chunked Transfer Encoding）** | 服务器不知道响应总大小时，拆成多块发送；每块标注大小，最后一块大小为 0 |
| **幂等性（Idempotent）** | 同一操作执行一次和执行 N 次，服务器最终状态相同 |
| **GET** | 幂等、安全的请求方法，用于获取资源，参数在 URL 上 |
| **POST** | 不幂等、不安全的请求方法，用于创建资源或提交数据，参数在请求体 |
| **PUT** | 幂等的方法，用于全量替换资源 |
| **DELETE** | 幂等的方法，用于删除资源 |
| **状态码** | 三位数字，表示请求结果：2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误 |

## 验证方法

在终端执行：

```bash
curl -v http://httpbin.org/get
```

然后逐行解释输出，能说出：
1. 请求行包含哪三个部分？
2. 哪一行是请求头结束的标志？
3. 响应行中 `200` 是什么？
4. `Content-Type` 和 `Content-Length` 分别告诉你什么？
5. 空行之后的内容是什么？

再回答一个口头问题：
- 为什么银行转账接口一定用 POST 而不是 GET？如果 POST 请求没收到响应，直接重试会有什么风险？

如果你能解释清楚这些，说明本章目标达成。
