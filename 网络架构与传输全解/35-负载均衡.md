## 35.1 为什么需要负载均衡

### 单机时代的死局

假设你开了一家餐厅，只有一个厨师（一台服务器）：

- 平时 10 个客人 → 厨师应付自如
- 高峰期 100 个客人 → 厨师崩溃，所有人等餐
- 厨师请假 → 餐厅关门

解决方案不是找一个"更快的厨师"，而是**多雇几个厨师**，然后让一个领班（负载均衡器）把客人分配给空闲的厨师。

```
没有负载均衡：                      有负载均衡：
用户 → 服务器A（一个人扛）          用户 ─→ 负载均衡器 ─→ 服务器A
                                    用户 ─→              ─→ 服务器B
                                    用户 ─→              ─→ 服务器C
```

### 好处

1. **水平扩展**：业务量上来了，加机器就行，不需要改代码
2. **高可用**：一台服务器挂了，自动切到其他服务器，用户无感知
3. **灵活运维**：可以单独下线某台服务器维护，不影响服务

💡 **想多一点：单机能扛就别上负载均衡**

负载均衡虽然好，但它本身就是一层额外的网络跳转，会增加延迟。如果你的业务一天就几百个请求，一台机器完全够用，加负载均衡是"脱裤子放屁"。先判断是否需要，再决定怎么加。不要为了"架构完善"而过早优化。

## 35.2 L4 vs L7：负载均衡的两大层次

负载均衡可以在网络的不同层工作。最关键的分界线：**四层（L4）和七层（L7）**。

### 四层负载均衡（L4 Load Balancing）

**工作在 OSI 传输层**，只看数据包的 IP 地址和端口（TCP/UDP），不看内容。

**比喻**：交警在十字路口指挥交通。交警不管你的车是什么颜色、里面坐了多少人、要去哪家店——只管"这辆车走左边车道，那辆车走右边车道"。

**决策依据**：
- 源 IP + 源端口
- 目标 IP + 目标端口

**特点**：
- 极快：只解析到传输层头部，不关心上层协议
- 通用：不关心你是 HTTP、MySQL、Redis 还是 SSH
- 粗粒度：不知道请求什么 URL、带什么 Cookie、是 GET 还是 POST

### 七层负载均衡（L7 Load Balancing）

**工作在 OSI 应用层**，能解析 HTTP/HTTPS 协议内容，根据 URL、Header、Cookie 等做路由决策。

**比喻**：餐厅领班。领班看到客人进来，可以根据"这位客人预订了包厢"（看 Cookie）、"这位客人要去寿司区"（看 URL 路径）、"这位客人是 VIP"（看 Header），决定把他带去不同的区域。

**决策依据**：
- URL 路径（`/api/` → 后端服务，`/static/` → 静态资源）
- HTTP Header（`User-Agent` 区分移动端/桌面端）
- Cookie（会话保持）
- 请求方法（GET/POST）

**特点**：
- 慢一些：需要完整的 TCP 连接 + TLS 解密 + HTTP 解析
- 灵活：可以根据内容智能路由
- 必须能理解应用层协议（Nginx 对 HTTP，HAProxy 对 HTTP/MySQL）

### 对比表

| 维度 | L4 负载均衡 | L7 负载均衡 |
|------|-----------|-----------|
| 工作层 | 传输层（IP + Port） | 应用层（HTTP/HTTPS） |
| 速度 | 快（只看包头） | 慢（需要解析协议） |
| 路由粒度 | 粗（按连接） | 细（按 URL/Cookie/Header） |
| 协议支持 | 任何 TCP/UDP | 需要理解具体协议 |
| 典型产品 | LVS、F5 硬件、Nginx stream | Nginx http、HAProxy、Traefik |
| 适用场景 | 简单分流、数据库代理 | Web 应用、API 网关、A/B 测试 |

## 35.3 五种负载均衡算法

负载均衡器拿到一个请求，决定发给哪台后端服务器——这叫**调度算法**。下面五种是最常用的。

### 35.3.1 轮询（Round Robin）

**规则**：按顺序轮流分配。第 1 个请求给 A，第 2 个给 B，第 3 个给 C，第 4 个回到 A……

```
请求序列： 1   2   3   4   5   6   ...
服务器：   A → B → C → A → B → C → ...
```

**优点**：最简单，每台服务器平均分配请求。

**缺点**：不看服务器实际负载。如果 A 性能差、处理慢，它的请求累积越来越多，而 B 和 C 闲着。

### 35.3.2 加权轮询（Weighted Round Robin）

**规则**：给每台服务器设一个权重，能力强多分配，能力弱少分配。

```
服务器 A：性能强，权重 = 5
服务器 B：性能一般，权重 = 3
服务器 C：性能弱，权重 = 2

请求序列：A A A A A B B B C C（每 10 个请求的分配比例）
```

**优点**：考虑了服务器性能差异。

**缺点**：还是不看实时负载。A 可能正好在处理一个超慢请求，但调度器不知道，继续往 A 塞。

### 35.3.3 最少连接（Least Connections）

**规则**：谁当前处理的连接数最少，就发给谁。

**优点**：动态感知负载，性能好的服务器自然处理得快、连接数少、得到更多请求。

**缺点**：依赖"连接数"作为负载指标，但连接数多不一定代表压力大。一个 WebSocket 长连接（几乎不传数据）和一个短连接（在传 500MB 文件）的连接数都是 1。

### 35.3.4 IP Hash

**规则**：对客户端 IP 做哈希运算，同一个 IP 的请求永远发给同一台服务器。

```
hash("192.168.1.100") % 3 = 1  → 永远发给服务器 1
hash("192.168.1.101") % 3 = 2  → 永远发给服务器 2
hash("192.168.1.102") % 3 = 0  → 永远发给服务器 0
```

**优点**：天然实现了会话保持——同一个用户的请求总是打到同一台服务器，不需要共享 Session。

**致命缺陷 — 节点增减时全乱套**：

假设原来有 3 台服务器（A, B, C），`% 3` 取模。现在加了一台服务器 D，取模变成 `% 4`。几乎所有哈希结果都变了——原来发给 A 的用户可能现在发给了 B，原来发给 B 的发给了 C。**所有用户的"绑定关系"全部作废**。

```
原来的映射（% 3）：                加节点后（% 4）：
hash("192.168.1.100") % 3 = 1 → B     hash("192.168.1.100") % 4 = 0 → A  ❌ 变了！
hash("192.168.1.101") % 3 = 2 → C     hash("192.168.1.101") % 4 = 1 → B  ❌ 变了！
hash("192.168.1.102") % 3 = 0 → A     hash("192.168.1.102") % 4 = 2 → C  ❌ 变了！
```

### 35.3.5 一致性哈希（Consistent Hashing）

一致性哈希就是为了解决"节点增减导致所有映射全乱"这个问题而设计的。

**核心思想**：不用取模，改用**环形哈希空间**。

### 环形空间图解

```
把哈希值的取值范围（0 ~ 2^32-1）想象成一个圆环：

                        0
                   /         \
                 /             \
           ...                   ...
          |                       |
          |     • 服务器A         |
          |      (hash=100)      |
          |                       |
          |     • 服务器B         |
          |      (hash=300)      |
          |                       |
          |     • 服务器C         |
          |      (hash=700)      |
          |                       |
           ...                   ...
                 \             /
                   \         /
                    2^32-1
```

每个服务器通过哈希函数映射到环上的一个点。当一个请求到来时：

1. 对请求的 IP 做哈希，得到环上的一个点
2. **顺时针**找到环上第一个遇到的服务器节点
3. 请求就发到那台服务器

```
请求 hash = 150 → 顺时针找 → 第一个遇到服务器 B(hash=300) → 发给 B
请求 hash = 500 → 顺时针找 → 第一个遇到服务器 C(hash=700) → 发给 C
请求 hash = 800 → 顺时针找 → 绕一圈回到服务器 A(hash=100) → 发给 A
```

### 节点增减时只影响相邻节点

**加节点**（在 hash=500 位置新增服务器 D）：

```
加 D 之前：
请求 hash=400 → 顺时针 → 服务器 C(hash=700)

加 D 之后：
请求 hash=400 → 顺时针 → 服务器 D(hash=500)  ← 只有这部分请求变了
请求 hash=600 → 顺时针 → 服务器 C(hash=700)  ← 不受影响
```

只有原本会发到 C 的那段弧上的部分请求（hash 在 300~500 之间）现在发给 D。**其他所有映射不受影响**。

**减节点**（服务器 B 挂了）：

```
只有原本发给 B 的请求（hash 在 100~300 之间）需要重新映射到 C。
其他所有映射不受影响。
```

### 一致性哈希 vs IP Hash 本质区别

| 维度 | IP Hash（取模） | 一致性哈希（环形） |
|------|---------------|-------------------|
| 数据结构 | 线性数组 | 环形哈希空间 |
| 节点增减影响 | 几乎所有映射全乱 | 只影响相邻节点的那一段弧 |
| 缓存友好度 | 极差（加一台机器，缓存全废） | 极好（大部分缓存仍然有效） |
| 适用场景 | 节点数固定不变 | 节点频繁增减（弹性扩缩容） |
| 是否需要虚拟节点 | 不需要 | 建议加，否则分配不均 |

❌ **常见误区**："一致性哈希让所有请求均匀分布"
✅ **真相**：一致性哈希不能保证均匀分布（节点少的环上可能有"数据倾斜"——大段弧上没有节点）。解决方案是引入**虚拟节点**（Virtual Node）：每个物理节点在环上映射多个虚拟点，让分布更均匀。Nginx 的一致性哈希实现已经内置了虚拟节点。

## 35.4 负载均衡器软硬件区分

负载均衡器有两种形态：

| 类型 | 代表产品 | 优点 | 缺点 |
|------|---------|------|------|
| **软件** | Nginx、HAProxy、Traefik、Envoy | 免费、灵活、可部署在任何服务器、配置即代码 | 性能受限于服务器硬件 |
| **硬件** | F5 BIG-IP、A10、Citrix ADC | 专用芯片处理，吞吐量极高（Tbps 级）、延迟极低 | 贵（几十万起步）、配置复杂、不灵活 |

**选型原则**：
- 绝大多数场景：Nginx/HAProxy 软件负载均衡完全够用
- 超大规模金融/运营商场景：考虑硬件负载均衡（F5）
- 云原生/K8S 场景：Traefik/Envoy + Service Mesh 更合适

💡 **想多一点：软件 LB 已经能跑到 100Gbps+**

现代服务器 + DPDK（跳过内核网络栈直接处理数据包的框架）+ Nginx/Envoy 的软件负载均衡，单机轻松处理 100Gbps 甚至更高的流量。硬件 LB 的优势在缩小，除非你是阿里/腾讯级别的流量，否则软件 LB 是最优选择。

## 35.5 健康检查：自动剔除挂掉的服务器

负载均衡器需要持续探测后端服务器的健康状况——这叫**健康检查**（Health Check）。

### 检查方式

**TCP 端口检查**：每隔 N 秒向后端服务器的目标端口发起 TCP 连接。三次握手成功 → 健康；连接拒绝或超时 → 不健康。

```nginx
# Nginx 示例：每 5 秒做一次 TCP 端口检查
upstream backend {
    server 192.168.1.10:80 max_fails=3 fail_timeout=30s;
    server 192.168.1.11:80 max_fails=3 fail_timeout=30s;
}
# max_fails=3：连续失败 3 次就标记为不可用
# fail_timeout=30s：标记不可用后，30 秒内不再转发给它
```

**HTTP 健康检查**：向后端发一个 HTTP 请求（通常是 `GET /health`），检查返回状态码和响应体。

```nginx
# 更精确的 HTTP 健康检查（需要 nginx-plus 或第三方模块）
server 192.168.1.10:80;
check interval=3000 rise=2 fall=3 timeout=1000 type=http;
check_http_send "HEAD /health HTTP/1.0\r\n\r\n";
check_http_expect_alive http_2xx http_3xx;
```

### 行为

- 标记不可用 → 流量自动跳过这台服务器
- 恢复健康 → 自动重新加入服务
- 过渡期间不丢流量（其他健康服务器继续处理）

💡 **想多一点：后端挂了，客户端看到什么？**

这取决于健康检查检测到故障的时机。从后端进程崩溃到负载均衡器标记它为不可用，中间有一段"时间窗口"。在这段窗口内：

1. 负载均衡器还没发现后端挂了 → 仍然把请求转发给已经挂掉的服务器
2. 客户端发起 TCP 连接 → 后端进程不存在 → 收到 RST 或超时
3. 如果是正常关闭（后端发送 FIN），但负载均衡器还没感知 → TCP 进入 **CLOSE_WAIT** 状态（回顾 Ch17 四次挥手）

所以健康检查的间隔越短，用户感受到的故障时间越短。但间隔太短会消耗资源——这是一个权衡。生产环境通常设为 3~10 秒。

## 35.6 会话保持（Sticky Session）

**问题**：用户的第一个请求打到了服务器 A，A 在内存里存了用户的登录状态。第二个请求如果被负载均衡器发给服务器 B——B 没有这个用户的登录状态，用户被当成"未登录"。

**解决方案 — 会话保持**：让同一个用户的请求始终打到同一台服务器。

### 实现方式

**方式一：IP Hash（前面讲过的）**——同一个 IP 永远到同一台服务器。缺点是 NAT 下失效（办公室 100 人共享一个公网 IP，全部打到同一台服务器）。

**方式二：Cookie 植入**——负载均衡器在第一次响应时，向用户浏览器写入一个 Cookie（如 `SERVERID=A`）。后续请求带这个 Cookie，负载均衡器读到 `SERVERID=A`，永远转发给 A。

```
第一次请求：
用户 → LB（没有Cookie） → 随便选一台（比如A）
用户 ← A返回数据 + Set-Cookie: SERVERID=A

第二次请求：
用户 → LB（Cookie: SERVERID=A） → 读取Cookie，转发给A
```

**方式三：共享 Session**——用 Redis 或数据库把 Session 存到共享存储，所有服务器都能读。这样不需要会话保持，每台服务器都能处理任何请求。这是**最推荐**的做法，因为它彻底解耦了"请求"和"服务器"的绑定。

## 术语表

| 术语 | 解释 |
|------|------|
| **L4 负载均衡** | 工作在传输层，只看 IP+端口，不解包上层协议 |

| **轮询（Round Robin）** | 按顺序轮流分配请求给后端服务器 |
| **加权轮询** | 给性能强的服务器更高权重，多分配请求 |

| **一致性哈希** | 环形哈希空间，节点增减只影响相邻弧段的请求 |
| **虚拟节点** | 一个物理节点映射为环上多个虚拟点，解决数据倾斜 |
| **健康检查** | 持续探测后端服务器是否存活，挂了自动剔除 |
| **会话保持（Sticky Session）** | 同一用户的请求始终发到同一台服务器 |
