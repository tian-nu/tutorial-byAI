# 19-权限保护：认证中间件

> "第 18 章用户能登录了，能拿到 token 了——但后端还没用这个 token 保护任何接口。任何人都还能随意创建、修改、删除文章，token 形同虚设。这一章创建认证中间件：从请求头提取 JWT，验证签名，把用户信息挂到 `req.user`。然后把这个中间件加到文章的创建、修改、删除接口上——没带 token 的人统统 401。做完之后，你的 API 第一次有了'门禁'——没登录的人只能看文章，不能写。"

## 一、目标与完成效果

**一句话目标**：创建 `middleware/auth.js` 认证中间件，从请求头 `Authorization: Bearer <token>` 提取并验证 JWT，将用户信息挂到 `req.user`，在文章路由中保护写操作接口（POST/PUT/DELETE），将 `author_id` 从写死的 `1` 改为 `req.user.id`。

**完成后的可观测效果**：
- 你创建了 `middleware/auth.js`，导出 `authenticate` 中间件函数。
- 你在 `routes/articles.js` 中引入了 `authenticate`，并加到了 POST、PUT、DELETE 路由上。
- `POST /api/articles` 创建文章时，`author_id` 从 `req.user.id` 获取（不再是写死的 `1`）。
- 不带 token 访问 `POST /api/articles` → 401。
- 带有效 token 访问 → 成功创建，文章归属当前用户。
- 带过期或伪造的 token → 401。
- `GET /api/articles` 仍然不需要 token（公开接口）。

## 三、分步操作

### 步骤 1：认证 vs 授权——先分清两个概念

这是初学者最容易混淆的两个词：

| | 认证（Authentication） | 授权（Authorization） |
|---|---|---|
| **回答的问题** | "你是谁？" | "你能不能干这事？" |
| **类比** | 出示身份证——证明你是张三 | 身份证显示你满 18 岁了吗——能不能买酒 |
| **HTTP 状态码** | 401 Unauthorized（没带身份证） | 403 Forbidden（带了身份证但不够年龄） |
| **英文缩写** | AuthN | AuthZ |
| **本章做的** | ✅ 认证中间件 | ❌ 授权在下一章 |

> **餐厅比喻**：
> - **认证** = 门卫检查你的会员卡，确认你是会员。
> - **授权** = 服务员检查你的会员等级——普通会员不能进 VIP 包厢。

**401 vs 403 的精确区别**：
- `401`：你还没证明你是谁（没带 token，或 token 无效/过期）。
- `403`：你已经证明你是谁了，但你没权限做这件事（比如改别人的文章）。

### 步骤 2：创建 middleware/auth.js——认证中间件

创建 `middleware/auth.js`：

```javascript
const jwt = require('jsonwebtoken');
const AppError = require('../utils/AppError');

/**
 * 认证中间件
 * 从请求头 Authorization: Bearer <token> 中提取 JWT，
 * 验证签名，将用户信息挂到 req.user。
 */
function authenticate(req, res, next) {
    // 1. 从请求头提取 Authorization
    const authHeader = req.headers.authorization;

    // 2. 检查是否存在且格式正确
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
        throw new AppError('未提供认证令牌', 401);
    }

    // 3. 提取 token（"Bearer " 后面 7 个字符之后的部分）
    const token = authHeader.split(' ')[1];

    // 4. 验证 JWT
    try {
        const decoded = jwt.verify(token, process.env.JWT_SECRET);
        // 5. 把解码后的用户信息挂到 req.user
        req.user = decoded;
        next();
    } catch (err) {
        // 区分 token 过期和其他错误
        if (err.name === 'TokenExpiredError') {
            throw new AppError('认证令牌已过期，请重新登录', 401);
        }
        throw new AppError('认证令牌无效', 401);
    }
}

module.exports = { authenticate };
```

**关键点解析**：

| 行 | 做什么 | 为什么 |
|----|--------|--------|
| `authHeader.startsWith('Bearer ')` | 检查格式 | 必须是 `Bearer <token>`，不是 `Basic` 或别的 |
| `authHeader.split(' ')[1]` | 提取 token | `"Bearer eyJ..."` → `["Bearer", "eyJ..."]` → 取第二部分 |
| `jwt.verify(token, secret)` | 验证签名 + 解码 | 如果签名不匹配或 token 过期，抛出异常 |
| `req.user = decoded` | 挂载用户信息 | 后续路由处理函数通过 `req.user` 知道"当前是谁" |
| `err.name === 'TokenExpiredError'` | 区分过期 | 给用户明确的提示——"过期了，请重新登录" |

> 🔥 **魔鬼细节**：`Authorization: Bearer <token>` 中 `Bearer` 后面**必须有一个空格**。`"Bearer" + " " + token`，不是 `"BearereyJ..."`。如果忘了空格，`split(' ')` 只能切出一个元素，`token` 会是 `undefined`，后续 `jwt.verify()` 报错。

> 🔥 **魔鬼细节**：中间件中 `next()` 后面要 `return`，否则代码可能继续执行（虽然本中间件中 `next()` 是最后一行，但养成习惯：`return next()` 或 `next(); return;`）。

> 🔥 **魔鬼细节**：`jwt.verify()` 签名验证失败时抛出 `JsonWebTokenError`，过期时抛出 `TokenExpiredError`。我们区分这两种情况，给用户不同的提示。

### 步骤 3：在文章路由中使用认证中间件

打开 `routes/articles.js`，引入 `authenticate` 中间件，加到需要保护的接口上：

```javascript
const { authenticate } = require('../middleware/auth');   // ← 新增

// GET /api/articles — 公开（不需要登录）
router.get('/', (req, res) => { ... });

// GET /api/articles/:id — 公开（不需要登录）
router.get('/:id', (req, res) => { ... });

// POST /api/articles — 需要登录
router.post('/', authenticate, (req, res) => {
    const { title, content } = req.body;

    if (!title || !content) {
        throw new AppError('标题和内容为必填字段', 400);
    }

    // ✅ 从 JWT 中获取当前用户 ID，而不是写死为 1
    const author_id = req.user.userId;

    const now = new Date().toISOString();

    const insertArticle = db.prepare(`
        INSERT INTO articles (title, content, author_id, created_at, updated_at)
        VALUES (?, ?, ?, ?, ?)
    `);

    const result = insertArticle.run(title, content, author_id, now, now);

    const newArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `).get(result.lastInsertRowid);

    res.status(201).json({
        success: true,
        data: newArticle
    });
});

// PUT /api/articles/:id — 需要登录
router.put('/:id', authenticate, (req, res) => {
    // ... 更新逻辑不变，但下一章会加入归属检查 ...
});

// DELETE /api/articles/:id — 需要登录
router.delete('/:id', authenticate, (req, res) => {
    // ... 删除逻辑不变，但下一章会加入归属检查 ...
});
```

**变更总结**：

| 接口 | 之前 | 现在 |
|------|------|------|
| `GET /api/articles` | 公开 | 公开（不变） |
| `GET /api/articles/:id` | 公开 | 公开（不变） |
| `POST /api/articles` | 公开，`author_id = 1` | **需要登录**，`author_id = req.user.userId` |
| `PUT /api/articles/:id` | 公开 | **需要登录** |
| `DELETE /api/articles/:id` | 公开 | **需要登录** |

> 🔥 **魔鬼细节**：`authenticate` 中间件放在路由处理函数之前——`router.post('/', authenticate, (req, res) => {...})`。Express 按顺序执行中间件：先 `authenticate` 验证 token，通过了才执行路由处理函数。如果 `authenticate` 抛错，路由处理函数根本不会执行。

### 🤔 想多一点：`req.user` 里有什么？

`req.user` 是 `jwt.verify()` 解码后的 Payload 对象。回顾第 18 章签发 JWT 时我们放入 Payload 的内容：

```javascript
jwt.sign(
    { userId: user.id, username: user.username },  // ← 这就是 Payload
    process.env.JWT_SECRET,
    { expiresIn: '7d' }
);
```

所以 `req.user` 的内容是：

```json
{
  "userId": 3,
  "username": "testuser",
  "iat": 1718200000,
  "exp": 1718804800
}
```

- `req.user.userId` — 当前用户的 ID
- `req.user.username` — 当前用户的用户名
- `req.user.iat` — token 签发时间（Issued At）
- `req.user.exp` — token 过期时间（Expiration）

### ❌ 常见错误 → ✅ 解决方案

| 错误信息 / 现象 | 原因 | 解决 |
|-----------------|------|------|
| `Cannot find module '../middleware/auth'` | `middleware/auth.js` 没创建 | 创建 `middleware/auth.js` 并写入代码 |
| 带 token 也返回 401 "未提供认证令牌" | Headers 中 `Authorization` 拼写错误，或格式不对 | 确认 Header 名为 `Authorization`，值为 `Bearer <token>`（注意空格） |
| `jwt expired` / "认证令牌已过期" | token 的 `exp` 时间已过 | 重新登录获取新 token |
| `invalid signature` | token 被篡改，或用了不同的 `JWT_SECRET` 验证 | 确认签发和验证用的是同一个 `JWT_SECRET` |
| `jwt malformed` | token 格式错误——少了 `Bearer ` 前缀，或 token 被截断 | 确认 Header 值是 `Bearer eyJ...`（一个空格分隔） |
| 创建文章时 `author_id` 是 `undefined` | `req.user` 中没有 `userId` 字段 | 确认 `jwt.sign()` 的 Payload 中有 `userId`，且中间件中 `req.user = decoded` |
| `POST /api/articles` 返回 500，`FOREIGN KEY constraint failed` | `author_id` 对应的用户不存在（如 `req.user.userId` 指向已删除的用户） | 确认登录用户确实存在于 `users` 表中 |
| 中间件 `throw` 了但返回的不是 JSON | `express-async-errors` 没配置 | 确认 `server.js` 顶部有 `require('express-async-errors')` |

### `blog-backend/routes/articles.js`（本章变更：引入 authenticate，保护写操作）

```javascript
const express = require('express');
const router = express.Router();
const { db } = require('../database/db');
const AppError = require('../utils/AppError');
const { authenticate } = require('../middleware/auth');   // ← 新增

// ========== 文章 CRUD 接口（数据库版） ==========

// GET /api/articles — 获取所有文章（公开）
router.get('/', (req, res) => {
    const page = parseInt(req.query.page) || 1;
    const limit = parseInt(req.query.limit) || 10;
    const offset = (page - 1) * limit;

    const selectArticles = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        ORDER BY articles.created_at DESC
        LIMIT ? OFFSET ?
    `);

    const articles = selectArticles.all(limit, offset);

    const { total } = db.prepare('SELECT COUNT(*) AS total FROM articles').get();

    res.json({
        success: true,
        data: {
            page: page,
            limit: limit,
            total: total,
            articles: articles
        }
    });
});

// GET /api/articles/:id — 获取单篇文章（公开）
router.get('/:id', (req, res) => {
    const { id } = req.params;

    const selectArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `);

    const article = selectArticle.get(id);

    if (!article) {
        throw new AppError('文章不存在', 404);
    }

    res.json({
        success: true,
        data: article
    });
});

// POST /api/articles — 创建文章（需要登录）
router.post('/', authenticate, (req, res) => {
    const { title, content } = req.body;

    if (!title || !content) {
        throw new AppError('标题和内容为必填字段', 400);
    }

    const author_id = req.user.userId;   // ← 从 JWT 获取，不再是写死的 1

    const now = new Date().toISOString();

    const insertArticle = db.prepare(`
        INSERT INTO articles (title, content, author_id, created_at, updated_at)
        VALUES (?, ?, ?, ?, ?)
    `);

    const result = insertArticle.run(title, content, author_id, now, now);

    const newArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `).get(result.lastInsertRowid);

    res.status(201).json({
        success: true,
        data: newArticle
    });
});

// PUT /api/articles/:id — 更新文章（需要登录）
router.put('/:id', authenticate, (req, res) => {
    const { id } = req.params;
    const { title, content } = req.body;

    if (!title || !content) {
        throw new AppError('标题和内容为必填字段', 400);
    }

    const now = new Date().toISOString();

    const updateArticle = db.prepare(`
        UPDATE articles 
        SET title = ?, content = ?, updated_at = ?
        WHERE id = ?
    `);

    const result = updateArticle.run(title, content, now, id);

    if (result.changes === 0) {
        throw new AppError('文章不存在', 404);
    }

    const updatedArticle = db.prepare(`
        SELECT 
            articles.id,
            articles.title,
            articles.content,
            articles.author_id,
            articles.created_at,
            articles.updated_at,
            users.username AS author
        FROM articles
        INNER JOIN users ON articles.author_id = users.id
        WHERE articles.id = ?
    `).get(id);

    res.json({
        success: true,
        data: updatedArticle
    });
});

// DELETE /api/articles/:id — 删除文章（需要登录）
router.delete('/:id', authenticate, (req, res) => {
    const { id } = req.params;

    const deleteArticle = db.prepare('DELETE FROM articles WHERE id = ?');
    const result = deleteArticle.run(id);

    if (result.changes === 0) {
        throw new AppError('文章不存在', 404);
    }

    res.status(204).send();
});

module.exports = router;
```

## 六、小结表格

| 学到的东西 | 一句话解释 |
|-----------|-----------|
| 认证（Authentication） | "你是谁"——出示身份证，对应 401 |
| 授权（Authorization） | "你能不能干这事"——身份证显示年龄，对应 403 |
| 401 vs 403 | 401 = 没带身份证（没登录），403 = 带了身份证但不够年龄（没权限） |
| `Authorization: Bearer <token>` | HTTP 请求头的标准格式，携带 JWT 令牌 |
| `jwt.verify(token, secret)` | 验证签名 + 解码 Payload，失败抛异常 |
| `req.user` | 认证中间件挂载的当前用户信息，后续路由通过它获取用户 ID |
| 中间件顺序 | `router.post('/', authenticate, handler)` —— 先认证，再处理 |
| `TokenExpiredError` vs `JsonWebTokenError` | 前者是过期，后者是签名无效——区分后给不同提示 |

| 术语 | 英文 | 通俗解释 | 本章出现位置 | 字面陷阱 |
|------|------|----------|-------------|----------|
| 认证 | Authentication (AuthN) | "你是谁？"——验证用户身份。通常通过用户名/密码、JWT、OAuth 等方式完成。 | 步骤 1 | 不是"认证"= 确认证书——是"验证身份"，确认你就是你声称的那个人 |

| 403 Forbidden | — | HTTP 状态码，表示"已认证但无权限"——你知道是谁，但你不允许做这件事。 | 步骤 1 | 不是"禁止"= 这个操作被禁止了——是"对你禁止"，别人可能可以做 |

## 八、已知坑点与禁止事项

1. **`Authorization: Bearer <token>` 格式**：`Bearer` 后面必须有一个空格。`"Bearer" + " " + token`，不是 `"BearereyJ..."`。

2. **先检查认证（401），再检查权限（403）**：顺序不能乱。如果用户没登录，直接返回 401，不要先查权限再返回 401。

3. **`req.user` 是自定义属性**：Express 没有内置的 `req.user`。是我们通过 `req.user = decoded` 挂上去的。

4. **`author_id` 从 `req.user.userId` 获取**：不再写死为 `1`。`req.user.userId` 来自 JWT 的 Payload，而 JWT 是登录时签发的，所以创建的文章会自动归属到当前登录用户。

5. **中间件中 `throw` 依赖 `express-async-errors`**：如果 `authenticate` 中 `throw` 了但返回的是 HTML 错误页面而不是 JSON，说明 `express-async-errors` 没配置。确认 `server.js` 顶部有 `require('express-async-errors')`。

6. **`jwt.verify()` 的异常类型**：`TokenExpiredError`（过期）和 `JsonWebTokenError`（签名无效/格式错误）是不同的错误类型。区分处理可以给用户更精确的提示。

## 九、下一步建议

认证中间件已经就位。未登录的用户被挡在门外，登录的用户能创建文章——但还有一个问题：**用户 A 登录后可以修改用户 B 的文章**。因为我们的 PUT 和 DELETE 接口只检查了"是否登录"，没检查"文章是不是你的"。下一章解决这个问题：

- **下一章**：[20-文章归属：只能改自己的文章](20-文章归属：只能改自己的文章.md) —— 在更新和删除文章前检查 `article.author_id === req.user.userId`，不是自己的文章返回 403 Forbidden。同时改造 GET 接口，让前端能区分"这篇文章是谁写的"。
- **延伸思考**：中间件可以进一步扩展——比如创建 `authorize` 中间件，检查用户角色（admin/user）。或者创建一个"可选认证"中间件：登录了挂 `req.user`，没登录也放行（`req.user` 为 `null`），用于"登录后能看到更多内容"的场景。
