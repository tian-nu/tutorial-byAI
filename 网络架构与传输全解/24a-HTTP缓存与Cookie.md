# 24a — HTTP 缓存与 Cookie

## 学习目标
- 掌握浏览器 HTTP 缓存的两级策略：强缓存 + 协商缓存
- 理解 Cookie 的工作原理和各个安全属性的作用
- 能区分 Session、Token、JWT 的适用场景
- 会在浏览器 DevTools 中查看缓存相关头

---

## 24a.1 为什么需要缓存？

你打开淘宝首页，页面里有几十张图片、几百KB的CSS和JS。如果每次刷新都要从服务器重新拉一遍这些一模一样的资源，不仅你加载慢，服务器也扛不住——白白浪费带宽和时间。

**HTTP 缓存**就是浏览器帮你把已经下载过的资源存在本地（硬盘或内存），下次再需要的时候直接用本地的，不用再去服务器要。这是 Web 世界最经典的性能优化手段。

💡 **想多一点**：缓存是性能优化的"银弹"——做好缓存，首页加载速度从 3 秒降到 300 毫秒都是常事。大部分静态资源（图片、CSS、JS）根本没必要每次都从服务器拉。

---

## 24a.2 两级缓存：强缓存 → 协商缓存

浏览器查找缓存的顺序是：**先看强缓存有没有效，有效就直接用（不请求服务器）；无效再发请求给服务器，走协商缓存问问"我本地这份还能用吗"**。

### 24a.2.1 强缓存：直接用本地的，不麻烦服务器

强缓存靠响应头 `Cache-Control` 控制，最常用的配置就是 `max-age=N`，单位是秒，表示"这份资源 N 秒内不用问服务器，直接用本地的"。

```http
# 响应头示例：静态资源一年不变化
Cache-Control: public, max-age=31536000
```

`public` 表示这份资源可以被 CDN 缓存，`max-age=31536000` 就是一年。如果你一年内再次访问这个资源，浏览器直接用本地缓存，**根本不发请求到服务器**。

❌ **常见错误理解**：
- 以为 `max-age` 是从你第一次访问开始算，过期了就一定重新请求 → 对，就是这样，没毛病。但很多人搞混了和协商缓存的关系。
- 以为每次按 F5 刷新都会跳过强缓存 → 其实普通刷新（F5）会让 `max-age` 过期（设为 0），走协商缓存；只有**强制刷新**（Ctrl+F5 / Cmd+Shift+R）才会完全跳过缓存重新下载。

✅ **正确操作流程**：

| 操作 | 强缓存 | 协商缓存 |
|------|--------|----------|
| 地址栏回车 / 链接跳转 | 遵循 `max-age` | 强缓存有效就不碰 |
| F5 刷新 | `max-age` 视为过期 | 一定会发请求协商 |
| Ctrl+F5 强制刷新 | 直接跳过 | 直接跳过，完全重下 |

### 强缓存相关字段速查

| 字段 | 含义 |
|------|------|
| `Cache-Control: no-cache` | **不是不缓存**！意思是"缓存可以存，但每次用之前必须问服务器" → 强制走协商缓存 |
| `Cache-Control: no-store` | 真·不缓存，根本不让浏览器存这份资源 |
| `Cache-Control: private` | 只能浏览器存，不能被 CDN 缓存（比如你个人的页面） |
| `Cache-Control: public` | CDN 也可以缓存这份资源 |
| `Expires` | HTTP/1.0 时代的写法，用绝对时间，现在基本被 `max-age` 取代 |

## 24a.2.2 协商缓存：我问问服务器，没变就继续用

强缓存过期了，浏览器就会发一个请求给服务器，问问"我本地这份缓存还能用吗？"。这就是**协商缓存**。

协商缓存有两种实现：`ETag + If-None-Match` 和 `Last-Modified + If-Modified-Since`。现在网站基本都用第一种。

### ETag + If-None-Match（推荐）

- 服务器返回资源的时候，顺便给一个 `ETag` 响应头，值是资源内容的哈希（比如 `ETag: "abc123"`）
- 浏览器缓存这个 ETag
- 下次强缓存过期，需要协商时，浏览器把 ETag 放到请求头 `If-None-Match` 发给服务器
- 服务器对比 ETag：如果内容没变，返回 **304 Not Modified**，告诉浏览器"没变，继续用你本地的"；如果变了，返回 200 和新内容

```http
# 第一次响应
HTTP/1.1 200 OK
Content-Type: image/jpeg
ETag: "a1b2c3"
Cache-Control: max-age=3600

# 一个小时后，强缓存过期，协商请求
GET /logo.jpg HTTP/1.1
If-None-Match: "a1b2c3"

# 服务器发现内容没变 → 返回 304
HTTP/1.1 304 Not Modified
ETag: "a1b2c3"
```

304 响应**没有 body**，只有头，体积很小，所以比重新传整个资源快很多。

### Last-Modified + If-Modified-Since（传统方案）

思路类似，只不过用"最后修改时间"代替哈希：

- 服务器返回 `Last-Modified: Fri, 07 Jun 2026 10:00:00 GMT`
- 下次协商时放在 `If-Modified-Since` 请求头里发给服务器
- 服务器对比修改时间，没变就返回 304

这个方案有个问题：文件改了内容，但修改时间没变（比如把文件改回去了），或者修改时间精度只有秒，一秒内改多次识别不出来。所以 ETag 更准确。

💡 **想多一点**：两种协商缓存可以一起用，浏览器会都发过去，服务器优先看 ETag。

## 24a.2.3 完整缓存流程图

```
用户发起请求
    ↓
浏览器：本地有没有缓存？
    ↓
    有 → 强缓存过期了吗？（Cache-Control: max-age）
          ↓
          没过期 → 直接读缓存，返回 200 (from disk/memory cache)
          ↓ 过期
          发请求给服务器，带上 If-None-Match（ETag）和 If-Modified-Since
                        ↓
                服务器：内容变了吗？
                        ↓
                        没变 → 返回 304 Not Modified，浏览器用缓存
                        ↓ 变了
                        返回 200 OK 和新内容，浏览器更新缓存
    ↓
    没有 → 直接请求服务器，返回内容，浏览器缓存下来
```

## 24a.3 实战：在 DevTools 看缓存

### Windows / Linux / macOS 操作都一样：

1. 打开 Chrome / Edge，按 F12 打开开发者工具
2. 切换到 **Network** 面板
3. 刷新页面，点击你想看的资源
4. 在 **Headers** 标签里看 `Cache-Control`、`ETag`、`If-None-Match` 这些头
5. 看 `Status` 列：
   - `200 OK (from disk cache)` → 强缓存命中，读磁盘
   - `200 OK (from memory cache)` → 强缓存命中，读内存
   - `304 Not Modified` → 协商缓存命中

内存缓存比磁盘缓存更快，但关掉页面就没了；磁盘缓存关了浏览器还在。

## 24a.4 Cookie：浏览器记住"你是谁"

HTTP 协议本身是**无状态**的——你第一次登录成功，第二次请求服务器，服务器根本不知道是你。怎么办？需要一个机制让服务器能记住客户端，这就是 **Cookie**。

简单说：Cookie 是浏览器帮服务器**存储在本地的一小块数据**，每次请求这个网站，浏览器都会自动把对应的 Cookie 放到请求头里带给服务器。

### 工作流程

```
1. 你第一次登录淘宝，输入用户名密码
2. 服务器验证通过，返回响应，在响应头里放 Set-Cookie
   Set-Cookie: sessionId=abc123xyz; Path=/; Domain=.taobao.com; HttpOnly
3. 浏览器看到 Set-Cookie，就把这个 sessionId 存在你本地
4. 你再刷新页面，或者点进商品详情，浏览器自动在请求头加：
   Cookie: sessionId=abc123xyz
5. 服务器拿到 sessionId，查数据库，就知道"哦，是这个用户"
```

就是这么简单。一句话：**服务器说"存这个"→浏览器存→下次自动带过去**。

## 24a.5 Cookie 的重要属性

Set-Cookie 可以跟很多属性，这些属性控制 Cookie 的作用范围和安全性，个个都很重要。

| 属性 | 作用 | 安全意义 |
|------|------|----------|
| `Domain=xxx.com` | 这个 Cookie 在哪些域名下有效 | 控制范围，不泄露给其他域名 |
| `Path=/` | 这个 Cookie 在哪些路径下有效，`/` 就是整个网站 | - |
| `Expires=日期` / `Max-Age=N秒` | Cookie 过期时间，过期了浏览器自动删除 | 避免长期留存敏感信息 |
| `HttpOnly` | 禁止 JavaScript 通过 `document.cookie` 读取这个 Cookie | **防 XSS 攻击**——就算网站被注入了JS，黑客也拿不到你的登录 Cookie |
| `Secure` | 只有 HTTPS 请求才会带上这个 Cookie | 防明文传输中被窃听 |
| `SameSite` | 控制跨站请求时是否带 Cookie | **防 CSRF 攻击**——第三方网站不能冒用你的登录态 |

❌ **常见错误**：
- 登录态的 Cookie 不加 `HttpOnly` → XSS 直接偷走你的 Session，账号被盗
- HTTPS 网站的登录 Cookie 不加 `Secure` → 如果有 HTTP 资源请求，可能被泄露

✅ **最佳实践**：用户登录相关的 Cookie，一定要同时开 `HttpOnly` + `Secure` + `SameSite`。

## 24a.6 Session vs Token vs JWT：一张对比表

服务器拿到 Cookie 里的 sessionId，怎么存用户信息？这就是 Session 和 Token 的区别。

| 对比维度 | Session | Token（一般指无状态 Token） | JWT |
|----------|---------|-----------------------------|-----|
| 存储位置 | Session 存在服务器数据库/内存里，客户端只存 ID | Token 本身就包含用户信息（加密或签名），服务器不用存 | JWT 是 Token 的一种标准格式 |
| 服务器存储 | 需要存 | 不需要存 | 不需要存 |
| 扩展性 | 多台服务器需要共享 Session（Redis） | 天生分布式，随便哪台服务器都能验 | 同 Token |
| 安全性 | sessionId 不加密，必须 HTTPS | Token 可以签名防篡改，也可以加密 | 签名防篡改，但**不加密**（payload 是 base64 编码，任何人都能解码），不要放敏感数据 |
| 大小 | Cookie 只存 ID，很小 | Token 越长越大，每次请求都带，占用带宽 | 一般几百字符 |
| 适用场景 | 传统服务端渲染网站（SSR） | 前后端分离、移动API | RESTful API、微服务 |

JWT 的全称是 **JSON Web Token**，它把用户信息（claims）用 JSON 存，然后签名，结构是 `头部.载荷.签名`，任何人都能解码看内容，但签名能保证没人改过。记住：**JWT 不加密，别塞密码进去**。

## 24a.7 小结

| 概念 | 要点 |
|------|------|
| **强缓存** | `Cache-Control: max-age`，有效期内不发请求，直接用本地 |
| **协商缓存** | 强缓存过期后，服务器问 304 还是 200，ETag 比 Last-Modified 准确 |
| **304 Not Modified** | 协商缓存命中，服务器告诉浏览器"继续用本地缓存"，无响应体 |
| **Cookie** | 浏览器存服务器给的小块数据，每次请求自动带上，用于保持登录态 |
| **HttpOnly** | 禁止JS读取，防XSS偷Cookie |
| **SameSite** | 防跨站请求，防CSRF |
| **Session** | 服务器存用户数据，客户端只存ID |
| **JWT** | 无状态Token标准，本身带数据，服务器不存，payload不加密 |

## 术语表

| 术语 | 解释 |
|------|------|
| **HTTP缓存** | 浏览器将已下载资源存储本地，重复访问时直接复用，提升性能减少带宽 |
| **强缓存**（此术语需进附录） | 第一级缓存，`max-age` 未过期时直接用本地，不发请求到服务器 |
| **协商缓存**（此术语需进附录） | 强缓存过期后，向服务器确认资源是否变更，没变返回304 |
| **ETag**（此术语需进附录） | 服务器给资源内容的哈希标识，用于协商缓存判断内容是否变化 |
| **304 Not Modified** | 协商缓存命中时服务器返回的状态码，告诉浏览器用本地缓存 |
| **Cookie**（此术语需进附录） | 浏览器存储服务器下发的小数据，每次请求自动携带，维持状态 |
| **HttpOnly**（此术语需进附录） | Cookie属性，禁止JavaScript读取，防止XSS攻击窃取 |
| **SameSite**（此术语需进附录） | Cookie属性，限制跨站请求携带，防止CSRF攻击 |
| **Session** | 服务端存储用户会话数据，客户端只保存会话ID |
| **JWT (JSON Web Token)** | 无状态Token的标准格式，自包含用户信息，数字签名防篡改 |

## 验证方法

1. 打开任意网站，按 F12 → Network → 刷新，找一个静态资源（比如图片）：
   - 看 `Status` 是不是 `200 (from disk cache)` 或 `304`
   - 看 Response Headers 里有没有 `Cache-Control` 和 `ETag`

2. 找一个你登录过的网站，看看登录 Cookie：
   - Application 标签 → Storage → Cookies → 看有没有 `HttpOnly` 打勾
   - 检查登录 Cookie 有没有 `Secure` 属性

如果你能找到这些头，说明你理解了本章内容。

---

## 最可能出错的地方及原因

1. **混淆 `Cache-Control: no-cache` 和 `no-store`**：`no-cache` 不是不缓存，是每次用之前必须协商；`no-store` 才是真不缓存。很多文档写错了，容易记混。

2. **登录 Cookie 忘记加 `HttpOnly`**：前端开发者经常图方便用 JS 读 Cookie，其实没必要，而且会打开XSS漏洞。

3. **强制刷新和普通刷新分不清**：开发调试缓存时，普通刷新F5会走协商缓存，不是完全重下，以为缓存没生效其实是操作错了。
