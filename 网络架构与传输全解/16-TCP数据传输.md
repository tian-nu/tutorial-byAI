## 16.1 数据切成小块：MSS 是什么？

TCP 不直接发送应用程序给的"一大坨"数据，而是切成一个个小段（Segment），每个段的大小不超过 **MSS（Maximum Segment Size，最大报文段长度）**。

MSS 的计算公式：

```
MSS = MTU - IP头部 - TCP头部
    = 1500 - 20 - 20
    = 1460 字节
```

- **MTU**（Maximum Transmission Unit）：链路层能传输的最大数据单元，以太网的典型值是 **1500 字节**
- **IP 头部**：标准 20 字节
- **TCP 头部**：标准 20 字节

所以以太网环境中的典型 MSS 是 **1460 字节**。这意味着如果你的应用调用 `send(5000字节)`，TCP 会把 5000 字节切成 4 段发出去（1460 + 1460 + 1460 + 620）。

❌ **常见错误**：以为 TCP 按 `send()` 的调用次数分包。事实是 TCP 是**字节流协议**——你调三次 `send("A")`，对方可能一次 `recv()` 就全收到，也可能分两次收到。TCP 不保留消息边界。

✅ **正确理解**：TCP 只保证字节按顺序到达，不保证"你发几次，对面就收几次"。如果你需要消息边界，必须在应用层自己实现（比如每行加换行符，或者加长度前缀）。

## 16.2 确认应答（ACK）：每一笔账都要回执

TCP 实现可靠传输的第一个机制是**确认应答**（Positive Acknowledgment）。规则很简单：

> 接收方每收到一批数据，就回复一个 ACK，告诉发送方"我已经收到了第 N 个字节，期望下一个是第 N+1 个"。

用一个具体例子：

```
假设 ISN（初始序列号）= 1000，MSS = 100 字节（简化）

发送方                                  接收方
  |                                       |
  |--- seq=1000, 数据(100字节) ---------->|  收到字节 1000~1099
  |                                       |
  |<---- ack=1100 -----------------------|  "下次从 1100 开始发"
  |                                       |
  |--- seq=1100, 数据(100字节) ---------->|  收到字节 1100~1199
  |                                       |
  |<---- ack=1200 -----------------------|  "下次从 1200 开始发"
  |                                       |
  |--- seq=1200, 数据(100字节) ---------->|  收到字节 1200~1299
  |                                       |
  |<---- ack=1300 -----------------------|  "下次从 1300 开始发"
```

注意：ACK 报文中的 `ack` 字段值是 **"已连续收到的最大字节序号 + 1"**，不是"我刚收到的这一段的最后字节"。比如收到 1100~1199 后，ack=1200。

> 💡 **想多一点**：TCP 把"数据编号"和"确认编号"分开成两个独立字段（seq 和 ack），这让全双工通信成为可能。你的数据用你的 seq 编号，你对对方数据的确认用 ack 字段。换句话说，**一个 TCP 报文可以同时携带数据（seq 增长）和确认（ack 更新）**，效率极高。

## 16.3 超时重传（RTO）：对方不回？再发一遍

如果发送方发出数据后，在一定时间内没有收到对应的 ACK，就认为数据丢失了，重新发送。这个等待时间叫 **RTO（Retransmission Timeout，重传超时）**。

RTO 不是拍脑袋定的固定值。它基于 **RTT（Round-Trip Time，往返时间）** 动态计算。RTT 就是从发出数据到收到 ACK 所花的时间：

```
RTT = 收到ACK的时刻 - 发出数据的时刻
```

用具体数字说明：

```
发送方发出 seq=1000，系统时间 0ms
接收方收到，回复 ack=1100
发送方收到 ack=1100，系统时间 50ms

→ RTT = 50ms

如果下次发出 seq=1100 后，等了 200ms 还没收到 ACK：
→ 触发超时重传！
```

TCP 使用 **Jacobson/Karels 算法** 来平滑估算 RTT 和 RTO：

```
SRTT(平滑RTT) = (1 - α) × SRTT + α × 最新RTT    (α 通常 1/8)
RTTVAR(偏差)  = (1 - β) × RTTVAR + β × |SRTT - 最新RTT|  (β 通常 1/4)
RTO = SRTT + 4 × RTTVAR
```

这个算法让 RTO 在稳定网络中很短（几毫秒到几十毫秒），在抖动大的网络中自动放宽。

❌ **常见错误**：认为超时重传一定是数据丢了。实际上，ACK 本身也可能丢失或延迟到达——发送方只是"太久没收到 ACK"就重传，它无法区分是数据丢了还是 ACK 丢了。

✅ **正确理解**：超时重传是 TCP 的安全网，但不是唯一手段。第 18 章会讲到**快速重传**（收到 3 个重复 ACK 就提前重传，不等超时），效率高得多。

## 16.4 滑动窗口：不等 ACK，批量发送（核心难点）

### 为什么不等 ACK 再发下一段？

如果发一段等一个 ACK，再发下一段，网络带宽就浪费了。比如 RTT = 100ms，MSS = 1460 字节，这种方式的最大吞吐量只有：

```
1460 字节 / 0.1 秒 = 14.6 KB/s ≈ 117 Kbps
```

这太可怜了。100Mbps 的光纤只能跑 0.1%，剩下的 99.9% 时间都在等 ACK。

**滑动窗口**就是解决这个问题的：允许发送方在没收到 ACK 的情况下连续发送多段数据，只要"在路上"的数据总量不超过窗口大小。

### 窗口是什么？

窗口大小（Window Size）由**接收方**通过 TCP 头部的窗口字段通告给发送方，表示"我的接收缓冲区还能装多少字节"。这个窗口叫 **rwnd（receiver window，接收窗口）**。

用 ASCII 图来看滑动窗口是怎么工作的。

假设窗口大小 = 4000 字节，MSS = 1000 字节（简化）。发送方有一大段数据（字节 1~9999）要发。

```
初始状态：窗口覆盖 1~4000
        已发送并确认        可发送（窗口内）        还不能发（窗口外）
    |<--- 无 --->|<------- 4000 字节 ------->|<-----------------|
    [1...................................................9999]
                 ^                           ^
              窗口左沿                      窗口右沿

发送 4 段（seq 1, 1001, 2001, 3001），每段 1000 字节：
        已发送未确认      可发送（窗口内剩余0）   还不能发（窗口外）
    |<--- 4000 --->|<------- 0 ------->|<-----------------|
    [■■■■■■■■■■■■■■■....................9999]    ← 窗口满了！不能再发
     ^                           ^
   已发                        窗口右沿

收到 ack=1001（确认了第1段）：
        已确认     已发送未确认   可发送          还不能发
    |<1000>|<-- 3000 -->|<1000>|<-----------------|
    [✓✓✓✓|■■■■■■■■■■■■■■■|░░░░|...................]
    1~1000                   ↑               ↑
                          窗口右沿右移     原右沿
                          → 窗口"滑动"了！
```

窗口的关键特性：
1. **左沿右移**：收到 ACK 时，窗口左沿右移，意味着"之前发的数据被确认了，窗口腾出空间"
2. **右沿右移**：接收方通告更大的窗口时，右沿右移
3. **窗口收缩**：接收方缓冲区紧张时，窗口变小，右沿左移
4. **窗口关闭**：左沿追上右沿（窗口 = 0），发送方必须暂停

### 吞吐量计算

有了滑动窗口，吞吐量的计算公式是：

```
最大吞吐量 = 窗口大小 / RTT

比如：窗口 = 65535 字节，RTT = 100ms
最大吞吐量 = 65535 / 0.1 = 655350 字节/秒 ≈ 5.2 Mbps
```

这也解释了为什么现代 TCP 的窗口缩放（Window Scaling）选项非常重要——65535 字节的窗口在 100ms RTT 下只能跑 5Mbps，对于千兆网络远远不够。启用窗口缩放后，窗口可达 **1GB**，消除了这个瓶颈。

## 16.5 糊涂窗口综合征：小数据、大开销

如果接收方每次只从缓冲区取走很少的数据（比如 1 字节），然后通告窗口为 1，发送方就发 1 字节的数据——TCP 头部 20 字节 + IP 头部 20 字节，总共 41 字节的头部开销只为传 1 字节数据，效率极低。这就叫**糊涂窗口综合征（Silly Window Syndrome）**。

解决方案分两端：

- **接收方**：不通告很小的窗口。当窗口小于某个阈值（通常是 MSS 或缓冲区的一半），直接通告窗口为 0，等缓冲区攒够了再通告。
- **发送方**：不发送很小的报文段。当可以发送的数据小于 MSS 时，延迟发送（Nagle 算法），等数据攒够 MSS 再发。

## 16.7 小结

| 概念 | 要点 |
|------|------|
| MSS | = MTU - IP头 - TCP头，以太网典型值 1460 字节 |
| 确认应答（ACK） | 接收方回复 ack = 已连续收到的最大字节序号 + 1 |
| 超时重传（RTO） | 超时未收到 ACK 就重发；RTO 基于 RTT 用 Jacobson/Karels 算法动态计算 |
| 滑动窗口 | 允许发送方不等 ACK 连续发送多段数据，窗口大小由接收方通告（rwnd） |
| 吞吐量 | = 窗口大小 / RTT |
| 糊涂窗口综合征 | 接收方通告极小窗口导致大量小包传输，由接收方和发送方策略共同防止 |

## 术语表

| 术语 | 解释 |
|------|------|
| **MSS（Maximum Segment Size）** | TCP 层能发送的最大数据载荷，= MTU - IP 头 - TCP 头，以太网典型值 1460 字节 |
| **MTU（Maximum Transmission Unit）** | 链路层最大传输单元，以太网 1500 字节 |
| **确认应答（ACK）** | TCP 可靠性机制：接收方每收到数据就回复确认号，告知已收到的字节范围 |
| **超时重传（RTO, Retransmission Timeout）** | 发出数据后超过 RTO 未收到 ACK 就重发；RTO 基于 RTT 动态计算 |
| **RTT（Round-Trip Time）** | 一个报文从发出到收到对应 ACK 所花的时间 |
| **滑动窗口（Sliding Window）** | 发送方维护的"可发送数据范围"，随 ACK 到来而右移 |
| **rwnd（Receiver Window）** | 接收方通告的窗口大小，反映其接收缓冲区剩余空间 |
| **糊涂窗口综合征（Silly Window Syndrome）** | 接收方通告极小窗口导致大量微小报文，效率极低 |
| **Nagle 算法** | 发送方避免小包的策略：当有未确认数据时，攒够 MSS 或收到所有 ACK 后再发 |
