# 34 — CDN：让内容离用户更近

## 学习目标

- 理解没有 CDN 时互联网内容分发的三大痛点

- 能画出 CDN 完整工作流程（DNS → GSLB → 边缘节点 → 回源）
- 理解 GSLB 如何通过 DNS 判断"最近节点"
- 知道 CDN 不止加速，还有 DDoS 防护、WAF、HTTPS 加速

---

前几章你学会了抓包（Ch28-31）、排查网络故障（Ch32）、分析性能瓶颈（Ch33）。你会发现一个问题：哪怕你服务器端优化到了极致，只要你的用户在北京而服务器在广州，物理距离带来的延迟（RTT，Ch33 已讲）永远存在。光速是不变的——北京到广州直线距离约 2000km，光在光纤中走一个来回至少 20ms，算上路由器跳数，40ms 起步。

怎么办？结论很直白：**如果距离是问题，就消灭距离——把内容搬到用户家门口。**

这就是 CDN 的核心理念。

## 34.1 没有 CDN 的世界：三个痛点

假设你的网站服务器设在深圳：

### 痛点 1：远处慢

- 深圳用户访问：RTT ≈ 10ms，爽
- 哈尔滨用户访问：RTT ≈ 60ms，每个资源都要走这个 RTT（回顾 Ch33 的耗时拆解：DNS + TCP + TLS + TTFB + 下载，每一步都受 RTT 影响）
- 纽约用户访问：RTT ≈ 250ms，开个网页要 3 秒以上

### 痛点 2：源站压力大

所有用户都直连你那台服务器。双十一、大促、热点事件——流量暴涨，服务器直接扛不住。加机器能缓解，但不能从根本上改变"所有流量汇聚一点"的局面。

### 痛点 3：单点故障

源站一挂，全站不可用。即使做多机房，切换也有延迟，更别提机房级故障（光纤被挖断、电力故障）。

## 34.2 CDN 核心原理：缓存到边缘节点

**CDN**（Content Delivery Network，内容分发网络）就是把你的网站内容（HTML、CSS、JS、图片、视频）提前缓存到分布在全球各地的服务器上。这些服务器称为**边缘节点**（Edge Node）。

**比喻**：你在深圳开了一家书店（源站），每次读者来买书都要跑到深圳。有了 CDN，就相当于在全国各地开了分店（边缘节点），每个分店存了最畅销的书。读者就近取书，既快又不用跑深圳。

```
没有 CDN：                        有 CDN：
哈尔滨用户 ──60ms──→ 深圳源站      哈尔滨用户 ──5ms──→ 哈尔滨边缘节点（有缓存）
北京用户   ──35ms──→ 深圳源站      北京用户   ──3ms──→ 北京边缘节点（有缓存）
纽约用户   ──250ms─→ 深圳源站      纽约用户   ──10ms──→ 纽约边缘节点（有缓存）
```

💡 **想多一点：CDN 不是"加速"，是"拉近"**

很多人说"CDN 加速网站"。准确的说法是：CDN 不改变传输速度，而是缩短传输距离。光速不变，但你可以让数据少走一段路。就像你家楼下开了便利店，不是你走路变快了，是你不用跑两公里去超市了。

❌ **常见误解**："我上了 CDN，源站更新了内容，为什么用户还是看到旧版本？CDN 坏了吧？"

✅ **真相**：CDN 没坏——是缓存 TTL 还没到期，边缘节点还在用旧版本。正常做法是：源站更新内容后，去 CDN 控制台执行**缓存刷新**（Purge），让边缘节点立即丢弃旧缓存，下次请求回源取新内容。大厂 CDN（Cloudflare/Aliyun CDN）通常支持秒级刷新，但免费套餐可能有频率限制（如每天 2000 次）。

## 34.3 CDN 工作流程（5 步图解）

这是整个 CDN 最核心的流程，每一步都有自己的道理：

```
步骤①                步骤②               步骤③               步骤④              步骤⑤
用户浏览器           DNS 服务器           GSLB              最近边缘节点         源站
  │                    │                   │                   │                  │
  │ "www.abc.com 的   │                   │                   │                  │
  │  IP 是什么？"     │                   │                   │                  │
  │──────────────────→│                   │                   │                  │
  │                    │ 查询请求来自哪个   │                   │                  │
  │                    │ 地区的用户          │                   │                  │
  │                    │──────────────────→│                   │                  │
  │                    │                   │ 根据 IP 地理位置    │                  │
  │                    │                   │ 数据库，判断用户    │                  │
  │                    │                   │ 在北京              │                  │
  │                    │                   │                   │                  │
  │                    │ 返回北京边缘节点   │                   │                  │
  │                    │ IP: 1.2.3.4       │                   │                  │
  │                    │←──────────────────│                   │                  │
  │                    │                   │                   │                  │
  │  返回 DNS 解析结果 │                   │                   │                  │
  │  www.abc.com →    │                   │                   │                  │
  │  1.2.3.4          │                   │                   │                  │
  │←──────────────────│                   │                   │                  │
  │                    │                   │                   │                  │
  │ HTTP 请求 www.abc.com/index.html      │                   │                  │
  │──────────────────────────────────────────────────────────→│                  │
  │                    │                   │                   │ 缓存有 index.html？
  │                    │                   │                   │   → 有：直接返回
  │                    │                   │                   │   → 没有：回源
  │                    │                   │                   │               回源请求
  │                    │                   │                   │──────────────────→│
  │                    │                   │                   │  返回最新内容     │
  │                    │                   │                   │←──────────────────│
  │                    │                   │                   │ 缓存一份 + 返回用户
  │  返回 index.html   │                   │                   │                  │
  │←──────────────────────────────────────────────────────────│                  │
```

### 逐步解释

**步骤① 用户发起 DNS 查询**：用户在浏览器输入 `www.abc.com`，浏览器向 DNS 服务器询问这个域名对应的 IP。这部分是标准的 DNS 流程（回顾 Ch20-21）。

**步骤② DNS 转发给 GSLB**：CDN 厂商的 DNS 服务器不会直接返回源站 IP，而是把请求交给 **GSLB**（Global Server Load Balance，全局负载均衡）。GSLB 是 CDN 的"大脑"，负责判断应该把用户导向哪个边缘节点。

**步骤③ GSLB 判断最近节点**：GSLB 拿到 DNS 请求的**来源 IP**（即用户所在 Local DNS 的 IP），去查 IP 地理位置数据库（GeoIP），判断用户大概在哪个地区、哪个运营商。然后从自己的边缘节点列表中，选出一个网络距离最近的节点，返回它的 IP。GSLB 的判断依据在 34.4 节详讲。

**步骤④ 用户访问边缘节点**：用户拿到最近边缘节点的 IP，发起 HTTP 请求。边缘节点检查自己有没有这份内容：

- **缓存命中**（Cache Hit）：有，直接返回。用户感受到的速度就是"访问本地服务器"的速度。
- **缓存未命中**（Cache Miss）：没有（或已过期），边缘节点代替用户向源站发请求，拿到内容后缓存一份，再返回给用户。这个从源站取内容的过程叫**回源**（Origin Pull）。

**步骤⑤ 内容返回用户**：无论走缓存命中还是回源，最终用户都拿到了内容，而且下次再请求同一份内容时，边缘节点已经有缓存了。

## 34.4 GSLB 如何判断"最近节点"

上一节说 GSLB 把用户导向最近的边缘节点。怎么判断"最近"？这里有一个重要细节很多人理解错了。

### GSLB 的判断依据

GSLB 能看到的是 **DNS 请求的来源 IP**（即用户所使用的 Local DNS 服务器的 IP）。然后：

1. **查 IP 地理位置数据库**：通过 GeoIP 数据库（MaxMind 等），判断这个 IP 大概属于哪个国家/省份/城市。注意：这不是 100% 精确——IP 地址和人一样，会"搬家"，GeoIP 数据库也有更新延迟。一般可以精确到城市级别。

2. **查运营商**：同一 IP 也对应了运营商信息（电信、联通、移动等）。这点非常重要——中国跨运营商访问可能比跨地域访问还慢。北京电信用户访问北京移动的服务器，延迟可能比访问广州电信还高。

3. **结合网络拓扑**：GSLB 内部维护了一张"网络距离表"——记录了自己每个边缘节点到各大运营商、各主要城市的延迟数据。这张表不是静态的，而是实时探测更新。

4. **遴选最优节点**：综合以上因素，选出一个"网络距离"最短的节点。排序优先级通常如下：

```
① 同城市 + 同运营商 → 最佳（如北京电信用户 → 北京电信节点）
② 同城市 + 不同运营商 → 次佳（跨网但物理距离近）
③ 临近城市 + 同运营商 → 第三选择
④ ...以此类推
```

### 为什么看到的 IP 和别人的不一样

这就是 CDN 最直观的验证。你在北京 `dig www.cloudflare.com`，得到的是北京附近节点的 IP；你朋友在上海 `dig`，得到的是上海附近节点的 IP。DNS 解析结果是**因人而异**的——GSLB 让同一个域名在不同地区解析到不同 IP。

💡 **想多一点：为什么用 Local DNS IP 而不是用户真实 IP？**

GSLB 看到的是 DNS 请求的来源 IP，也就是你的 Local DNS 服务器的 IP，不是你电脑的 IP。这就产生了一个经典问题：**DNS 劫持/EDNS**。

- 如果你用的是运营商默认 DNS（如电信的 DNS），GSLB 看到的是这个 DNS 服务器的 IP——能准确反映你的地理位置。
- 如果你手动配了 8.8.8.8（Google DNS），GSLB 看到的是 8.8.8.8 所在位置的 IP——可能在美国。即使你在北京，GSLB 也可能把你导向美国的边缘节点，因为 Google DNS 没有把"用户真实 IP"透传给 GSLB。

好在现在大多数 CDN 支持 **EDNS Client Subnet**（ECS），允许 DNS 服务器在请求中附带用户真实 IP 的前缀，让 GSLB 做出更准确的调度。但这不是默认开启的，取决于 DNS 服务商是否支持。

**实用建议**：用 CDN 的用户，尽量使用运营商默认 DNS 或支持 ECS 的公共 DNS（如 114.114.114.114），不要盲目切到 8.8.8.8，否则可能"反向加速"。

## 34.5 回源策略：缓存不是永久的

边缘节点的缓存空间有限，不可能把所有内容都存下来。有以下几种回源场景：

### 缓存过期

边缘节点上的每份内容都有一个 **TTL**（Time To Live，生存时间）。TTL 到期后，缓存被视为"过期"。注意：过期不等于删除——下次用户请求时，边缘节点会先问源站"这份内容有没有更新"，如果没有更新，延长 TTL；如果有更新，获取新内容。

设置过期的 HTTP 头（源站返回）：
```
Cache-Control: max-age=3600     → 缓存 1 小时
Cache-Control: max-age=86400    → 缓存 1 天
Cache-Control: no-cache         → 每次都要问源站
```

### 缓存未命中

边缘节点上没有此内容（冷数据、新发布的文章等），直接回源取数据并缓存。

### 主动预热

在大促、活动前，CDN 厂商提供**缓存预热**（Cache Prefetch）功能：你可以提交一份 URL 列表，CDN 提前去源站把这些内容拉到边缘节点缓存好。这样活动开始时，所有用户直接命中缓存，源站零压力。

## 34.6 CDN 不止加速：三大附加价值

很多人以为 CDN 就是加速器。实际上，现代 CDN 已经演变成一个"边缘安全 + 加速平台"：

### 1. DDoS 防护

CDN 天然具备抗 DDoS（分布式拒绝服务攻击）的能力。因为用户请求先打到边缘节点而不是源站：

- 攻击流量被分散到全球数百个节点上，每个节点承受的压力很小
- 边缘节点可以识别并丢弃恶意流量，不会让攻击流量到达源站
- 源站的真实 IP 被隐藏（用户只知道 CDN 节点 IP），攻击者无法直接攻击源站

### 2. WAF（Web Application Firewall，Web 应用防火墙）

**WAF** 是一种专门防护 Web 应用层攻击（如 SQL 注入、XSS 跨站脚本、CSRF 跨站请求伪造）的安全产品。在 CDN 场景下，WAF 通常集成在边缘节点上，在请求到达源站之前就拦截恶意请求。

**一句话记住**：传统防火墙挡 IP/端口级别的攻击（DDoS、端口扫描），WAF 挡应用层攻击（SQL 注入、XSS）。两者的区别就像——传统防火墙管"谁可以进门"，WAF 管"进门的人有没有带武器"。

### 3. HTTPS 加速

CDN 节点可以替你处理 TLS 握手（回顾 Ch25）。用户和 CDN 节点之间走 HTTPS，CDN 和源站之间可以走 HTTP（如果信任链路），也可以走 HTTPS。这样可以：

- TLS 握手在就近节点完成，延迟低（不用跨全球做 TLS 握手）
- CDN 节点维护 SSL 证书，源站不用关心证书管理
- 支持 HTTP/2、HTTP/3 等新协议，即使源站只支持 HTTP/1.1

## 术语表

| 术语 | 解释 |
|------|------|
| **CDN** | Content Delivery Network，内容分发网络。通过全球边缘节点缓存内容，让用户就近访问 |
| **边缘节点（Edge Node）** | 分布在各地的 CDN 缓存服务器，存放源站内容的副本 |
| **GSLB** | Global Server Load Balance，全局负载均衡。CDN 的"大脑"，通过 DNS 判断用户位置并导向最近节点 |
| **回源（Origin Pull）** | 边缘节点缓存未命中时，向源站请求内容的过程 |
| **缓存命中（Cache Hit）** | 请求的内容在边缘节点缓存中存在（且未过期），直接返回 |
| **缓存未命中（Cache Miss）** | 请求的内容在边缘节点不存在或已过期，需要回源 |
| **缓存预热（Cache Prefetch）** | 提前把内容主动推送到边缘节点，避免首次访问回源 |
| **WAF** | Web Application Firewall，Web 应用防火墙。防护 SQL 注入、XSS 等应用层攻击 |
| **TTL** | Time To Live，缓存内容的生存时间。到期后边缘节点需要向源站验证是否更新 |
| **EDNS Client Subnet** | DNS 扩展协议，允许 DNS 服务器将用户真实 IP 前缀传给 GSLB，提高调度精度 |
