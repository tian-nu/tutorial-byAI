# 26 — WebSocket：HTTP 做不到的长连接

## 学习目标
- 理解 HTTP 请求-响应模型的局限：服务器不能主动推送
- 掌握 WebSocket 的升级握手过程
- 理解 WebSocket 是**同一条 TCP 连接升级**（不是新建连接）
- 能对比短轮询、长轮询、SSE、WebSocket 四种实时通信方案
- 会用 DevTools 查看 WebSocket 帧交互

---

## 26.1 HTTP 的痛点：服务器有话说不出口

HTTP 的模式是**请求-响应**——客户端不提问，服务器就不能说话。

你能想到的所有"实时"功能——微信消息推送、股票价格跳动、游戏队友位置更新、协作文档里别人打的字——都不是"先请求再响应"的。**服务器需要主动通知客户端**。

如果只靠 HTTP，你怎么实现"服务器主动告诉浏览器消息"？

---

## 26.2 没有 WebSocket 的时候，大家怎么凑合

### 方案一：短轮询（Short Polling）

每隔 N 秒，客户端发一个请求问"服务器，有新消息吗？"

```
客户端 ─每隔3秒─→ "有新消息吗？"
服务器              "没有"
客户端 ─每隔3秒─→ "有新消息吗？"
服务器              "还是没有"
客户端 ─每隔3秒─→ "有新消息吗？"
服务器              "有！3 条！"
```

问题很明显：90% 的请求都是"没有"，白白消耗带宽、CPU 和连接资源。3 秒中间到达的消息要等 3 秒才被拿到，不够实时。

### 方案二：长轮询（Long Polling）

短轮询的优化版：客户端发请求，服务器不立即返回，而是**先等着**——等有新消息才返回；返回后客户端立即再发一个请求。

```
客户端 ──→ "有新消息吗？"
服务器     (等着...) 等 10 秒终于有新消息了
客户端 ←── "有！回你消息了"
客户端 ──→ "继续等新消息"
```

比短轮询好（没消息时不浪费请求），但本质上还是"一问一答"，连接频繁断开重建。

### 方案三：SSE（Server-Sent Events，服务器推送事件）

SSE 是 HTTP 的一个扩展：客户端发起一个长连接，服务器在这个连接上**持续写入数据**，但只单向——服务器→客户端。客户端不能发数据。

```javascript
// 客户端（浏览器）
const eventSource = new EventSource('/api/events');
eventSource.onmessage = (event) => {
  console.log('服务器推送:', event.data);
};
```

- 优点：浏览器原生支持、自动重连、比 WebSocket 简单
- 局限：**单向**，HTTP 连接

### WebSocket 出场——四种方案对比

| 方案 | 方向 | 底层连接 | 延迟 | 协议开销 | 场景 |
|------|------|----------|------|----------|------|
| **短轮询** | 双向（但浪费） | 每次新 HTTP 连接 | 取决于轮询间隔（典型 1~5s） | 每个请求都带完整 HTTP 头 | 旧系统、不需要实时的 |
| **长轮询** | 双向（但一问一答） | 每次新 HTTP 连接 | 比短轮询低 | 每个应答带 HTTP 头 | 过渡方案 |
| **SSE** | **单向**（服→客） | 一条 HTTP 长连接 | 低 | 很低 | 单向推送：股票、通知、feed |
| **WebSocket** | **全双工双向** | **一条 TCP 连接升级后保持** | 毫秒级 | 仅 2~10 字节帧头 | 聊天、游戏、协作编辑 |

💡 **想多一点**：SSE 和 WebSocket 的选择很直观——如果你只需要服务器推消息而客户端不需要主动发（新闻推送、实时股价），用 SSE 就够了，比 WebSocket 少写不少代码。但聊天这种客户端也要发言的场景，SSE 不够用，必须 WebSocket。

## 26.3 WebSocket 的连接升级——同一根电话线，换个通话模式

WebSocket 最容易被误解的就是"它是独立的协议"。**它不是独立的**——它始于一个 HTTP 请求，然后**同一条 TCP 连接升级**为 WebSocket 模式。

用快递公司打比喻：你叫了一辆货车（TCP 连接），先送了一封普通快递（HTTP GET 请求），收货人回来说"以后这辆货车改成专线车，24 小时来回直接送"，然后**同一辆车**开始在你们之间往返跑——这就是 WebSocket。

### 升级握手过程

```
客户端                                        服务器
   │                                            │
   │── HTTP GET /chat ────────────────────────→│
   │   Connection: Upgrade                      │
   │   Upgrade: websocket                       │
   │   Sec-WebSocket-Key: dGhlIHNhbXBsZ...      │
   │   Sec-WebSocket-Version: 13                │
   │                                            │
   │←── 101 Switching Protocols ───────────────│
   │   Connection: Upgrade                      │
   │   Upgrade: websocket                       │
   │   Sec-WebSocket-Accept: s3pPLMBiTxa...     │
   │                                            │
   ═══ 同一条 TCP 连接，现在走 WebSocket 帧 ═══
```

关键点：
1. 握手是标准的 **HTTP GET** 请求，带 `Upgrade: websocket` 头
2. 服务器返回 **101 Switching Protocols**——从 HTTP 模式切换到 WebSocket 模式
3. 切换后，**这条 TCP 连接还在**，没有断开也新建，只是协议从 HTTP 变成了 WebSocket 帧格式

验证：你可以在 DevTools Network 面板里点 WS 标签，看到请求最开始就是普通的 HTTP，然后状态码是 101。

## 26.4 WebSocket 帧格式——极简到只剩 2 字节

HTTP 每个请求都要带完整的 header（几百到几千字节），WebSocket 不一样——它直接发包，帧头只有 **2~10 字节**：

```
WebSocket 帧结构：
┌──────────────────────────────────────┐
│ FIN│RSV│Opcode│Mask│Payload len... │  ← 开头 2 字节
├──────────────────────────────────────┤
│   [Masking key（如果 Mask=1）]       │  ← 4 字节（仅客户端→服务器）
├──────────────────────────────────────┤
│   负载数据（Payload）                 │
└──────────────────────────────────────┘
```

这个开销小到可以忽略不计。每秒钟发送几十条消息，流量几乎全是数据本身。

## 26.5 WebSocket 的常见应用场景

| 场景 | 为什么必须 WebSocket |
|------|---------------------|
| **即时通讯（微信/钉钉/WhatsApp）** | 消息必须毫秒级推送，双向通信 |
| **协作编辑（Google Docs/Notion）** | 多人同时编辑，改动需要实时广播给所有人 |
| **实时数据大屏** | 服务器持续推送监控数据，HTTP 轮询撑不住 |
| **在线游戏** | 位置和状态需要双向、低延迟传输 |
| **实时交易/竞价** | 延迟是钱，100ms 就可能亏一大笔 |

## 26.6 实战：在 DevTools 看 WebSocket

### Windows / Linux / macOS 操作都一样：

1. F12 打开 DevTools → 切换到 **Network** 面板
2. 打开一个使用 WebSocket 的网站（比如很多聊天 demo、实时数据大屏）
3. Network 面板里找到 **WS** 标签（网页加载完就会出现）
4. 点击 WebSocket 连接 → 选择 **Messages** 标签
5. 可以看到：
   - **Request Headers** 里有 `Upgrade: websocket`
   - **Response Headers** 里状态码是 **101 Switching Protocols**
   - **Messages** 标签里绿色的（发送）和白色的（接收）帧交互

---

## 26.7 一个常见坑：心跳保活

WebSocket 建立在 TCP 上，TCP 连接如果长时间没有数据流量，中间的网络设备（NAT、防火墙、负载均衡器）会认为这个连接"死了"，主动切断。

实际开发中，WebSocket 要做**心跳（Ping/Pong）**——每隔一段时间（30 秒~60 秒）发送一个空帧，确保网络设备不会把连接关掉。

WebSocket 协议原生支持 Ping/Pong 帧，但大部分框架封装了一层，你自己定时发即可。

❌ **常见错误**：以为建立了 WebSocket 就一直连着。不做心跳的话，过了几分钟连接会在你不知不觉的时候断开，等真正有消息要发的时候才发现连不上了。

## 26.8 小结

| 概念 | 要点 |
|------|------|
| **WebSocket** | 在 HTTP 握手后，将同一条 TCP 连接升级为全双工双向通信 |
| **升级握手** | HTTP GET + `Upgrade: websocket` → 101 Switching Protocols |
| **同一条 TCP 连接** | WebSocket 不是新建连接，是复用握手时那条 TCP 连接 |
| **帧头开销** | 仅 2~10 字节，适合高频消息 |
| **SSE** | 单向（服务器→客户端），HTTP 长连接，比 WebSocket 简单 |
| **心跳** | 必须定期发 Ping/Pong 防网络设备切断连接 |

## 术语表

| 术语 | 解释 |
|------|------|
| **WebSocket**（此术语需进附录） | 基于单条 TCP 连接的全双工通信协议，通过 HTTP 升级握手建立 |
| **全双工（Full-Duplex）** | 通信双方可以同时发送和接收数据，不需要等待对方 |
| **101 Switching Protocols**（此术语需进附录） | WebSocket 升级握手成功时服务器的 HTTP 状态码 |
| **SSE（Server-Sent Events）** | 服务器推送事件，基于 HTTP 的单向推送技术，自动重连 |
| **短轮询（Short Polling）** | 定期发送 HTTP 请求检查新消息，浪费资源 |
| **长轮询（Long Polling）** | 服务器在无新消息时延迟响应，有新消息立即返回，提高效率 |
| **心跳（Ping/Pong）** | 定期发送空帧保持连接活跃，防止中间网络设备超时断连 |

## 验证方法

1. 打开任意使用了 WebSocket 的网站（推荐用一些 WebSocket 测试页面，比如 Websocket.org 的 Echo Test）
2. F12 → Network → WS 标签
3. 确认你能看到：
   - HTTP 请求头里 `Upgrade: websocket`
   - 响应状态码 **101**
   - Messages 标签里有双向帧交互

如果能找到这些，说明你理解了本章的核心内容。

## 最可能出错的地方及原因

1. **以为 WebSocket 是独立协议**：很多人把 WebSocket 和 TCP、UDP 并列，其实它工作在 TCP 之上，通过 HTTP 升级握手建立。`ws://` 和 `http://` 的关系就像 `https://` 和 `http://` 的关系——前者是后者的升级版，不是全新的东西。

2. **忘加心跳保活导致连接超时断开**：WebSocket 没有自动心跳，连接空闲 1~5 分钟就被中间设备切断。如果上线后发现用户"莫名掉线"，大概率是没做心跳。

3. **混淆 SSE 和 WebSocket 的适用场景**：不是所有"实时"都需要 WebSocket。单向推送（比如新闻通知、股价更新）用 SSE 更简单；只有需要客户端也及时往服务器发数据时（聊天、游戏）才用 WebSocket。
