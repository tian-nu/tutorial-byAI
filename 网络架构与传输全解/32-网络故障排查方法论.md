## 32.1 核心思维：从底层往上排，每次只动一层

想象你家突然停水了。你会：

1. 先去厨房拧水龙头 → 确认确实没水（不是幻觉）
2. 问邻居有没有水 → 判断是自家问题还是整栋楼问题
3. 检查自家总阀门 → 看是不是自己关了
4. 打电话问物业 → 确认是不是小区停水

你不会：一上来就把热水器拆了。

网络排错也是如此——**从最底层（物理/网络层）开始，一层一层往上确认，每次只排查一层**。

网络分层（TCP/IP 四层模型，回顾第 2-3 章）：

```
应用层（HTTP/DNS/TLS）  ← 最后排查
传输层（TCP/UDP）       ← 第三排查
网络层（IP/路由）        ← 第二排查
网络接口层（网卡/链路）   ← 最先排查
```

💡 **想多一点：为什么不能跳过底层直接从应用层开始排查？**

因为如果你网络层（IP 不通）出了问题，你在应用层（curl、浏览器）试一万次也是白费。底层不通 = 上层全废。这个问题非常常见——很多人网络出问题时反复"清浏览器缓存"、"换个浏览器试试"、"重启路由器"，但压根没先 ping 一下看是否能通。

## 32.2 "网络不通"的 12 种原因（从物理到应用分层）

按 TCP/IP 分层由下到上排列，每种原因对应一层：

| 层级 | 可能原因 | 典型症状 |
|------|---------|---------|
| 🔌 物理 | 网线没插 / WiFi 没连 / 网卡禁用 | ping 127.0.0.1 通，ping 网关不通 |
| 🔌 物理 | 路由器死机 / 交换机断电 | 局域网内所有设备同时断网 |
| 🌐 网络层 | IP 地址配置错误（DHCP 没拿到） | ipconfig 显示 169.254.x.x |
| 🌐 网络层 | 网关设置错误 | ping 网关不通 |
| 🌐 网络层 | DNS 服务器不可达 | ping 8.8.8.8 通，nslookup 失败 |
| 🌐 网络层 | 路由表错误 / VPN 路由冲突 | 部分网站通、部分不通 |
| 🔒 网络层 | 防火墙拦截（本机或网关） | ping 通但端口不通 |
| 🔗 传输层 | 端口被占用 | 服务启动失败（Address already in use） |
| 🔗 传输层 | 服务未启动 / 崩溃 | 端口没监听 |
| 📄 应用层 | 代理配置错误 | 浏览器报"代理服务器无响应" |
| 📄 应用层 | DNS 劫持/污染 | 解析到错误 IP |
| 🔐 应用层 | 证书过期/不匹配 | HTTPS 报证书错误 |

## 32.3 标准五步排查链路

这是网络工程师的"标准体操"，建议背下来。每一步只验证一层。

```
Step 1: ping 127.0.0.1       → 验证 TCP/IP 协议栈本身是否正常
Step 2: ping 网关 IP          → 验证本机到路由器的链路
Step 3: ping 8.8.8.8         → 验证是否能出局域网到公网
Step 4: nslookup baidu.com   → 验证 DNS 是否正常
Step 5: curl -v http://xxx   → 验证应用层是否正常
```

### Step 1：ping 127.0.0.1 —— 验自己

```powershell
# Windows
ping 127.0.0.1
```

```bash
# macOS / Linux
ping -c 3 127.0.0.1
```

127.0.0.1 是回环地址，数据包不经过网卡，直接在操作系统内部绕一圈回来。

- ✅ **通了**：TCP/IP 协议栈正常工作，网卡驱动也正常
- ❌ **不通**：操作系统 TCP/IP 协议栈本身有问题，这是最严重的情况——考虑重启或检查网卡驱动

> 这个步骤对笔记本电脑意义较小（因为一般能 ping 通）。但如果你刚从 Windows 更新/驱动安装过来，这一步不能跳。

### Step 2：ping 网关 IP —— 验链路

先查看网关 IP：

```powershell
# Windows
ipconfig | findstr "默认网关"
```

```bash
# macOS / Linux
netstat -rn | grep default
# 或
ip route | grep default
```

然后 ping 网关：

```powershell
ping 192.168.1.1   # 替换成你的实际网关 IP
```

```bash
ping -c 3 192.168.1.1
```

- ✅ **通了**：电脑到路由器正常，物理链路没问题
- ❌ **不通**：WiFi 没连 / 网线松了 / 路由器挂了 / IP 地址没拿到

💡 **想多一点：Windows 用 `ipconfig` 看到 169.254.x.x 怎么办？**

169.254.x.x 是 Windows 在 DHCP 失败时自动分配的"僵尸地址"（APIPA，Automatic Private IP Addressing）。这说明你的电脑没从 DHCP 服务器（通常是路由器）拿到合法 IP。

三步修复：
1. `ipconfig /release`（释放僵尸地址）
2. `ipconfig /renew`（重新申请）
3. 如果还不行 → 重启路由器

### Step 3：ping 8.8.8.8 —— 验外网可达性

8.8.8.8 是 Google 公共 DNS，全球可访问，适合作为"外网可达性"检测点。不用域名（www.baidu.com），因为域名依赖 DNS，而现在 DNS 还没验证。

```powershell
ping 8.8.8.8
```

```bash
ping -c 3 8.8.8.8
```

- ✅ **通了**：你的网络能连接到公网，路由正常
- ❌ **不通**：可能是 ISP 断网、光猫掉了、宽带欠费、或者防火墙拦截了 ICMP

如果 Step 2 通但 Step 3 不通：问题在路由器之外（光猫、ISP、宽带线路）。

### Step 4：nslookup 域名 —— 验 DNS

```powershell
# Windows
nslookup baidu.com
```

```bash
# macOS / Linux
nslookup baidu.com
# 或指定 DNS 服务器测试
nslookup baidu.com 8.8.8.8
```

- ✅ **通了**：DNS 解析正常，返回了 IP 地址
- ❌ **不通**：DNS 服务器配置错误 / DNS 服务器不可达 / DNS 被劫持

**注意区分**：
- ping 8.8.8.8 通 + nslookup 不通 → DNS 问题（DNS 服务器挂了或配置错了）
- ping 8.8.8.8 不通 + nslookup 不通 → 连 DNS 服务器的路都不通 = 外网连接问题

### Step 5：curl -v 实际请求 —— 验应用层

```powershell
# Windows
curl.exe -v http://httpbin.org/get
```

```bash
# macOS / Linux
curl -v http://httpbin.org/get
```

观察输出：

- 卡在 `Trying <IP>...` → TCP 三握失败（端口被封、服务没开）
- 卡在 `Connected` 但没有响应 → 应用层问题
- 返回 `200 OK` → 全链路通

### Step 5.5：检查防火墙规则

在五步排查中，如果以下情况出现，就需要检查防火墙：

- ping 8.8.8.8 通但某端口不通（如 80、443）
- curl 卡在 TCP 连接阶段超时
- 内网通，外网不通，且 Step 3 通过

此时需要理解你面对的是哪种防火墙。

## 32.4 防火墙简介——三种防火墙的区别

防火墙就像是网络世界的"门禁系统"，但不同时代的门禁精细程度不同。

### 包过滤防火墙（Packet Filter）

**比喻**：写字楼门口保安，只看"信封上的地址"——来源 IP、目的 IP、端口号。不关心这封信里面写了什么，也不记得刚才谁进过。

**工作层级**：网络层 + 传输层（IP 头 + TCP/UDP 头）

**能做什么**：
- 允许/拒绝来自某 IP 的包
- 允许/拒绝去往某端口的包
- 例：`iptables -A INPUT -p tcp --dport 22 -j DROP`（拒绝所有到 22 端口的 TCP 包）

**不能做什么**：
- 不知道这个包是不是"合法 HTTP 请求"还是"恶意 HTTP 请求"
- 不记得连接状态（每个包独立判断）

### 状态检测防火墙（Stateful Firewall）

**比喻**：写字楼门口有访客登记系统——记得谁进来过，出去时核对。只有"从里面主动发起的连接"的回复包才放行。

**工作层级**：网络层 + 传输层 + 连接状态表

**能做什么**：
- 自动放行"内网主动发起的连接"的回复包（状态表记录）
- 拒绝伪装成回复包的攻击包
- 例：Windows 防火墙、家用路由器内置防火墙

**核心机制**：维护一个"连接追踪表"，记录 (源IP, 源端口, 目的IP, 目的端口, 状态)。

### 应用层防火墙（Application Layer Firewall / WAF）

**比喻**：写字楼安检机——每一封信都要拆开看内容，确认不是危险物品才放行。

**工作层级**：应用层（HTTP 头、请求体、SQL 语句等）

**能做什么**：
- 拦截 SQL 注入、XSS 攻击
- 拦截访问特定 URL 的请求
- 限制请求频率（防 DDoS）
- 例：ModSecurity、Cloudflare WAF

### 三种防火墙对比

| 类型 | 工作层 | 精细度 | 性能开销 | 典型产品 |
|------|--------|--------|---------|---------|
| 包过滤 | IP+端口 | 粗 | 低 | iptables, Windows 防火墙（基本） |
| 状态检测 | IP+端口+连接状态 | 中 | 中 | Windows 防火墙, 家用路由器 |
| 应用层 | HTTP内容 | 细 | 高 | ModSecurity, Cloudflare WAF |

### 排查时怎么看防火墙

在 Step 5.5 中，按以下顺序检查：

1. **本机防火墙**：
   ```powershell
   # Windows：检查防火墙状态
   Get-NetFirewallProfile | Select Name, Enabled
   ```
   ```bash
   # Linux：检查 iptables 规则
   sudo iptables -L -n
   # macOS：检查 pf 防火墙
   sudo pfctl -s all
   ```

2. **路由器/网关防火墙**：登录路由器管理页面，检查是否有端口过滤规则

3. **云服务商安全组**：如果你在用云服务器（阿里云/腾讯云/AWS），检查安全组是否允许对应端口

## 32.5 常见场景排错表

| 场景 | 最可能原因 | 排查方法 | 修复方法 |
|------|-----------|---------|---------|
| **能上 QQ 打不开网页** | DNS 故障 | ping 8.8.8.8 通但 nslookup 不通 | 改 DNS 为 8.8.8.8 |
| **内网资源通，外网不通** | 网关/路由问题 | ping 网关通，ping 8.8.8.8 不通 | 检查路由器外网连接 |
| **ping 通但端口不通** | 防火墙 / 服务没启动 | telnet IP 端口 看是否连接 | 检查防火墙规则和服务状态 |
| **HTTPS 打不开但 HTTP 可以** | 证书问题 / 443 端口被封 | curl -v https://xxx 看错误信息 | 检查证书、检查 443 端口是否开放 |
| **部分网站通、部分不通** | 路由 / DNS / VPN 分流 | traceroute 不通的域名 | 检查本地路由表或关闭 VPN |
| **间歇性断网** | WiFi 干扰 / DHCP 租约过期 | 长时间 ping 网关看丢包率 | 换信道/检查 DHCP 设置 |

💡 **想多一点：关于"能上 QQ 打不开网页"这个经典案例**

老网工一定听过这句话。它的经典解释是：**旧版 QQ 使用 IP 直连（UDP）而非域名访问，所以 DNS 挂了不影响 QQ，但浏览器依赖 DNS 解析域名。** 但这个结论需要更新了：

**现代 QQ 也大量使用域名**（登录、消息、文件传输都走 HTTP/HTTPS）。如果你今天真的遇到"QQ 能发消息但打不开网页"，更可能的原因是：
1. **DNS 故障但 QQ 缓存了 IP**（QQ 登录后会缓存服务器 IP，短时间内不需要再次 DNS 解析）
2. **代理设置问题**（浏览器配了代理但不通，QQ 不走代理）

所以排查时不要刻板套结论，先用 nslookup 验证 DNS 确实有问题再说。

## 32.6 故意制造问题——防火墙拦截实验

与其等出问题再排查，不如自己制造问题然后修好它。这会让你对排查链路有肌肉记忆。

### 实验：把 DNS 改错，然后排查为什么上不了网

**Step 1 — 制造问题**：

```powershell
# Windows：把 DNS 改成 127.0.0.1（本地回环，没有 DNS 服务）
# 控制面板 → 网络和共享中心 → 更改适配器设置 → 右键网卡 → 属性 → 
# Internet 协议版本 4 (TCP/IPv4) → 属性 → 使用下面的 DNS 服务器地址：
# 首选 DNS：127.0.0.1
# 备用 DNS：留空
```

```bash
# macOS：系统偏好设置 → 网络 → 高级 → DNS → 添加 127.0.0.1（移到最上面）
# Linux（临时，重启失效）：
sudo sh -c 'echo "nameserver 127.0.0.1" > /etc/resolv.conf'
```

**Step 2 — 验证问题存在**：打开浏览器，访问 `http://httpbin.org/get`，应该打不开（一直转圈或报 DNS 相关错误）。

**Step 3 — 五步排查**：

| 步骤 | 命令 | 结果 | 结论 |
|------|------|------|------|
| Step 1 | `ping 127.0.0.1` | 通 | TCP/IP 协议栈正常 |
| Step 2 | `ping 网关IP` | 通 | 到路由器链路正常 |
| Step 3 | `ping 8.8.8.8` | 通 | 外网可达，路由正常 |
| Step 4 | `nslookup baidu.com` | **失败**（连不上 127.0.0.1 的 DNS） | DNS 有问题！ |
| Step 5 | 跳过（DNS 没通，curl 也解析不了域名） | — | — |

**Step 4 — 定位根因**：Step 4 失败 + Step 3 通过 = DNS 服务器配置有问题。检查 DNS 设置，发现被改成了 `127.0.0.1`。

**Step 5 — 修复**：把 DNS 改回 `8.8.8.8` 或自动获取。刷新页面。

**Step 6 — 验证修复**：浏览器访问 `http://httpbin.org/get`，能打开即修复成功。

> 📝 完整走一遍流程后，你对五步排查法就会有肌肉记忆。下次真的网络出问题时，按这个顺序排查，比慌乱中到处乱试高效 10 倍。

## 术语表

| 术语 | 解释 |
|------|------|
| **回环地址（127.0.0.1）** | 本机内部通信地址，数据不经过物理网卡，用于测试操作系统 TCP/IP 协议栈是否正常 |
| **网关** | 局域网出口，通常由路由器担任。所有出局域网的流量都经过网关 |
| **APIPA (169.254.x.x)** | Windows DHCP 失败时自动分配的临时地址，只能局域网通信，不能上外网 |
| **包过滤防火墙** | 只看 IP 头和 TCP/UDP 头的源/目的信息做放行/拒绝决策，不关心包内容 |
| **状态检测防火墙** | 维护连接状态表，能自动放行"内网主动发起连接"的回复包，比包过滤更智能 |
| **应用层防火墙（WAF）** | 检查 HTTP 内容（URL、请求体），防御 SQL 注入、XSS 等应用层攻击 |
| **安全组** | 云服务器的虚拟防火墙，在实例级别控制入站和出站流量 |
