## 33.1 三个易混淆概念——别再乱用了

### 带宽（Bandwidth）

**比喻**：水管的粗细。

**定义**：链路在单位时间内能传输的最大数据量。单位：Mbps（兆比特每秒）。

**本质**：物理上限，由硬件决定（网线是百兆还是千兆、光纤带宽多大）。

**你说"我家宽带 100M"**：这说的是带宽。

### 延迟（Latency）

**比喻**：水从水厂流到你家水龙头的时间。

**定义**：一个数据包从源到目的地所需的时间。单位：毫秒（ms）。通常用 RTT（Round Trip Time，往返时间）来衡量。

**本质**：由物理距离、路由跳数、网络拥塞决定。RTT ≈ 距离 / 光速 + 路由器处理时间 + 排队时间。

**你 ping 百度看到 `time=30ms`**：这说的是延迟。

### 吞吐量（Throughput）

**比喻**：你打开水龙头，实际流出来的水量。

**定义**：单位时间内**实际传输**的数据量。单位：Mbps。

**本质**：受带宽限制，受延迟影响，受丢包率、拥塞控制等因素制约。

**关系**：

```
实际吞吐量 ≤ 带宽
实际吞吐量 ≤ TCP 窗口大小 / RTT    （理论上限）
```

❌ **常见误解**："我家里是千兆宽带，为什么上网还是慢？"

✅ **真相**：千兆是带宽，慢可能是因为延迟高（访问国外网站 RTT 300ms）、丢包率高（WiFi 信号差）、或者服务器本身就慢。

💡 **想多一点：带宽和延迟各自独立影响什么？**

| 场景 | 关键瓶颈 | 为什么 |
|------|---------|--------|
| 下载大文件 | 带宽 | 一次性大量数据传输 |
| 网页浏览 | 延迟 | 每个小资源（图片、CSS、JS）都要 RTT |
| 在线游戏 | 延迟 | 小包高频交互，延迟就是反应速度 |
| 视频会议 | 带宽 + 延迟 | 大量数据持续传输 + 低延迟需求 |
| 备份到云端 | 带宽 | 数据量大，不影响交互 |

这就是为什么"你家千兆宽带打游戏还是不流畅"——游戏要的是低延迟，跟带宽关系不大。

## 33.2 HTTP 请求耗时拆解——慢在哪一站？

一次 HTTP 请求的总耗时可以拆成以下几段：

```
总耗时 = DNS解析 + TCP握手 + TLS握手 + TTFB + 下载时间

  DNS解析    TCP三握    TLS握手    等待响应   下载内容
  |------|   |----|    |--------|  |------|  |--------|
  ─────────────────────────────────────────────────────→ 时间
```

| 阶段 | 含义 | 典型耗时（国内） | 受什么影响 |
|------|------|-----------------|-----------|
| DNS 解析 | 域名 → IP | 1~50ms | DNS 服务器距离/缓存 |
| TCP 三次握手 | 建立连接（第15-17章） | 1×RTT | 物理距离 |
| TLS 握手 | 加密协商（第24章） | 1~2×RTT | 物理距离+证书链长度 |
| TTFB | Time To First Byte，首个字节到达 | 不定 | 服务器处理速度 |
| 下载 | 传输响应体 | 取决于数据量/带宽 | 带宽+TCP 拥塞窗口 |

**TTFB** 是一个重要指标。它衡量的是：你发起请求后，服务器多久开始给你回数据的第一个字节。包含服务器处理逻辑、数据库查询、后端渲染的时间。

## 33.3 带宽延迟积（BDP）——为什么"快"不等于"大"

**带宽延迟积**（Bandwidth-Delay Product）是一个被很多人忽略的概念：

```
BDP = 带宽 × RTT
```

**它表示**：在任意时刻，网络中"飞行中"的最大数据量——已经发出但还没被确认的数据。

**为什么重要**：TCP 的发送窗口（第 15-17 章讨论的滑动窗口）必须 ≥ BDP，否则带宽无法被充分利用。

### 举例

**场景 A**：你家宽带 100Mbps，访问国内服务器 RTT = 10ms

```
BDP = 100Mbps × 10ms = 100 × 10^6 bit/s × 0.01s = 1,000,000 bit ≈ 125 KB
```

你的 TCP 窗口只需要 125KB 就能跑满带宽。几乎所有现代操作系统默认都能满足。

**场景 B**：你家宽带 100Mbps，访问美国服务器 RTT = 200ms

```
BDP = 100Mbps × 200ms = 20,000,000 bit ≈ 2.5 MB
```

你的 TCP 窗口需要 2.5MB 才能跑满 100Mbps！如果窗口不够大，实际吞吐量会远低于带宽。

❌ **常见结论错误**："我家是 100M 宽带，为什么访问美国服务器只能跑到 10M？"

✅ **正确诊断**：不是宽带缩水，是延迟太高导致 BDP 太大，TCP 窗口没跟上。或者是丢包率太高导致 TCP 不断降速（拥塞控制机制，第 15-17 章）。

## 33.4 curl -w —— 实测你的请求慢在哪

`curl` 的 `-w`（write-out）参数可以输出请求各阶段耗时，让你精确知道慢在哪一站。

### 完整模板文件

创建一个文件 `curl-format.txt`，内容如下：

```
    time_namelookup:  %{time_namelookup}\n
       time_connect:  %{time_connect}\n
    time_appconnect:  %{time_appconnect}\n
   time_pretransfer:  %{time_pretransfer}\n
      time_redirect:  %{time_redirect}\n
 time_starttransfer:  %{time_starttransfer}\n
                    ----------\n
         time_total:  %{time_total}\n
```

⚠️ **注意**：模板开头有 4 个空格的对齐缩进，保持即可。

### 各变量含义

| 变量 | 含义 | 对应阶段 |
|------|------|---------|
| `time_namelookup` | DNS 解析耗时 | DNS 解析 |
| `time_connect` | TCP 三次握手完成的时间（含 DNS） | DNS + TCP 握手 |
| `time_appconnect` | SSL/TLS 握手完成的时间（含前面所有） | DNS + TCP + TLS |
| `time_pretransfer` | 准备传输文件的时间 | DNS + TCP + TLS + 准备 |
| `time_redirect` | 所有重定向的总耗时 | — |
| `time_starttransfer` | 收到第一个字节的时间（TTFB） | DNS + TCP + TLS + 服务器处理 |
| `time_total` | 总耗时 | 全部 |

### 各段耗时计算

```
DNS 解析耗时    = time_namelookup
TCP 握手耗时    = time_connect - time_namelookup
TLS 握手耗时    = time_appconnect - time_connect
服务器处理+TTFB = time_starttransfer - time_pretransfer
内容下载耗时    = time_total - time_starttransfer
```

### 实测

```bash
# 对 HTTP 明文请求
curl -w "@curl-format.txt" -o NUL http://httpbin.org/get      # Windows
curl -w "@curl-format.txt" -o /dev/null http://httpbin.org/get  # macOS/Linux
```

```bash
# 对 HTTPS 加密请求
curl -w "@curl-format.txt" -o NUL https://www.baidu.com        # Windows
curl -w "@curl-format.txt" -o /dev/null https://www.baidu.com    # macOS/Linux
```

示例输出：

```
    time_namelookup:  0.015
       time_connect:  0.056
    time_appconnect:  0.129
   time_pretransfer:  0.129
      time_redirect:  0.000
 time_starttransfer:  0.243
                    ----------
         time_total:  0.348
```

解读：
- DNS：15ms（快，可能已有缓存）
- TCP 握手：56 - 15 = 41ms
- TLS 握手：129 - 56 = 73ms
- TTFB：243 - 129 = 114ms（服务器处理时间）
- 下载：348 - 243 = 105ms

从这个例子你能看出：**TLS 握手（73ms）和 TTFB（114ms）** 占了总耗时的大部分。如果要优化，优先看这两个。

## 33.5 iperf3 测速——测出你的真实带宽

💡 **本节为可选进阶内容，需要两台机器（两台电脑，或一台电脑 + 一台云服务器）。如果没有两台机器，可以跳过。**

`iperf3` 是网络性能测试的标准工具，能测出两点之间的真实吞吐量，不受协议开销的干扰。

### 安装

```powershell
# Windows：从 https://iperf.fr/iperf-download.php 下载 exe
```

```bash
# macOS
brew install iperf3

# Linux
sudo apt install iperf3
```

### 使用

**服务端**（在其中一台机器上运行）：

```bash
iperf3 -s
```

输出显示 `Server listening on 5201` 即表示就绪。

**客户端**（在另一台机器上运行）：

```bash
iperf3 -c <服务端IP> -t 10
```

`-c`：客户端模式，后面跟服务端 IP  
`-t 10`：测试 10 秒

### 输出解读

```
[ ID] Interval           Transfer     Bitrate
[  5]   0.00-10.00  sec   110 MBytes  92.5 Mbits/sec
```

- Transfer：10 秒内传输了 110MB
- Bitrate：实测吞吐量 92.5 Mbps

**如果 iperf3 显示 92.5Mbps 但你家是 100Mbps 宽带**：正常。100Mbps 是理论值，实际受 TCP 头开销、网络转换损耗、中间路由器性能等因素影响。

**iperf3 诊断技巧**：

- 吞吐量接近带宽 → 链路基本健康
- 吞吐量远低于带宽（如 100M 只测到 20M）→ 网络有问题：丢包、限速、路由器性能不足
- 用 `-u` 可以测试 UDP 吞吐量和丢包率：`iperf3 -c <IP> -u -b 100M`（UDP 模式，目标 100Mbps）

## 33.6 优化方向——知道慢在哪，才能对症下药

根据上面的分析，不同瓶颈有不同优化策略：

| 瓶颈在哪 | 优化方向 | 具体手段 |
|---------|---------|---------|
| DNS 解析慢 | 减少 DNS 延迟 | 用更快 DNS（8.8.8.8/1.1.1.1）、DNS 预解析 |
| TCP 握手慢 | 减少 RTT 次数 | 连接复用（HTTP/2、Keep-Alive）、CDN 就近接入 |
| TLS 握手慢 | 减少 TLS 开销 | TLS 1.3（1-RTT）、会话复用、OCSP Stapling |
| TTFB 高 | 加速服务器处理 | 缓存、数据库优化、CDN 边缘计算 |
| 下载慢 | 减少传输量 / 增加带宽 | 压缩（gzip/brotli）、CDN、升级带宽 |
| 延迟高（跨地域） | 拉近物理距离 | CDN、边缘节点、专线 |

### 三条金律

1. **减少 RTT 次数**（CDN、连接复用、协议升级）
2. **减少传输量**（压缩、缓存、按需加载）
3. **复用连接**（Keep-Alive、HTTP/2 多路复用、连接池）

这三条覆盖了 80% 的网络性能优化场景。

💡 **想多一点：有时候"优化"就是别瞎动**

很多人的"优化"实际上是：
- 调整 TCP 参数 → 调错了反而更慢
- 关闭 IPv6 → 没用，反而可能影响某些 IPv6-only 服务
- 换 DNS → 换到了更慢的 DNS 服务器

**优化之前先测量**。用 `curl -w` 确认慢在哪个阶段，再用对应的优化手段。不测量就优化 ≈ 蒙着眼睛调收音机。

## 术语表

| 术语 | 解释 |
|------|------|
| **带宽（Bandwidth）** | 链路最大传输速率，单位 Mbps，由物理硬件决定 |
| **延迟（Latency）** | 数据包从源到目的的时间，单位 ms。RTT 是往返延迟 |
| **吞吐量（Throughput）** | 实际传输速率，受带宽、延迟、丢包、拥塞控制多重影响 |
| **TTFB** | Time To First Byte，从发请求到收到第一个字节的时间 |
| **BDP** | 带宽延迟积 = 带宽 × RTT，决定 TCP 窗口需求的"管容" |
| **iperf3** | 网络吞吐量测试工具，支持 TCP/UDP 模式 |
