## 36.1 正向代理 vs 反向代理

这两个词是面试高频题。一句话区分：

### 正向代理 — 你明确知道要通过代理访问外网

你（客户端）→ 代理服务器 → 目标网站。**代理代表你**。

**比喻**：你被公司内网关着，上不了外网。你让前台小妹帮你去外网上买东西——你知道你在通过她，目标网站看到的也是"前台小妹"的 IP，不是你。

**典型场景**：
- 公司内网上外网（HTTP 代理）
- 科学上网（Shadowsocks、V2Ray）
- 爬虫换 IP（用代理池）

### 反向代理 — 你完全不知道背后有多台服务器

你（客户端）→ 反向代理 → 后端服务器集群。**代理代表服务端**。

**比喻**：你去一家大公司前台问"我要找技术部"，前台（反向代理）根据你的需求把你领到 3 楼 A 区——你根本不知道技术部有 50 个人，也不知道今天谁值班。你只认"前台"这一个入口。

**典型场景**：
- Nginx 在前面，后面 10 台 Node.js/Python/Java 服务
- CDN 边缘节点也是反向代理（上一章刚学过）
- API 网关（下一章会讲）

### 对比图

```
正向代理：                              反向代理：
你 ──→ 代理 ──→ 百度                    你 ──→ Nginx ──→ 后端A
            百度看到代理的IP                          ──→ 后端B
            你不知道百度的真实IP？                    ──→ 后端C
            不，你知道百度IP，                 你只知道 Nginx 的IP，
            但百度不知道你的IP                你不知道背后有ABC
```

| | 正向代理（Forward Proxy） | 反向代理（Reverse Proxy） |
|---|---|---|
| 谁在用 | 客户端 | 服务端 |
| 隐藏谁 | 隐藏客户端 IP | 隐藏服务端 IP 和结构 |
| 客户端知道 | 知道自己在用代理 | 以为自己直接访问服务器 |
| 典型产品 | Shadowsocks、Squid | Nginx、HAProxy、Traefik |
| 使用场景 | 翻墙、内网上外网、爬虫 | 负载均衡、SSL 终结、缓存 |

## 36.2 反向代理的五种能力

反向代理不仅仅是一个"转发器"。它站在客户端和服务器之间，这个位置给了它"中间人"的天然优势：

### 1. 负载均衡

上章（Ch35）讲的五种算法，Nginx 反向代理全部支持。`upstream` 块定义后端池，`proxy_pass` 引用池名：

```nginx
upstream my_backend {
    # 轮询（默认）
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080;
}

server {
    listen 80;
    location / {
        proxy_pass http://my_backend;
    }
}
```

### 2. SSL 终结（SSL Termination）

反向代理替你处理 TLS 握手（回顾 Ch25）。用户到 Nginx 走 HTTPS，Nginx 到后端走 HTTP：

```
用户 ── HTTPS ──→ Nginx（TLS 在此终结）── HTTP ──→ 后端服务器
```

好处：
- 后端服务器不用装证书、不用做加解密（省 CPU）
- 证书集中管理在一台 Nginx 上，不用每台后端都配
- 配合 CDN 可以实现"边缘 SSL 终结"（Ch34 已提）

⚠️ 安全提示：Nginx 到后端如果走内网且物理安全可控，可以用 HTTP；如果是跨机房/公网，**必须**也走 HTTPS。

### 3. 静态资源缓存

Nginx 可以直接处理静态文件（HTML、CSS、JS、图片），不需要转发到后端：

```nginx
location /static/ {
    root /var/www;            # 直接读本地文件
    expires 30d;              # 浏览器缓存 30 天
}

location / {
    proxy_pass http://backend;  # 动态请求才转发
}
```

### 4. gzip 压缩

Nginx 在返回响应之前压缩内容，减小传输量：

```nginx
gzip on;
gzip_types text/plain text/css application/json application/javascript;
gzip_min_length 1000;   # 小于 1KB 不压缩（压了反而变大）
```

### 5. 请求路由

根据 URL 路径、域名、Header 等把请求路由到不同的后端服务：

```nginx
# 按域名路由
server {
    server_name api.example.com;
    location / { proxy_pass http://api_backend; }
}
server {
    server_name admin.example.com;
    location / { proxy_pass http://admin_backend; }
}

# 按路径路由
location /api/    { proxy_pass http://api_backend; }
location /images/ { proxy_pass http://image_backend; }
```

## 36.3 proxy_pass 详解——流量是怎么走的

`proxy_pass` 是 Nginx 反向代理最核心的指令。它的语法很简单：

```nginx
proxy_pass <协议>://<地址>;
```

### 一个完整的配置示例

```nginx
upstream app_servers {
    server 10.0.1.10:3000;
    server 10.0.1.11:3000;
}

server {
    listen 80;
    server_name www.mysite.com;

    location / {
        proxy_pass http://app_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

### 流量走向（一次完整请求）

```
① 用户浏览器：输入 http://www.mysite.com/api/users
      │
② DNS 解析（Ch20-21）：www.mysite.com → Nginx 的公网 IP
      │
③ TCP 三次握手（Ch15）：用户 ←→ Nginx
      │
④ TLS 握手（Ch25）：如果配了 HTTPS，在这里完成
      │
⑤ 用户发送 HTTP 请求：
     GET /api/users HTTP/1.1
     Host: www.mysite.com
      │
⑥ Nginx 解析请求：
   - 匹配到 server_name www.mysite.com
   - 匹配到 location /
   - 查 upstream app_servers，选一台后端（按负载均衡算法）
   - 构造新的 HTTP 请求发往后端
      │
⑦ Nginx → 后端（10.0.1.10:3000）：
     GET /api/users HTTP/1.1
     Host: www.mysite.com
     X-Real-IP: 客户端真实IP
     X-Forwarded-For: 客户端真实IP
      │
⑧ 后端处理，返回响应
      │
⑨ Nginx 收到后端响应 → 可选 gzip 压缩 → 返回给用户
      │
⑩ 用户收到响应
```

## 36.4 proxy_pass 末尾 `/` —— 最高频的坑

这是 Nginx 新手碰到最多的问题，也是面试最喜欢问的点。**`proxy_pass` 后面的 URI 是否带 `/`，决定了 Nginx 如何拼接路径。**

### 规则（只此一条，记住即可）

如果 `proxy_pass` 后面**只有主机名和端口，没有任何路径**（如 `http://backend`），Nginx 把 `location` 匹配到的完整 URI 原封不动转发过去。

如果 `proxy_pass` 后面**有路径**（哪怕只有一个 `/`，如 `http://backend/`），Nginx 会把 `location` 匹配到的部分"替换"成 `proxy_pass` 的路径部分再转发。

### ❌/✅ 示例对比

假设请求都是 `http://www.example.com/api/users/list`。

**示例一：`proxy_pass` 不带路径**

```nginx
location /api/ {
    proxy_pass http://backend;    # 注意：没有路径部分
}
```

转发出去的 URI：`/api/users/list`（完整保留）

**示例二：`proxy_pass` 带 `/`**

```nginx
location /api/ {
    proxy_pass http://backend/;   # 注意：有 /
}
```

转发出去的 URI：`/users/list`（`/api/` 被替换成了 `/`）

**示例三：`proxy_pass` 带自定义路径**

```nginx
location /api/ {
    proxy_pass http://backend/v2/;   # 替换成 /v2/
}
```

转发出去的 URI：`/v2/users/list`

### 更多对比

| 请求 URI | location | proxy_pass | 最终转发 URI | 说明 |
|----------|----------|-----------|-------------|------|
| `/api/users` | `/api/` | `http://backend` | `/api/users` | 无路径→完整保留 |
| `/api/users` | `/api/` | `http://backend/` | `/users` | `/api/` 替换为 `/` |
| `/api/users` | `/api/` | `http://backend/v2/` | `/v2/users` | `/api/` 替换为 `/v2/` |
| `/foo/bar` | `/foo/` | `http://backend` | `/foo/bar` | 无路径→完整保留 |
| `/foo/bar` | `/foo/` | `http://backend/` | `/bar` | `/foo/` 替换为 `/` |

❌ **常见错误**：

场景：你想把 `/api/` 请求转发给后端，路径不变。

```nginx
# 错误写法：
location /api/ {
    proxy_pass http://backend/;      # 末尾有 /
}
# 转发 URI = /users（后端收到的是 /users，404！）
```

✅ **正确写法**：

```nginx
# 路径不变的写法：
location /api/ {
    proxy_pass http://backend;       # 末尾没有 /
}
# 转发 URI = /api/users（后端收到完整的 /api/users，正确！）
```

💡 **想多一点：如何一劳永逸记住这个规则**

把 `proxy_pass` 后面的值想象成一个"替换指令"：

- `http://backend` → "不要替换，直接转发"（因为没给替换目标）
- `http://backend/` → "把 location 匹配的部分替换成 `/`"
- `http://backend/v2/` → "把 location 匹配的部分替换成 `/v2/`"

另一个记忆方法：看 `proxy_pass` 值中 `http://host` 后面有没有 `/xxx`，有就替换，没有就保留。

## 36.5 七层代理 vs 四层代理：proxy_pass vs stream

前面讲的 `proxy_pass` 工作在七层（HTTP 层）。Nginx 还可以做**四层代理**——用 `stream` 模块。

### proxy_pass（七层代理）

- 必须解析 HTTP 协议
- 可以看 URL、Header、Cookie
- 可以修改请求和响应
- 必须为 HTTP/HTTPS 协议

### stream 模块（四层代理）

这是 Nginx **特有的**一个模块，用于 TCP/UDP 四层代理。它不做 HTTP 解析，纯粹转发字节流。

```nginx
# stream 模块配置（在 http 块外面！）
stream {
    upstream mysql_servers {
        server 10.0.1.10:3306;
        server 10.0.1.11:3306;
    }

    server {
        listen 3306;                 # 监听 3306 端口
        proxy_pass mysql_servers;    # 转发 TCP 连接
        proxy_connect_timeout 5s;    # 连接超时
    }
}
```

**使用场景**：
- MySQL/Redis/MongoDB 等非 HTTP 协议的 TCP 代理
- SSH 代理
- 不想解析 HTTP 只想做纯四层转发（性能更高）

**为什么 stream 模块是 Nginx 特有概念**：因为 Nginx 最初只做 HTTP 七层代理（`http` 块），后来才加了 `stream` 块用于四层代理。HAProxy 则从一开始就同时支持 L4 和 L7，不需要区分"模块"。

### 对比

| | proxy_pass（七层） | stream（四层） |
|---|---|---|
| 配置位置 | `http` 块内 | `stream` 块内（顶层） |
| 协议 | HTTP/HTTPS | 任意 TCP/UDP |
| 能否看 URL | ✅ | ❌ |
| 能否加 Header | ✅ | ❌ |
| 性能 | 较低（需解析 HTTP） | 较高（纯转发） |
| SSL 终结 | 可以 | 可以（`proxy_ssl`） |

## 36.6 X-Forwarded-For：让后端知道"到底是谁"

当 Nginx 做反向代理时，后端服务器看到的连接来源 IP 是 Nginx 的 IP，不是用户的真实 IP。这意味着：

- 日志里全是一个 IP（Nginx 的内网 IP）
- 没法做基于 IP 的限流、黑名单
- 没法分析用户地域分布

### 解决方案：X-Forwarded-For

`X-Forwarded-For` 是一个 HTTP 请求头，Nginx 把用户真实 IP 写进去，再转发给后端：

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

- `$proxy_add_x_forwarded_for`：如果请求已经有 `X-Forwarded-For`（说明前面还有其他代理），就把当前客户端 IP **追加**在后面；如果没有，就新建这个头。

### 多级代理时的 X-Forwarded-For

```
用户(1.2.3.4) → CDN(5.6.7.8) → Nginx(10.0.0.1) → 后端

X-Forwarded-For 的演变：
CDN 收到请求时：            （没有这个头）
CDN 转发给 Nginx：          X-Forwarded-For: 1.2.3.4
Nginx 转发给后端：          X-Forwarded-For: 1.2.3.4, 5.6.7.8
                            或：1.2.3.4, 10.0.0.1（取决于中间还有几层）

后端的日志/代码读 X-Forwarded-For 的最左边一个 IP → 用户的真实 IP
```

### 相关 Header

| Header | 含义 | 谁设置 |
|--------|------|--------|
| `X-Forwarded-For` | 请求经过的代理链，逗号分隔的 IP 列表 | 每个代理追加自己的上一跳 IP |
| `X-Real-IP` | 单一值，用户真实 IP | Nginx 的 `$remote_addr` |
| `X-Forwarded-Proto` | 原始请求的协议（`http` 或 `https`） | 代理设置，后端据此判断是否 HTTPS |

```nginx
# 完整推荐配置
location / {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;     # http 或 https
}
```

## 术语表

| 术语 | 解释 |
|------|------|
| **正向代理（Forward Proxy）** | 代理代表客户端访问外部资源，隐藏客户端 IP |
| **反向代理（Reverse Proxy）** | 代理代表服务端接收请求并转发，隐藏服务端结构 |
| **SSL 终结（SSL Termination）** | 反向代理处理 TLS 解密，后端走明文 HTTP |
| **proxy_pass** | Nginx 反向代理核心指令，指定请求转发目标 |
| **upstream** | Nginx 中定义后端服务器组的配置块，配合 proxy_pass 使用 |
| **stream 模块** | Nginx 特有模块，实现四层 TCP/UDP 代理（不解包 HTTP） |
| **X-Forwarded-For** | HTTP 头，记录请求经过的代理链 IP 列表，用于透传真实客户端 IP |
| **X-Real-IP** | HTTP 头，单一值，通常是直连 Nginx 的客户端 IP |
| **X-Forwarded-Proto** | HTTP 头，原始请求的协议（http/https），后端据此判断是否安全连接 |
