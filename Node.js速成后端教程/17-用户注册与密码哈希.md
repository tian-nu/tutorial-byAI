### 步骤 2：为什么不能明文存密码——"数据库泄露 = 所有用户密码泄露"

想象一下：如果用户注册时，你把密码直接存进数据库：

```sql
-- ❌ 明文存密码
INSERT INTO users (username, email, password_hash) 
VALUES ('alice', 'alice@example.com', 'mypassword123');
```

**后果**：
1. 数据库管理员能直接看到所有用户的密码。
2. 如果数据库文件泄露（比如 `blog.db` 被传到 GitHub），攻击者拿到所有人的密码。
3. 很多人用同一个密码登录多个网站——你泄露了一个，等于泄露了全部。

> **餐厅比喻**：明文存密码就像把客人的信用卡号写在点菜单上——任何一个服务员、洗碗工、甚至路过的人都能看到。哈希就像把信用卡号用碎纸机碎掉——碎纸屑还在，但谁也拼不回原号。

**正确做法**：密码不存原文，存"指纹"（哈希值）。验证时，不比对原文，比对指纹。

---

### 步骤 3：哈希 vs 加密——"哈希不可逆，加密可解密"

这是初学者最容易混淆的概念之一：

| | 哈希（Hashing） | 加密（Encryption） |
|---|---|---|
| **可逆性** | ❌ 不可逆（单向） | ✅ 可逆（双向，有密钥就能解密） |
| **用途** | 存密码、校验文件完整性 | 保护传输中的数据（如 HTTPS） |
| **输出长度** | 固定（如 SHA-256 始终 256 位） | 与输入长度相关 |
| **类比** | **绞肉机**：肉进去变成肉馅，肉馅变不回肉 | **保险箱**：放进去锁上，有钥匙就能取出来 |
| **典型算法** | bcrypt, SHA-256, Argon2 | AES, RSA |

```
哈希（绞肉机）：
  "mypassword" → [bcrypt 哈希] → "$2b$10$7Q..."（一坨乱码）
  从 "$2b$10$7Q..." 推导出 "mypassword"？不可能。

加密（保险箱）：
  "mypassword" → [AES 加密 + 密钥] → "U2FsdGVkX1..."（密文）
  "U2FsdGVkX1..." → [AES 解密 + 密钥] → "mypassword"（恢复原文）
```

**验证密码时**：不是把哈希值"解密"回去比对，而是**把用户输入的密码再次哈希，比对两次哈希结果是否一致**。

### 步骤 4：bcrypt 的盐值（Salt）——"同样的密码，哈希结果不同"

如果只用哈希（如 SHA-256），有一个致命问题：

```javascript
// 两个用户都用密码 "123456"
SHA256("123456") → "8d969eef..."  // alice 的哈希
SHA256("123456") → "8d969eef..."  // bob 的哈希——完全一样！
```

**攻击者可以建彩虹表（Rainbow Table）**：提前算好常见密码的哈希值，做成字典。数据库泄露后，一查表就知道 `"8d969eef..."` 对应 `"123456"`。

**bcrypt 的解决方案：盐值（Salt）**

bcrypt 在哈希时自动加一个随机字符串（盐值），每个人的盐值不同：

```javascript
bcrypt.hash("123456", 10) → "$2b$10$随机盐值22字符.哈希值31字符"
//                          ^^^^^^^^ 盐值嵌入在结果里
```

- alice 的盐值是 `abc123...`，哈希结果是 `$2b$10$abc123...XXX`
- bob 的盐值是 `xyz789...`，哈希结果是 `$2b$10$xyz789...YYY`

**同样的密码，哈希结果完全不同**——彩虹表彻底失效。

> **餐厅比喻**：盐值就像在肉馅里混入不同的调料——alice 的肉馅放了辣椒，bob 的放了花椒。即使他们用同样的肉（密码），绞出来的肉馅（哈希）也完全不同。攻击者想通过"肉馅字典"反查原肉——没用，因为调料配方千变万化。

**`bcrypt.hash(password, 10)` 中的 `10` 是什么？**

`10` 是**盐值轮数**（cost factor / salt rounds）。轮数越大，哈希越慢，攻击者暴力破解的成本越高。但轮数太大，登录时验证也慢——10 是平衡点（约 50-100ms），12 更适合生产环境。

```
轮数 8：  约 10ms  （太快，攻击者可以快速试密码）
轮数 10： 约 50ms  （推荐，平衡安全与性能）
轮数 12： 约 200ms （更安全，但登录稍慢）
轮数 14： 约 800ms （用户可能等得不耐烦）
```

### 步骤 5：创建 routes/auth.js——注册接口

创建 `routes/auth.js`：

```javascript
const express = require('express');
const router = express.Router();
const bcrypt = require('bcryptjs');       // 如果安装的是 bcrypt，改为 require('bcrypt')
const { db } = require('../database/db');
const AppError = require('../utils/AppError');

// ========== 认证接口 ==========

// POST /api/auth/register — 用户注册
router.post('/register', async (req, res) => {
    const { username, email, password } = req.body;

    // 1. 验证必填字段
    if (!username || !email || !password) {
        throw new AppError('用户名、邮箱和密码为必填字段', 400);
    }

    // 2. 验证密码长度
    if (password.length < 6) {
        throw new AppError('密码至少需要 6 位', 400);
    }

    // 3. 验证邮箱格式（简单正则）
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    if (!emailRegex.test(email)) {
        throw new AppError('邮箱格式不正确', 400);
    }

    // 4. 检查用户名是否已存在
    const existingUser = db.prepare('SELECT id FROM users WHERE username = ?').get(username);
    if (existingUser) {
        throw new AppError('用户名已被注册', 409);
    }

    // 5. 检查邮箱是否已存在
    const existingEmail = db.prepare('SELECT id FROM users WHERE email = ?').get(email);
    if (existingEmail) {
        throw new AppError('邮箱已被注册', 409);
    }

    // 6. 哈希密码
    const saltRounds = 10;
    const password_hash = await bcrypt.hash(password, saltRounds);

    // 7. 插入数据库
    const now = new Date().toISOString();
    const insertUser = db.prepare(`
        INSERT INTO users (username, email, password_hash, created_at)
        VALUES (?, ?, ?, ?)
    `);

    const result = insertUser.run(username, email, password_hash, now);

    // 8. 返回新用户信息（不返回 password_hash！）
    const newUser = db.prepare(
        'SELECT id, username, email, created_at FROM users WHERE id = ?'
    ).get(result.lastInsertRowid);

    res.status(201).json({
        success: true,
        data: newUser
    });
});

module.exports = router;
```

**关键点解析**：

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| 1-3 | 验证输入 | 永远不信任客户端传来的数据——先验证再处理 |
| 4-5 | 检查唯一性 | 用户名和邮箱必须唯一，否则登录时不知道哪个是哪个 |
| 6 | `await bcrypt.hash()` | **异步操作**，必须 `await`，否则拿到的是 Promise 对象 |
| 7 | 插入数据库 | 存的是 `password_hash`（哈希值），不是原始密码 |
| 8 | 返回用户信息 | 只返回 `id, username, email, created_at`——**绝不返回 `password_hash`** |

> 🔥 **魔鬼细节**：`bcrypt.hash()` 是异步的（返回 Promise），必须用 `await`。如果你忘了 `await`，`password_hash` 会是一个 Promise 对象，存进数据库后永远无法登录。同时，`router.post('/register', async (req, res) => ...)` 的处理函数要加 `async`。

> 🔥 **魔鬼细节**：接口响应中**绝对不要返回 `password_hash`**。即使它是哈希值，不是明文，也不应该暴露给客户端。SELECT 时明确列出需要的列（`SELECT id, username, email, created_at`），而不是 `SELECT *`。

> 🔥 **魔鬼细节**：验证邮箱格式用简单的正则 `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` 就够了。**不要用网上那些几百字符的"完美邮箱正则"**——它们过于复杂，且可能拒绝合法的邮箱地址（如带 `+` 号的 Gmail 别名）。简单的正则能拦住明显的错误输入（如 `"notanemail"`），剩下的——用户如果填错邮箱，收不到验证邮件，自然会改。

#### 7.1 正常注册

**预期响应**（201 Created）：

```json
{
  "success": true,
  "data": {
    "id": 3,
    "username": "charlie",
    "email": "charlie@example.com",
    "created_at": "2026-06-12T..."
  }
}
```

注意：响应里**没有** `password_hash` 字段。

#### 7.2 验证密码是哈希存储的

在终端中查看数据库：

```bash
node -e "const {db}=require('./database/db');console.log(db.prepare('SELECT id, username, password_hash FROM users').all())"
```

你应该看到类似：

```
[
  { id: 1, username: 'alice', password_hash: 'hash_placeholder' },
  { id: 2, username: 'bob', password_hash: 'hash_placeholder' },
  { id: 3, username: 'charlie', password_hash: '$2b$10$...' }
]
```

charlie 的 `password_hash` 是一长串 `$2b$10$...` 开头的乱码——**这才是正确的**。alice 和 bob 的 `hash_placeholder` 是 seed 脚本塞的假数据，后面会淘汰。

#### 7.3 测试各种错误场景

| 测试 | Body | 预期状态码 | 预期错误信息 |
|------|------|-----------|-------------|
| 缺少密码 | `{"username":"test","email":"test@test.com"}` | 400 | 用户名、邮箱和密码为必填字段 |
| 密码太短 | `{"username":"test","email":"test@test.com","password":"123"}` | 400 | 密码至少需要 6 位 |
| 邮箱格式错误 | `{"username":"test","email":"notanemail","password":"123456"}` | 400 | 邮箱格式不正确 |
| 用户名重复 | `{"username":"charlie","email":"c2@test.com","password":"123456"}` | 409 | 用户名已被注册 |
| 邮箱重复 | `{"username":"charlie2","email":"charlie@example.com","password":"123456"}` | 409 | 邮箱已被注册 |

> 409 Conflict 是 HTTP 标准中表示"资源冲突"的状态码——用户名或邮箱已存在，与你要创建的新资源冲突。

### 🤔 想多一点：为什么 seed 脚本里的密码是 `hash_placeholder`？

回顾第 14 章的 `database/seed.js`：

```javascript
{ username: 'alice', email: 'alice@example.com', password_hash: 'hash_placeholder' }
```

`hash_placeholder` 是一个**占位符**——因为当时还没引入 bcrypt，无法生成真正的哈希值。现在有了注册接口，alice 和 bob 应该通过注册接口重新创建（或者用 bcrypt 重新生成哈希值更新 seed 脚本）。但这不是必须的——下一章登录时，`bcrypt.compare(密码, 'hash_placeholder')` 会失败，你会知道原因。

### ❌ 常见错误 → ✅ 解决方案

| 错误信息 / 现象 | 原因 | 解决 |
|-----------------|------|------|
| `Cannot find module 'bcrypt'` | bcrypt 编译失败，模块未安装 | 改用 `npm install bcryptjs`，代码中 `require('bcryptjs')` |
| `bcrypt.hash is not a function` | 忘了 `require('bcryptjs')` 或拼写错误 | 确认文件顶部有 `const bcrypt = require('bcryptjs')` |
| 注册成功但数据库中 `password_hash` 是 `[object Promise]` | 忘了 `await`——`bcrypt.hash()` 返回 Promise | 改为 `const password_hash = await bcrypt.hash(password, 10)` |
| `Cannot read properties of undefined` | 注册接口返回 500，忘了 `async` | 处理函数改为 `async (req, res) => { ... }` |
| `SQLITE_CONSTRAINT: UNIQUE constraint failed` | 用户名或邮箱重复，但错误处理没生效 | 在 `INSERT` 之前先检查是否存在（步骤 4-5） |
| 注册成功但响应里包含 `password_hash` | 用了 `SELECT *` | 改为 `SELECT id, username, email, created_at` 明确列出列 |
| `UNIQUE constraint failed: users.email` 但没有前置检查 | 数据库报错后才知重复，用户体验差 | 在 INSERT 前先用 SELECT 检查邮箱唯一性，返回友好的 409 错误 |

| 密码哈希 | 把密码变成不可逆的"指纹"，存指纹不存原文 |
| 哈希 vs 加密 | 哈希是绞肉机（不可逆），加密是保险箱（有钥匙能开） |
| 盐值（Salt） | 随机字符串，让同样的密码产生不同的哈希，防彩虹表 |
| 彩虹表 | 提前算好的"常见密码 → 哈希值"字典，盐值让它彻底失效 |
| 盐值轮数 | `bcrypt.hash(password, 10)` 中的 10，越大越慢越安全 |
| `bcryptjs` 备选 | 纯 JS 实现，零编译问题，API 与 bcrypt 完全相同 |
| 409 Conflict | 资源冲突——用户名或邮箱已被占用 |
| 接口不返回密码哈希 | 即使哈希值不是明文，也不该暴露给客户端 |

## 八、已知坑点与禁止事项

1. **bcrypt 编译失败**：Windows 用户安装 `bcrypt` 可能遇到 `node-gyp` 错误。**解决方案**：改用 `bcryptjs`（`npm install bcryptjs`），API 完全一样，只需改 `require` 路径。

2. **`bcrypt.hash()` 是异步的**：必须用 `await`，否则 `password_hash` 是 Promise 对象，存进数据库后永远无法登录。

3. **接口响应中绝不包含 `password_hash`**：用 `SELECT id, username, email, created_at` 而不是 `SELECT *`。

4. **邮箱正则不要过度复杂**：`/^[^\s@]+@[^\s@]+\.[^\s@]+$/` 足够过滤明显的错误输入。复杂的"完美正则"可能拒绝合法邮箱。

5. **先检查再插入**：在 INSERT 之前用 SELECT 检查用户名和邮箱唯一性，返回友好的 409 错误，而不是让数据库抛出 `UNIQUE constraint failed`。

6. **seed 脚本中的 `password_hash: 'hash_placeholder'` 是假数据**：这些用户无法通过登录接口验证。下一章会解决这个问题。
