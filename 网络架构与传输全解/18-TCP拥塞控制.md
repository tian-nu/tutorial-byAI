# 18 — TCP 拥塞控制：网络堵车怎么办

## 学习目标
- 区分流量控制（rwnd）和拥塞控制（cwnd）
- 理解慢启动、拥塞避免、快速重传、快速恢复四个阶段
- 用具体数字例子比较 Tahoe 和 Reno 在丢包后的不同行为
- 知道 BBR 是什么、和传统算法有什么不同

---

## 18.1 流量控制 vs 拥塞控制：两个完全不同的"刹车"

第 16 章讲的滑动窗口解决的是**流量控制**——接收方管的事。接收方通过窗口字段告诉发送方："我的缓冲区还能装这么多，你别发快了撑爆我。"

**拥塞控制**是发送方自己管的事——发送方不关心接收方能装多少，而是担心**网络中间的路由器能处理多少**。就像你开车，限速 120km/h 是你车（接收方）能跑多快，但前方堵车（网络拥塞）才是你真正开不动的理由。

| 对比维度 | 流量控制 | 拥塞控制 |
|----------|----------|----------|
| 谁决定 | 接收方通告（rwnd） | 发送方探测（cwnd） |
| 约束什么 | 接收方缓冲区 | 网络链路容量 |
| 所在层 | 传输层（端到端） | 传输层（端到网络） |
| 依据 | TCP 头部窗口字段 | 丢包 / RTT 变化 |

**发送方实际能发送的数据量 = min(rwnd, cwnd)**。两个窗口取小值。大多数情况下瓶颈是 cwnd（网络），而不是 rwnd（接收方缓冲区）。

---

## 18.2 拥塞窗口（cwnd）：发送方的"猜想"

**cwnd（Congestion Window，拥塞窗口）** 是发送方维护的一个变量，表示"我估计网络现在能承受多少数据在路上"。

- cwnd 初始很小（通常 1~10 MSS）
- 发送方不断试探：没丢包就慢慢加大，丢包就缩小
- cwnd 的大小决定了"有多少个报文段可以同时在路上"

```
发送方视角：

已经发送并确认    已发送未确认(≤cwnd)    还不能发
|<---- ✓ ---->|<---- ≤ cwnd ---->|<---------------|
[✓✓✓✓✓✓✓✓✓✓✓|■■■■■■■■■■■■■■■■■■■■|.................]
              |<-- cwnd 个报文段 -->|
```

TCP 用了几十年时间逐步演化出四种拥塞控制算法阶段，下面逐一讲解。

---

## 18.3 慢启动：一开始慢，但加速很快

TCP 刚开始传输时，不知道网络能承受多大数据量。如果一上来就以最大速度发，可能瞬间把网络塞死。

**慢启动（Slow Start）** 的策略是：从很小的 cwnd 开始，每收到一个 ACK，cwnd 就略微增大。但因为 ACK 是批量回来的，cwnd 实际上**每个 RTT 翻一倍**（指数增长）。

```
慢启动的增长过程（假设 MSS=1460 字节）：

RTT 1: cwnd = 1 MSS     = 1.46 KB    发送 1 段
RTT 2: cwnd = 2 MSS     = 2.92 KB    发送 2 段
RTT 3: cwnd = 4 MSS     = 5.84 KB    发送 4 段
RTT 4: cwnd = 8 MSS     = 11.68 KB   发送 8 段
RTT 5: cwnd = 16 MSS    = 23.36 KB   发送 16 段
RTT 6: cwnd = 32 MSS    = 46.72 KB   发送 32 段
```

"慢启动"这个名字其实有点误导——它起步慢（1 MSS），但增速是指数级的，很快就快起来了。10 个 RTT 后 cwnd 就能到 1024 MSS ≈ 1.5 MB，已经很快了。

---

## 18.4 ssthresh 与拥塞避免：从"踩油门"到"匀速"

一直指数增长下去肯定会超出网络容量。所以 TCP 设定了一个阈值 **ssthresh（Slow Start Threshold，慢启动阈值）**：

- 当 cwnd < ssthresh → **慢启动**（指数增长）
- 当 cwnd ≥ ssthresh → **拥塞避免**（线性增长，每个 RTT +1 MSS）

拥塞避免的思路很简单：快到上限了，别猛踩油门了，慢慢试探。

```
ssthresh = 8 MSS

RTT 1~3: 慢启动，1→2→4→8 MSS
RTT 4:   cwnd = 8 ≥ ssthresh → 进入拥塞避免
RTT 4:   cwnd = 9 MSS    (线性: 8+1)
RTT 5:   cwnd = 10 MSS   (线性: 9+1)
RTT 6:   cwnd = 11 MSS   (线性: 10+1)
...
```

---

## 18.5 丢包之后怎么办？Tahoe vs Reno（具体数字演示）

现在来到最关键的部分：当 cwnd 已经涨得很大时，突然丢包了，cwnd 怎么调整？这是 TCP 拥塞控制历史上最重要的分水岭。

**设定具体场景**：假设在丢包那一刻，cwnd = 16 MSS，ssthresh = 8 MSS。

### 18.5.1 Tahoe 算法（早期 TCP，保守派）

Tahoe 遇到丢包的处理非常"一刀切"：

```
丢包时：  cwnd = 16, ssthresh = 8

步骤1：ssthresh = max(未确认数据量/2, 2×MSS) ≈ cwnd/2 = 8
步骤2：cwnd = 1 MSS
步骤3：重新进入慢启动

丢包后：
RTT 1: cwnd = 1 MSS
RTT 2: cwnd = 2 MSS
RTT 3: cwnd = 4 MSS
RTT 4: cwnd = 8 MSS  ← 回到 ssthresh，进入拥塞避免
RTT 5: cwnd = 9 MSS
RTT 6: cwnd = 10 MSS
...
```

Tahoe 的问题：**每丢一次包都要从 1 重新慢启动**，对于偶尔丢包（不是真正拥塞）的情况太"粗暴"了，造成了不必要的性能损失。

### 18.5.2 Reno 算法（改进版，实用派）

Reno 引入了两个关键机制：**快速重传**和**快速恢复**。

**快速重传**：发送方收到 **3 个重复 ACK**（dup ACK）时，不等超时，立即重传那个丢失的包。

```
为什么是 3 个？
假设 seq=1000 的包丢了，后面的 seq=2000, 3000, 4000 都到了：
接收方对每个乱序到达的包都回复 ack=1000（"我还在等 1000"）

发送方收到：
ack=1000 (首次)
ack=1000 (第1个dup) ← seq=2000 到了
ack=1000 (第2个dup) ← seq=3000 到了
ack=1000 (第3个dup) ← seq=4000 到了 → 触发快速重传！

不等超时，立即重传 seq=1000！
```

**快速恢复**：收到 3 个 dup ACK 后，不把 cwnd 砍到 1（不进入慢启动），而是：

```
丢包时：  cwnd = 16, ssthresh = 8
（通过 3 dup ACK 检测到丢包，不是超时）

步骤1：ssthresh = cwnd / 2 = 8
步骤2：cwnd = ssthresh = 8  ← 不是归 1！
步骤3：cwnd = 8 + 3×MSS = 11（每收一个 dup ACK +1）
步骤4：收到新 ACK 后，cwnd = ssthresh = 8
步骤5：进入拥塞避免，线性增长
       RTT 1: cwnd = 9
       RTT 2: cwnd = 10
       ...
```

Tahoe vs Reno 对比（同场景：cwnd=16, ssthresh=8, 丢包）：

```
Tahoe:  cwnd 16 → 1 → 2 → 4 → 8 → 9 → 10 ...  (4个RTT回到8)
Reno:   cwnd 16 → 8 → 9 → 10 → ...               (1个RTT就恢复了)
```

Reno 聪明在：如果能收到 3 个 dup ACK，说明后面的包还在到达——**网络没有完全堵死**，只是丢了一个包。所以不必"从头来过"，直接把窗口减半就够了。

❌ **常见错误**：认为"丢包就一定触发慢启动"。只有当丢包是通过**超时（RTO）**检测到的，才会进入慢启动（cwnd=1）。如果丢包是通过**3 dup ACK（快速重传）**检测到的，Reno 会进入快速恢复，cwnd 减半但不归 1。

## 18.6 BBR：不看丢包，看带宽

Tahoe 和 Reno 都属于**基于丢包的拥塞控制**——它们的核心假设是"丢包 = 网络拥塞"。这个假设在 1980 年代是对的（路由器缓冲区小，一拥塞就丢包），但在现代网络中出了问题：

- 无线网络：丢包可能只是信号干扰，不是网络拥塞
- 大缓冲区（Bufferbloat）：缓冲区太大导致排队延迟飙升，但一直不丢包

**BBR（Bottleneck Bandwidth and Round-trip propagation time）** 是 Google 在 2016 年提出的全新算法。它不看丢包，而是**持续测量瓶颈带宽和最小 RTT**，让发送速率始终保持在"管道刚好装满但不满溢"的最佳点。

BBR 的优势：
- 在高延迟、有损网络（如跨国专线、移动网络）中比 CUBIC（Reno 的后继者）快数倍
- 不因偶然丢包而降低速度

如何在 Linux 上开启 BBR（需要 Linux 4.9+）：

```bash
# 检查内核版本
uname -r

# 编辑 /etc/sysctl.conf，添加：
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr

# 生效
sudo sysctl -p

# 验证
sysctl net.ipv4.tcp_congestion_control
# 输出：net.ipv4.tcp_congestion_control = bbr
```

> 💡 **想多一点**：BBR 的核心理念是"不要让缓冲区填满"。传统算法（Reno/CUBIC）的逻辑是：往网络里灌水，直到水溢出来（丢包），才知道灌满了。BBR 则是：不断测量水管的宽度（带宽）和长度（RTT），算出水管容积，然后精确地保持水位在满而不溢的状态。这是控制论中"开环控制"的思路，比"反馈控制"更稳定。

## 18.7 整个拥塞控制的"大图景"

把上面所有阶段串起来，一个 TCP 连接从建立到稳定传输的过程：

```
阶段1：慢启动
  cwnd 从 1 MSS 指数增长（每个 RTT ×2）
  直到 cwnd ≥ ssthresh 或丢包

阶段2：拥塞避免
  cwnd 线性增长（每个 RTT +1 MSS）
  直到丢包

阶段3：丢包处理
  超时丢包 → 慢启动（cwnd=1）
  3 dup ACK → 快速恢复（cwnd 减半，不进慢启动）

阶段4：回到拥塞避免
  继续线性增长
```

这也解释了你在生活中观察到的现象：**下载速度为什么是一点点变快的？** 因为 TCP 从慢启动开始，逐步探测网络容量，找到平衡点。

## 18.8 小结

| 概念 | 要点 |
|------|------|
| 流量控制 vs 拥塞控制 | 流控由接收方 rwnd 决定，拥塞控制由发送方 cwnd 探测网络 |
| 实际发送窗口 | = min(rwnd, cwnd) |
| 慢启动 | cwnd 从 1 MSS 指数增长（每个 RTT ×2），直到达到 ssthresh |
| 拥塞避免 | cwnd ≥ ssthresh 后线性增长（每个 RTT +1 MSS） |
| Tahoe 丢包处理 | 超时/3 dup ACK：ssthresh=cwnd/2, cwnd=1，重新慢启动 |
| Reno 丢包处理 | 超时→慢启动；3 dup ACK→快速恢复（cwnd=ssthresh=cwnd/2） |
| 快速重传 | 收到 3 个 dup ACK 立即重传，不等超时 |
| BBR | Google 算法，基于带宽和 RTT 而非丢包，Linux 4.9+ 支持 |

## 术语表

| 术语 | 解释 |
|------|------|
| **cwnd（Congestion Window）** | 拥塞窗口，发送方根据网络状况动态调整的"在途数据上限" |
| **ssthresh（Slow Start Threshold）** | 慢启动阈值，cwnd 超过此值后从指数增长切换为线性增长 |
| **慢启动（Slow Start）** | cwnd 从 1 MSS 开始指数增长（每个 RTT ×2）的阶段 |
| **拥塞避免（Congestion Avoidance）** | cwnd ≥ ssthresh 后线性增长（每个 RTT +1 MSS）的阶段 |
| **快速重传（Fast Retransmit）** | 收到 3 个重复 ACK 立即重传丢失的报文段，不等超时 |
| **快速恢复（Fast Recovery）** | Reno 算法中通过 3 dup ACK 检测丢包后的处理：cwnd 减半但不归 1 |
| **BBR** | Google 提出的拥塞控制算法，基于瓶颈带宽和 RTT 而非丢包信号 |
| **dup ACK** | 重复确认，接收方对乱序到达数据的响应，连续 3 个触发快速重传 |
| **Bufferbloat** | 路由器缓冲区过大导致高延迟而不丢包的现象 |

## 验证方法

用文字描述以下场景中 cwnd 的变化过程（假设 MSS=1 简化计算，cwnd 以 MSS 为单位）：

> cwnd=16，ssthresh=8，发生丢包。分别描述 Tahoe 和 Reno 的处理方式，从丢包时刻起到 cwnd 恢复到 10，各需要多少个 RTT？

答案：
- **Tahoe**：丢包→cwnd=1→2→4→8→9→10（共 5 个 RTT）
- **Reno（3 dup ACK）**：丢包→cwnd=8→9→10（共 2 个 RTT）
