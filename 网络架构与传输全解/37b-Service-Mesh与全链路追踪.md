- 知道 mTLS 是什么，解决什么问题
- 用收费站比喻理解全链路追踪的 TraceID + SpanID 机制

上一章（Ch37a）你学到了：API 网关管南北流量（进门），那东西流量（楼内服务间互相调用）谁管？

你要是不管，服务间调用就是"裸奔"——没有重试、没有超时控制、没有加密、没有链路追踪，"订单服务调用用户服务超时了？不好意思，谁也不知道，除非用户投诉。"

**Service Mesh 就是管这件事的。**

## 37b.1 为什么需要 Service Mesh

### 微服务的"内政"问题

回顾 Ch37a 的架构图——订单服务调用用户服务、支付服务调用订单服务……每个服务都要处理：

- **重试**：调用失败了，重试几次？间隔多久？
- **超时**：等多久没回应就放弃？
- **熔断**：如果用户服务挂了，直接快速失败，不浪费时间等超时
- **负载均衡**：用户服务有 3 个实例，选哪个？
- **安全**：服务间通信要不要加密？
- **可观测性**：这次调用花了多少毫秒？成功还是失败？

这些是"服务治理"的范畴。传统做法是把这些逻辑写成 SDK/库，嵌在业务代码里：

```
❌ 老方案（代码侵入式）：
订单服务代码里混杂着：
  - 业务逻辑：创建订单
  - 重试逻辑：如果用户服务返回500，重试3次
  - 超时逻辑：等500ms没回应就放弃
  - 日志逻辑：记录调用耗时、状态码

业务代码和治理代码耦合在一起！
```

问题：
- 每种语言都要写一遍这些逻辑（Java 一套、Go 一套、Python 一套）
- SDK 版本升级 → 所有服务重新部署
- 业务开发要同时理解治理代码，心智负担重

### Service Mesh 的方案：把治理逻辑从代码里拆出来

**Service Mesh**（服务网格）的核心思想：**治理逻辑不放在应用代码里，而是放在应用旁边的一个独立代理进程中。**

```
✅ 新方案（Sidecar 模式）：
┌──────────────┐        ┌──────────────┐
│  订单服务      │        │  用户服务      │
│  (只有业务逻辑) │        │  (只有业务逻辑) │
│              │        │              │
│ 订单服务想调   │        │              │
│ 用户服务 →    │        │              │
└──────┬───────┘        └──────┬───────┘
       │ 127.0.0.1:15001      │ 127.0.0.1:15001
       ↓                       ↓
┌──────────────┐        ┌──────────────┐
│ Envoy Sidecar│ ←mTLS→ │ Envoy Sidecar│  ← 所有治理逻辑在这里
│ (代理)        │        │ (代理)        │
└──────────────┘        └──────────────┘
```

这个模式叫 **Sidecar（边车）**——就像摩托车的边斗，挂在主服务旁边，伴随主服务一起运行。

## 37b.2 Sidecar 模式详解

### 比喻

想象你是一个大公司的员工（微服务），你的工作就是写代码（业务逻辑）。但是：
- 发邮件？找秘书
- 安排会议室？找秘书
- 订机票？找秘书
- 对接其他部门？还是找秘书

**秘书（Sidecar）**就是跟你绑定的——你到哪他到哪，帮你处理所有"非业务"的杂事。其他部门的同事不直接找你，先找你的秘书，你的秘书再把重要信息转给你。

### 技术实现

在 Kubernetes 中，一个 Pod 里可以跑多个容器。微服务就是主容器，Sidecar 代理（通常是 **Envoy**）是辅助容器：

```
┌─────────── Pod ───────────┐
│                           │
│  ┌─────────┐  ┌─────────┐ │
│  │ 订单服务  │  │  Envoy  │ │
│  │ (业务)   │←→│(Sidecar)│ │
│  │ :8080   │  │ :15001  │ │
│  └─────────┘  └────┬────┘ │
│                    │      │
└────────────────────┼──────┘
                     │ 所有进出流量
                     ↓
                Pod 网络
```

工作流程：
1. 订单服务的业务代码不直接调"用户服务"的 IP，而是调 `127.0.0.1:15001`（本地 Envoy）
2. 本地 Envoy 负责：选实例（负载均衡）、加密（mTLS）、重试、超时、记录日志
3. 目标服务的 Envoy 收到请求，解密、转发给业务容器

**业务代码完全不需要知道 Sidecar 的存在**——它以为自己就在调一个普通的 HTTP 服务。

## 37b.3 Istio（控制面）+ Envoy（数据面）

Service Mesh 有两个层面：

### 数据面（Data Plane）—— Envoy

**Envoy** 是每个服务旁边的 Sidecar 代理。它做"体力活"：
- 转发流量
- TLS 加解密
- 收集指标（请求数、延迟、成功率）
- 执行重试/超时/熔断策略

每一个微服务都有一个 Envoy 实例，整个集群可能有几百上千个 Envoy。

### 控制面（Control Plane）—— Istio

**Istio** 是管理所有 Envoy 的"大脑"。它做"脑力活"：
- 向所有 Envoy 下发配置（路由规则、重试策略、安全设置）
- 收集所有 Envoy 上报的监控数据
- 管理证书（mTLS 所需的密钥和证书）

```
┌──────────── Istio 控制面 ────────────┐
│                                      │
│  Pilot（流量管理）  Citadel（安全管理）  │
│  Galley（配置管理）  Mixer（遥测）      │
│                                      │
└──┬──────────┬──────────┬─────────────┘
   │ 下发配置  │ 下发配置  │ 下发配置
   ↓          ↓          ↓
┌──────┐   ┌──────┐   ┌──────┐
│Envoy │   │Envoy │   │Envoy │   ← 数据面（Sidecar）
│服务A  │   │服务B  │   │服务C  │
└──────┘   └──────┘   └──────┘
```

**比喻**：Envoy 是每个房间配的管家（体力活，跑腿），Istio 是管家总管的办公室（脑力活，发号施令）。

💡 **想多一点：为什么不用 Istio 直接处理流量，还要 Envoy？**

分层架构的核心好处是**解耦**：
- Envoy（数据面）可以换：不用 Envoy，可以用 Linkerd-proxy、NGINX Mesh 等
- Istio（控制面）可以换：不用 Istio，可以用 Linkerd、Consul Connect 等
- 控制面挂了不影响数据面：Envoy 缓存了最后一次配置，Istio 宕机期间流量照常转发

## 37b.4 mTLS：服务间通信自动加密

### 什么是 mTLS

普通 TLS（Ch25）：客户端验证服务器身份（服务器出示证书），客户端可选地出示证书。

**mTLS**（Mutual TLS，双向 TLS）：**客户端和服务器互相验证身份**——双方都要出示证书。

```
普通 TLS：                     mTLS：
你验证"这家银行是真的"           你验证"这家银行是真的"
                              银行也验证"你真的是这个账户的持有人"
单向信任                        双向信任
```

### 为什么微服务需要 mTLS

在微服务集群中：
- 订单服务调用用户服务 → 怎么知道对面真的是"用户服务"而不是一个冒充的恶意服务？
- 如果攻击者在集群内部放置了一个假的服务，普通 HTTP 调用根本无法识别

mTLS 确保：**你说的"我是用户服务"必须用证书证明。**

### Service Mesh 如何简化 mTLS

没有 Service Mesh 时，你要给每个服务签发证书、配置 TLS、管理证书过期和轮换——这是运维噩梦。

有了 Service Mesh：
1. Istio 的 Citadel 组件自动为每个 Sidecar 签发证书
2. Sidecar 之间的通信自动升级为 mTLS
3. 证书自动轮换（到期前自动换新）
4. 业务代码一行都不用改——Sidecar 透明处理

## 37b.5 全链路追踪：TraceID + SpanID

### 问题

一个用户请求经过：API 网关 → 订单服务 → 用户服务 → 库存服务 → 支付服务 → 通知服务

如果这个请求失败了（返回 500），你怎么知道是哪个环节出的问题？一个个查日志？等你查到，用户已经跑了。

### 核心机制：TraceID 和 SpanID

**收费站比喻**：

你开车从北京到上海，一路上经过多个收费站：
- 你出发时拿到一个"行程编号"（**TraceID**）——全程唯一，记录你这一趟的全部行程
- 每经过一个收费站，记录一段"路段编号"（**SpanID**）——北京站、济南站、南京站、上海站
- 每个收费站记录：进入时间、离开时间、收费金额（耗时）
- 最后把所有收费站的记录串起来——完整的"北京→上海"行程单

**TraceID**：一次完整请求的全局唯一标识，贯穿所有服务。（全程路线的过路费记录）

**SpanID**：一次请求在每个服务中的处理片段标识。每个 Span 有独立的 SpanID，指向父 SpanID。（经过的每个收费站）

```
TraceID: abc-123 （全程唯一，贯穿所有服务）

网关（SpanID: 001, 父SpanID: 无）        ← 起点
  耗时: 200ms
  │
  ├─→ 订单服务（SpanID: 002, 父SpanID: 001）
  │     耗时: 80ms
  │     │
  │     ├─→ 用户服务（SpanID: 003, 父SpanID: 002）
  │     │     耗时: 30ms ← 慢？正常？
  │     │
  │     └─→ 库存服务（SpanID: 004, 父SpanID: 002）
  │           耗时: 490ms ← ❌ 问题在这！
  │
  └─→ 通知服务（SpanID: 005, 父SpanID: 001）
        耗时: 5ms
```

通过这个调用树，你一眼就能看到：**库存服务花了 490ms**，是性能瓶颈。

### 技术实现

全链路追踪通常需要：
1. **每个服务**在收到请求时生成/传递 TraceID，在处理时创建 Span
2. **Sidecar（Envoy）**自动注入和传播这些追踪 Header（如 `x-request-id`、`x-b3-traceid`、`x-b3-spanid`）
3. **收集器**（如 Jaeger、Zipkin）收集所有服务的 Span 数据
4. **可视化界面**展示完整调用链

有了 Service Mesh，Sidecar 自动做追踪注入——业务代码不需要自己实现追踪逻辑。

## 37b.6 API 网关 + Service Mesh 的分工（回顾）

回到 Ch37a 的结论：网关和 Mesh 是互补的，不是替代的。

```
                        互联网
                          │
                   ┌──────┴──────┐
                   │  API 网关    │  ← 南北：认证、限流、协议转换
                   │  (Kong等)    │     外部用户只看到这一层
                   └──────┬──────┘
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   ┌────┴────┐       ┌────┴────┐       ┌────┴────┐
   │ Envoy   │ ←mTLS→│ Envoy   │ ←mTLS→│ Envoy   │  ← 东西：加密、重试、
   │ 服务A    │       │ 服务B    │       │ 服务C    │     追踪、超时控制
   └─────────┘       └─────────┘       └─────────┘
        │                 │                 │
   ┌────┴────┐       ┌────┴────┐       ┌────┴────┐
   │  Istio  │       │  Istio  │       │  Istio  │  ← 控制面下发配置
   │ 控制面   │       │ 控制面   │       │ 控制面   │
   └─────────┘       └─────────┘       └─────────┘
```

| 谁 | 管什么 | 比喻 |
|----|-------|------|
| API 网关 | 南北流量：外部用户 → 系统 | 大楼正门的保安 |
| Service Mesh | 东西流量：服务 ↔ 服务 | 每层楼走廊的管理员 |

**任何说"用 API 网关替代 Service Mesh"或"用 Service Mesh 替代 API 网关"的说法都是错的。** 它们管的是不同方向的流量，解决不同层次的问题，两者并存才是完整的微服务网络架构。

## 术语表

| 术语 | 解释 |
|------|------|
| **Service Mesh** | 服务网格，将服务间通信的治理逻辑（重试/超时/加密/追踪）从应用代码中剥离到独立代理层 |
| **Sidecar** | 边车模式，每个微服务旁挂一个代理容器，伴随主服务运行，透明处理所有进出流量 |
| **Envoy** | CNCF 开源的高性能代理，Service Mesh 的标准数据面实现，作为 Sidecar 部署 |
| **Istio** | 最流行的 Service Mesh 控制面实现，管理 Envoy 配置下发、证书管理、遥测收集 |
| **数据面（Data Plane）** | 执行流量的实际转发、加密、重试等操作（Envoy 的角色） |
| **控制面（Control Plane）** | 管理配置、下发策略、收集监控（Istio 的角色） |
| **mTLS** | Mutual TLS，双向 TLS。客户端和服务器互相验证证书，确保通信双方身份可信 |
| **TraceID** | 全链路追踪中一次完整请求的全局唯一标识，贯穿所有服务（全程路线的过路费记录） |
| **SpanID** | 全链路追踪中一次请求在单个服务上的处理片段标识（经过的每个收费站） |
| **Jaeger / Zipkin** | 开源全链路追踪系统，收集和可视化 Trace 数据 |
