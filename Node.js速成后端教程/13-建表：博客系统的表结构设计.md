## 三、分步操作

### 步骤 1：博客系统需要哪些表？——ER 关系图

一个博客系统，最核心的是三个实体：**用户**、**文章**、**评论**。它们之间的关系用一句话描述：

> 一个用户可以写多篇文章，一篇文章可以有多条评论，一条评论属于一个用户和一篇文章。

这叫 **ER 关系**（Entity-Relationship，实体-关系）。用图表示：

```
┌──────────┐        ┌──────────────┐        ┌──────────┐
│  users   │        │   articles   │        │ comments │
├──────────┤        ├──────────────┤        ├──────────┤
│ id       │◄───────│ author_id    │        │ id       │
│ username │  1对多  │ id           │◄───────│ article_id│
│ email    │        │ title        │  1对多  │ user_id  │
│ password │        │ content      │        │ content  │
│ created  │        │ created_at   │        │ created  │
└──────────┘        └──────────────┘        └──────────┘
     ▲                                            │
     │              1对多                         │
     └────────────────────────────────────────────┘
```

**解读**：
- `users` 和 `articles`：**一对多**——一个用户（users 中的一行）可以写多篇文章（articles 中的多行）。`articles.author_id` 指向 `users.id`。
- `articles` 和 `comments`：**一对多**——一篇文章可以有多条评论。`comments.article_id` 指向 `articles.id`。
- `users` 和 `comments`：**一对多**——一个用户可以发多条评论。`comments.user_id` 指向 `users.id`。

> 这个关系图决定了表结构设计——**外键（Foreign Key）**就是用来实现"指向"关系的。

### 步骤 2：users 表——用户信息

```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL UNIQUE,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TEXT DEFAULT (datetime('now'))
);
```

#### 逐列解释

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | 用户唯一 ID，自增。1, 2, 3... |
| `username` | TEXT | NOT NULL, UNIQUE | 用户名，不能为空，不能重复 |
| `email` | TEXT | NOT NULL, UNIQUE | 邮箱，不能为空，不能重复 |
| `password_hash` | TEXT | NOT NULL | 密码的哈希值（不是明文密码！） |
| `created_at` | TEXT | DEFAULT (datetime('now')) | 注册时间，默认当前时间，ISO 8601 格式 |

#### 约束（Constraint）详解

约束是加在列上的"规则"，违反规则的数据会被拒绝插入。

| 约束 | 含义 | 违反时的行为 |
|------|------|-------------|
| `NOT NULL` | 不能为空 | 插入 NULL 值时拒绝，报错 |
| `UNIQUE` | 不能重复 | 插入重复值时拒绝，报错 |
| `PRIMARY KEY` | 主键，唯一标识一行，自动 NOT NULL + UNIQUE | 插入重复主键时拒绝 |
| `AUTOINCREMENT` | 自动递增（1, 2, 3...） | 插入时如果不指定，自动生成下一个值 |
| `DEFAULT` | 默认值 | 插入时如果不指定，使用默认值 |

> 🔥 **魔鬼细节**：`INTEGER PRIMARY KEY` 在 SQLite 中已经自带自增属性——即使不写 `AUTOINCREMENT`，`id` 也会自动递增。区别在于：`AUTOINCREMENT` 保证新 ID 一定大于旧 ID（即使删掉了最大的行），而不加 `AUTOINCREMENT` 可能复用被删除的 ID。**对博客系统来说，加不加 `AUTOINCREMENT` 都可以，本教程加上以明确意图。**

#### 为什么 `password_hash` 而不是 `password`？

**永远不要明文存储密码！** 如果数据库被泄露，攻击者直接拿到所有用户的密码。`password_hash` 存的是密码经过哈希（Hash）计算后的结果——一个不可逆的字符串。验证密码时，把用户输入的密码同样哈希一次，比较哈希值是否相等。

> 密码哈希会在第 15 章（用户注册）详细讲解。现在先记住：**字段名是 `password_hash`，不是 `password`。**

### 步骤 3：articles 表——文章信息

```sql
CREATE TABLE IF NOT EXISTS articles (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    author_id INTEGER NOT NULL,
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now')),
    FOREIGN KEY (author_id) REFERENCES users(id)
);
```

#### 逐列解释

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | 文章唯一 ID |
| `title` | TEXT | NOT NULL | 文章标题 |
| `content` | TEXT | NOT NULL | 文章正文 |
| `author_id` | INTEGER | NOT NULL, FOREIGN KEY | 作者 ID，指向 `users.id` |
| `created_at` | TEXT | DEFAULT (datetime('now')) | 创建时间 |
| `updated_at` | TEXT | DEFAULT (datetime('now')) | 最后更新时间 |

#### 外键（FOREIGN KEY）——表与表之间的"指针"

```sql
FOREIGN KEY (author_id) REFERENCES users(id)
```

这句话的意思是：`articles.author_id` 的值必须在 `users.id` 中存在。如果你插入一篇文章，`author_id = 999`，但 `users` 表中根本没有 `id = 999` 的用户——数据库会拒绝这次插入。

**外键的作用**：
- **保证数据一致性**：不会出现"一篇文章的作者是一个不存在的用户"。
- **级联操作**（高级）：删除用户时，可以自动删除他的所有文章（`ON DELETE CASCADE`）。

> 🔥 **魔鬼细节**：SQLite 默认**不强制外键约束**！即使你定义了 `FOREIGN KEY`，插入一个不存在的 `author_id` 也不会报错。必须执行 `PRAGMA foreign_keys = ON` 才能开启外键检查。这是 SQLite 向后兼容的历史设计——详见步骤 5。

### 步骤 4：comments 表——评论信息

```sql
CREATE TABLE IF NOT EXISTS comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    content TEXT NOT NULL,
    article_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    created_at TEXT DEFAULT (datetime('now')),
    FOREIGN KEY (article_id) REFERENCES articles(id),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

#### 逐列解释

| 列名 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | 评论唯一 ID |
| `content` | TEXT | NOT NULL | 评论内容 |
| `article_id` | INTEGER | NOT NULL, FOREIGN KEY | 所属文章 ID，指向 `articles.id` |
| `user_id` | INTEGER | NOT NULL, FOREIGN KEY | 评论者 ID，指向 `users.id` |
| `created_at` | TEXT | DEFAULT (datetime('now')) | 评论时间 |

comments 表有两个外键：
- `article_id` → `articles.id`：这条评论属于哪篇文章。
- `user_id` → `users.id`：这条评论是谁发的。

**为什么评论需要两个外键？** 因为"评论"这个实体同时关联了"文章"和"用户"——你需要知道"谁在什么文章下说了什么"。这是关系型数据库中非常典型的"多对一"关系：多条评论指向同一篇文章，也指向同一个用户。

### 步骤 5：外键约束——PRAGMA foreign_keys = ON

这是本章最重要的一个魔鬼细节。

**SQLite 默认不强制外键约束。** 即使你写了 `FOREIGN KEY (author_id) REFERENCES users(id)`，下面这行代码也不会报错：

```javascript
// authors 表中根本没有 id=999 的用户，但这行代码不会报错！
db.prepare('INSERT INTO articles (title, content, author_id) VALUES (?, ?, ?)')
  .run('测试文章', '内容', 999);
```

**为什么？** SQLite 早期的默认行为就是不强制外键（为了兼容性和性能）。你需要手动开启：

```sql
PRAGMA foreign_keys = ON;
```

**这条语句必须在每个数据库连接建立后执行一次。** 它只对当前连接生效，不会保存到数据库文件中。

> 🔥 **魔鬼细节**：`PRAGMA foreign_keys = ON` 必须**每次连接都执行**，因为它是连接级别的设置，不是数据库文件级别的。如果忘了执行，你的外键约束就形同虚设——这是一个非常隐蔽的 bug，数据和代码看起来都正常，但数据完整性已经被破坏了。

### 步骤 6：CREATE TABLE IF NOT EXISTS——幂等建表

注意到每张表的建表语句都以 `IF NOT EXISTS` 开头吗？

```sql
CREATE TABLE IF NOT EXISTS users (...)
```

这意味着：**如果表已经存在，什么都不做（不会报错）。** 这叫**幂等性**（Idempotency）——重复执行同样的操作，结果不变。

**为什么需要幂等建表？** 因为 `server.js` 每次启动都会调用 `initDatabase()`。如果不用 `IF NOT EXISTS`，第二次启动时 `CREATE TABLE` 会报错 "table already exists"，服务器启动失败。

> 如果你需要修改表结构（加列、改类型），不能用 `CREATE TABLE IF NOT EXISTS`，而应该用 `ALTER TABLE`。这属于"数据库迁移"（Migration）的范畴，后面会讲到。

### 步骤 7：创建 database/schema.js——集中管理建表语句

现在把三张表的建表语句整合到一个文件里。

创建 `database/schema.js`：

```javascript
// database/schema.js — 数据库表结构定义
const Database = require('better-sqlite3');
const path = require('path');

/**
 * 初始化数据库：创建连接 + 建表 + 开启外键约束
 * @returns {Database} 数据库连接对象
 */
function initDatabase() {
    const db = new Database('blog.db');

    // ⚠️ 必须开启外键约束！SQLite 默认不强制外键
    db.pragma('foreign_keys = ON');

    // ========== 建表（幂等：IF NOT EXISTS 保证重复执行不报错） ==========

    db.exec(`
        CREATE TABLE IF NOT EXISTS users (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            username TEXT NOT NULL UNIQUE,
            email TEXT NOT NULL UNIQUE,
            password_hash TEXT NOT NULL,
            created_at TEXT DEFAULT (datetime('now'))
        )
    `);

    db.exec(`
        CREATE TABLE IF NOT EXISTS articles (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            title TEXT NOT NULL,
            content TEXT NOT NULL,
            author_id INTEGER NOT NULL,
            created_at TEXT DEFAULT (datetime('now')),
            updated_at TEXT DEFAULT (datetime('now')),
            FOREIGN KEY (author_id) REFERENCES users(id)
        )
    `);

    db.exec(`
        CREATE TABLE IF NOT EXISTS comments (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            content TEXT NOT NULL,
            article_id INTEGER NOT NULL,
            user_id INTEGER NOT NULL,
            created_at TEXT DEFAULT (datetime('now')),
            FOREIGN KEY (article_id) REFERENCES articles(id),
            FOREIGN KEY (user_id) REFERENCES users(id)
        )
    `);

    console.log('✅ 数据库表结构已就绪（users, articles, comments）');
    console.log('✅ 外键约束已开启（PRAGMA foreign_keys = ON）');

    return db;
}

module.exports = { initDatabase };
```

#### 逐行解释

```javascript
db.pragma('foreign_keys = ON');
```

`better-sqlite3` 提供了 `.pragma()` 方法来执行 PRAGMA 命令。PRAGMA 是 SQLite 特有的"配置命令"，用于修改数据库连接的行为。`foreign_keys = ON` 是最重要的一个——不开它，外键就是摆设。

```javascript
return db;
```

`initDatabase()` 返回 `db` 对象，这样 `server.js` 可以拿到数据库连接，在路由中使用。**注意：这里没有 `db.close()`**——因为数据库连接要在整个服务器运行期间保持打开。

### 🤔 想多一点：为什么不用 `database/init.js` 了？

第 12 章的 `database/init.js` 是一个**独立脚本**——运行完就退出。它的作用是演示数据库连接和基本操作。

现在有了 `database/schema.js`，建表逻辑被集成到了 `server.js` 的启动流程中。`database/init.js` 完成了历史使命，你可以保留它作为参考，也可以删除它。

**保留 vs 删除？** 建议保留——它作为"Hello World"式的数据库演示脚本，以后复习时可以参考。但后续开发中，所有建表逻辑都在 `schema.js` 中。

### ❌ 常见错误 → ✅ 解决方案

| 错误信息 / 现象 | 原因 | 解决 |
|-----------------|------|------|
| 插入不存在的 `author_id` 没有报错 | 没开启 `PRAGMA foreign_keys = ON` | 在 `initDatabase()` 中第一行加 `db.pragma('foreign_keys = ON')` |
| `npm run dev` 第二次启动时报 "table already exists" | 建表语句没用 `IF NOT EXISTS` | 在 `CREATE TABLE` 后加 `IF NOT EXISTS` |
| `npm run dev` 报 `Cannot find module './database/schema'` | 文件路径不对或文件不存在 | 确认 `database/schema.js` 已创建，路径拼写正确 |
| `db.pragma is not a function` | `better-sqlite3` 版本太旧 | 升级：`npm install better-sqlite3@latest` |
| 外键约束生效了，但插入测试数据时 `users` 表是空的 | 外键要求 `author_id` 指向存在的用户 | 先插入用户，再插入文章——这是"先有鸡还是先有蛋"的经典问题，下一章用 seed 脚本解决 |
| `datetime('now')` 返回的是 UTC 时间 | SQLite 默认使用 UTC | 正常——在应用层转换时区，数据库统一存 UTC 是业界最佳实践 |

| 术语 | 英文 | 通俗解释 | 本章出现位置 | 字面陷阱 |
|------|------|----------|-------------|----------|
| DDL | Data Definition Language | SQL 中用于定义表结构的语句（CREATE TABLE、ALTER TABLE、DROP TABLE）。与 DML（INSERT/SELECT 等操作数据的语句）相对。 | 步骤 2-4 | 不是"数据定义语言"听起来很高大上——其实就是"建表的命令"。 |

## 八、已知坑点与禁止事项

1. **SQLite 默认不强制外键约束**：这是最常见的坑。每次建立连接后必须执行 `PRAGMA foreign_keys = ON`。如果你忘了，外键就是摆设。

2. **`PRAGMA foreign_keys = ON` 是连接级别的**：每次 `new Database()` 后都要执行一次。它不会保存到数据库文件中。

3. **建表语句必须用 `IF NOT EXISTS`**：否则服务器重启时 `CREATE TABLE` 会报错。除非你确定每次启动前都删掉 `blog.db`。

4. **不要在 `server.js` 的 `initDatabase()` 中调用 `db.close()`**：数据库连接需要在整个服务器运行期间保持打开。关闭连接应该在进程退出时（Express 会处理）。

5. **`password_hash` 字段不能存明文密码**：字段名已经暗示了——它存的是哈希值，不是原始密码。永远不要改名为 `password` 然后存明文。

6. **一个建议：永远不要直接在生产环境执行 DDL**：`CREATE TABLE` 等建表语句应该通过迁移文件（Migration）管理，而不是在启动时执行。本教程为简化学习，直接在启动时建表。实际项目中请使用迁移工具。
