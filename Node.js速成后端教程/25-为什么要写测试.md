## 三、分步操作

### 步骤 1：一个真实的故事——小改动，大崩溃

假设你三周前完成了博客系统的所有接口——注册、登录、文章 CRUD、评论、分页、搜索、文件上传。你用手动测试（Thunder Client）把所有接口跑了一遍，完美。上线了。

三周后，产品经理说："文章列表页加个排序功能吧，按更新时间倒序排列。"

你打开 `routes/articles.js`，改了一行 SQL：

```javascript
// 原来按创建时间排序
ORDER BY articles.created_at DESC

// 改成按更新时间排序
ORDER BY articles.updated_at DESC
```

改完，你用 Thunder Client 测了一下 `GET /api/articles`——返回了文章，排序也对。你提交代码，上线。

**一小时后，用户投诉："创建文章报错！"**

你赶紧排查——原来你改 SQL 时不小心删掉了 `LIMIT ? OFFSET ?` 的逗号，`GET /api/articles` 碰巧返回了数据（因为当时数据库里只有 3 篇文章），但 `POST /api/articles` 在内部用了一个查出 `author_id` 的查询，那个查询也用了相同的分页逻辑——崩溃了。

**关键问题：你只测了改动的那个接口。其他接口（创建文章、评论、搜索）有没有被搞坏？你不知道，因为你没测。**

> 这就是手动测试最大的问题——**你只测你以为受影响的地方，但你不知道真正的受影响范围有多大。**

**比喻**：你装修客厅（改排序），以为只动了客厅的墙。结果你在客厅墙上打洞时，不小心打穿了隔壁卧室的水管（搞坏了创建文章接口）。你只检查了客厅（测了 GET 接口），没检查卧室（没测 POST 接口）。等住进去才发现卧室漏水——已经晚了。

### 步骤 2：手动测试 vs 自动测试——用数据说话

#### 2.1 手动测试的日常

你现在是怎么测试的？

1. 改了几行代码。
2. 切到 Thunder Client，发 `POST /api/auth/register`，看返回。
3. 发 `POST /api/auth/login`，复制 token。
4. 发 `POST /api/articles`，贴 token，填 JSON，看返回。
5. 发 `GET /api/articles`，看列表。
6. 发 `GET /api/articles/:id`，看详情。
7. 发 `PUT /api/articles/:id`，看更新。
8. 发 `DELETE /api/articles/:id`，看删除。
9. 发 `POST /api/articles/:id/comments`，看评论。
10. 发 `GET /api/articles?search=测试`，看搜索。
11. 发 `GET /api/articles?page=1&limit=5`，看分页。
12. 每个接口还要测"边界情况"——密码错误、token 过期、文章不存在、缺少必填字段……

**算一算**：你至少有 15 个测试场景。每次手动测试需要 3-5 分钟。这还是"熟练工"——如果需要复制粘贴 token、复制粘贴 JSON，时间更长。

#### 2.2 自动测试的日常

你只需要一条命令：

```bash
npm test
```

3 秒后，终端输出：

```
 PASS  tests/articles.test.js
 PASS  tests/auth.test.js

Test Suites: 2 passed, 2 total
Tests:       18 passed, 18 total
```

全绿？放心提交代码。有红？看哪一行失败了，修。

#### 2.3 数据对比

| 维度 | 手动测试 | 自动测试 |
|------|----------|----------|
| 第 1 次测试 | 3 分钟 | 写测试：40 分钟 |
| 第 2 次测试 | 3 分钟 | 3 秒 |
| 第 10 次测试 | 3 分钟，开始烦躁 | 3 秒 |
| 第 50 次测试 | 开始跳过"不重要的"接口 | 3 秒，从不跳过 |
| 第 100 次测试 | "测了 GET 和 POST 就行，DELETE 应该没问题" | 3 秒，所有接口全覆盖 |
| 凌晨 2 点改代码 | 困，可能漏测，上线出 bug | `npm test`，全绿，安心睡觉 |
| 同事接手你的代码 | 他不知道要测哪些接口 | `npm test`，自动跑了你写的所有测试 |

**关键洞察**：写测试是一次性的时间投资，但它会在未来**每次代码变更时**自动保护你。测一次简单，测 100 次呢？测 1000 次呢？手动测试的边际成本不变，自动测试的边际成本趋近于零。

> 🔥 **魔鬼细节**：很多人觉得"写测试浪费时间"——那是只看到了第一次。你写代码的 90% 时间不是在写新功能，而是在改已有功能。每次改代码你都要验证——测试帮你把验证成本从 3 分钟降到 3 秒。

**比喻**：手动测试就像**每次出门前亲手检查每个窗户、每个门锁**。自动测试就像**装了一套智能安防系统**——你出门前按一个按钮，系统自动检查所有门窗，3 秒后告诉你"全部安全"或"客厅窗户没关"。装安防系统要花时间（写测试），但之后每次出门只需要 3 秒。

### 步骤 3：测试金字塔——不是所有测试都一样

在写测试之前，你必须理解一个核心概念：**测试金字塔**。此术语需进附录。

```
        /\
       /E2E\          ← 少（端到端：模拟真实用户操作整个系统）
      /------\
     / 集成测试 \      ← 中（多个模块协作：发 HTTP 请求 → 路由 → 数据库 → 返回响应）
    /----------\
   /   单元测试   \    ← 多（单个函数独立测试：不涉及数据库、网络、文件系统）
  /--------------\
```

**三层测试的含义**：

| 层级 | 测什么 | 例子（博客系统） | 速度 | 数量 | 维护成本 |
|------|--------|-----------------|------|------|----------|
| **单元测试** | 单个函数的逻辑 | 测试 `hashPassword("123")` 的返回值长度是否为 60 | 毫秒级 | 最多 | 低 |
| **集成测试** | 多个模块协作的完整链路 | 测试 `POST /api/articles` → 数据库有记录 → 返回 201 + 文章数据 | 秒级 | 中等 | 中 |
| **E2E 测试** | 模拟真实用户的完整操作流程 | 打开浏览器 → 登录 → 写文章 → 发布 → 查看文章 → 发表评论 | 分钟级 | 最少 | 高 |

**本教程写的是哪一层？** 主要是**集成测试**——用 Jest + supertest 发 HTTP 请求到 Express 应用，验证整个请求-响应-数据库链路。这比单元测试覆盖更全面（一次测试覆盖路由、中间件、数据库操作），又比 E2E 测试快得多（不需要浏览器）。

**比喻**：测试金字塔就像一个体检套餐：
- 单元测试 = 每天量体温、测血压（快、频繁、基础）
- 集成测试 = 每月体检，查血常规、肝功能（检查几个关键系统的协作）
- E2E 测试 = 每年全身大体检，CT、核磁共振全上（慢、全面、昂贵）

你不会每天都做全身大体检，但每天量体温能快速发现异常。同样，你不会为每个函数都写 E2E 测试，但核心业务逻辑的集成测试是必须的。

### 步骤 4：什么该测，什么不必测——测试的边界感

**不是所有代码都需要写测试。** 写测试也需要成本——测试代码也是代码，也需要维护。如果测试的维护成本大于它带来的收益，那就不值得写。

#### 4.1 必测（核心业务逻辑）

这些是你的"保险必须覆盖的范围"：

| 类别 | 具体内容 | 为什么 |
|------|----------|--------|
| **用户注册** | 正常注册、重复用户名、密码过短 | 注册是用户入口，出问题用户直接流失 |
| **用户登录** | 正常登录、密码错误、不存在的用户 | 登录是每次访问的必经之路 |
| **JWT 认证中间件** | 无 token、无效 token、过期 token | 安全相关——误判会导致越权访问 |
| **文章 CRUD** | 创建/读取/更新/删除的正常流程 + 404 场景 | 核心业务，使用频率最高 |
| **权限检查** | 用户A不能修改用户B的文章 | 数据安全——误判会导致数据被篡改 |
| **必填字段验证** | 缺少 title、缺少 content | 防御性——脏数据进入数据库后很难清理 |

#### 4.2 不必测（投入产出比低）

| 类别 | 例子 | 为什么 |
|------|------|--------|
| **简单的 getter/setter** | `const getTitle = (article) => article.title` | 太简单，不会出错 |
| **第三方库的内部逻辑** | `better-sqlite3` 的 `INSERT` 实现 | 库的作者已经测过了，你不需要重复测 |
| **Express 框架本身** | `app.use(express.json())` 是否正常工作 | Express 已经有上万测试覆盖，你不需要再测 |
| **纯配置代码** | `const PORT = process.env.PORT \|\| 3000` | 逻辑太简单 |
| **日志输出** | `console.log('请求来了')` 是否真的打印了 | 日志不影响业务逻辑，且难以断言 |

**判断标准**：问自己一个问题——"如果这段代码出错了，用户会发现吗？"如果答案是"会"，那就值得写测试。如果答案是"不会"或"无所谓"，就不必测。

**比喻**：写测试就像买保险——你不会给一支铅笔买保险（太便宜，不值得），但你会给房子买保险（太贵，不敢不保）。测试也是这样——你不会给 `console.log` 写测试，但你会给"用户登录"写测试。

### 步骤 5：测试驱动开发的信心增益——你敢改代码了

**为什么有测试的代码库让人安心？** 因为测试给了你两个能力：

#### 5.1 你敢改代码

```bash
# 没有测试时改代码：
"我改了这个函数……嗯，应该没问题……吧？"
"算了，先上线吧，有问题再说。"
"线上出 bug 了！紧急回滚！"

# 有测试时改代码：
"改完了，npm test 跑一下。"
3 秒后：18 passed, 0 failed
"全绿，放心提交。"
```

测试就像给你的代码装了一个"安全网"。你在高空走钢丝（改代码），安全网（测试）在下面兜着。没有安全网，你每一步都小心翼翼；有了安全网，你才敢大步走。

#### 5.2 新同事能看懂你的业务逻辑

想象一个新同事接手你的博客项目。他打开 `tests/articles.test.js`，看到的不是抽象的"业务文档"，而是可执行的"业务说明书"：

```javascript
// 测试：不能创建缺少标题的文章
it('创建文章缺少标题应返回 400', async () => {
    const res = await request(app)
        .post('/api/articles')
        .set('Authorization', `Bearer ${token}`)
        .send({ content: '有内容，没标题' });
    expect(res.status).toBe(400);
});
```

这段代码告诉新同事三件事：
1. 创建文章需要标题（`title`）。
2. 缺少标题返回 400 状态码。
3. 创建文章需要认证（`Authorization` header）。

**比任何文档都准确**——因为如果文档写错了，没人会知道。但测试写错了，`npm test` 会告诉你。

**比喻**：测试代码就是"活文档"。传统文档（Word、Notion）会过时——你改了代码但忘了更新文档，文档就成了"谎言"。测试不会过时——你改了代码，如果测试没更新，`npm test` 会红，逼你更新。测试永远和代码同步。

> 🔥 **魔鬼细节**：很多人认为"测试是给测试人员写的"，这是错误的。测试是给**未来的你**和**你的同事**写的——它是代码的"用户手册"和"安全手册"的合体。

### 步骤 6：本教程的测试策略——我们怎么测

在动手写测试之前，先明确"我们测什么、怎么测"。这样你不会在下一章迷路。

#### 6.1 测试层级：集成测试为主

我们重点测 **API 路由**（集成测试），原因：
- 我们的博客系统是 API 服务，核心价值在"请求 → 响应"这条链路上。
- 集成测试一条用例覆盖路由、中间件、数据库操作——效率高。
- 单元测试留给那些"纯逻辑函数"（如密码哈希、分页计算），但本教程中这类函数很少。

#### 6.2 测试数据库：与开发数据库隔离

**绝对不用开发数据库（`blog.db`）跑测试！** 原因：
- 测试会创建大量测试数据，污染你的开发数据。
- 测试可能删除数据，导致你的开发环境数据丢失。
- 测试需要可重复——每次运行测试前，数据库状态必须一致。

**做法**：使用独立的 SQLite 数据库（`test.db` 或 `:memory:` 内存数据库），测试前建表，测试后清空/删除。

**比喻**：测试数据库是"实验田"——你在实验田里随便种、随便拔，不影响真正的农田（开发数据库）。试验做完，实验田清空，农田完好如初。

#### 6.3 测试范围清单

| 测试文件 | 覆盖内容 | 用例数（预估） |
|----------|----------|---------------|
| `tests/auth.test.js` | 注册（正常 + 重复用户名）、登录（正常 + 密码错误 + 用户不存在） | 5 |
| `tests/articles.test.js` | 获取全部/单篇/404、创建（带 token + 缺字段 + 无 token）、更新（正常 + 404）、删除（正常 + 404）、权限（用户A不能改用户B的文章）、认证中间件（无 token、无效 token） | 12+ |

#### 6.4 工具选型

| 工具 | 用途 | 替代品 |
|------|------|--------|
| **Jest** | 测试框架（运行测试、断言、覆盖率报告） | Mocha + Chai，但 Jest 零配置开箱即用 |
| **supertest** | HTTP 测试库（模拟 HTTP 请求到 Express app） | 手动 `http.createServer` + 自己发请求，但 supertest 一行搞定 |

### 🤔 想多一点：TDD 和 "先写代码再写测试" 有什么区别？

**TDD（Test-Driven Development，测试驱动开发）** 此术语需进附录。它的核心流程是：**红 → 绿 → 重构**。

1. **红**：先写测试，运行——测试失败（因为还没写代码）。
2. **绿**：写最少的代码让测试通过。
3. **重构**：优化代码，保持测试绿色。

**本教程不要求 TDD**。我们采用"先写代码，再补测试"的方式——因为你现在是初学者，同时学"写功能"和"写测试"会认知过载。先学会写测试，以后可以尝试 TDD。

**但你要知道 TDD 的存在**——它是很多专业团队的开发方式。它的核心哲学是：**先想清楚"这个功能该怎么用"，再写实现。** 测试就是"怎么用"的规格说明。

## 五、验证方法

本章不需要动手操作。用以下问题自检理解程度：

1. **你能说出手动测试和自动测试的三个区别吗？**（提示：速度、覆盖范围、可重复性）
2. **测试金字塔从下到上分别是哪三层？**（提示：单元 → 集成 → E2E）
3. **"获取文章列表"接口的测试属于哪一层？**（提示：涉及 HTTP 请求 → 路由 → 数据库，多模块协作）
4. **以下哪个不需要写测试？** `console.log('请求来了')` / `用户注册` / `JWT 认证中间件` / `文章的必填字段验证`（答案：`console.log`）
5. **为什么测试数据库和开发数据库要分开？**（提示：数据污染、可重复性）

如果你能回答以上 5 个问题，恭喜——你已经理解了测试的核心概念。下一章就是动手了。

## 六、小结表格

| 学到的东西 | 一句话解释 |
|-----------|-----------|
| 手动测试的痛点 | 烦、慢、容易漏、不可重复——测一次简单，测 100 次呢？ |
| 自动测试的价值 | 一次投入，终身保护——每次改代码后 3 秒跑完所有检查 |
| 测试金字塔 | 单元测试（多、快）→ 集成测试（中）→ E2E 测试（少、慢），按比例分配 |
| 单元测试 | 测单个函数的逻辑，不涉及数据库/网络，毫秒级 |
| 集成测试 | 测多个模块协作的完整链路（HTTP → 路由 → 数据库 → 响应），本教程重点 |
| E2E 测试 | 模拟真实用户操作整个系统，最慢，最接近真实场景 |
| 什么该测 | 核心业务逻辑：注册、登录、JWT、CRUD、权限、必填字段验证 |
| 什么不必测 | 简单 getter、第三方库内部逻辑、Express 框架本身、纯配置代码 |
| TDD | 测试驱动开发：红 → 绿 → 重构，先写测试再写代码 |
| 测试数据库隔离 | 测试用独立数据库（`test.db`），不污染开发数据（`blog.db`） |
| 测试即文档 | 测试代码是可执行的"业务说明书"，永远和代码同步，不会过时 |

## 七、术语附录

| 术语 | 英文 | 通俗解释 | 本章出现位置 | 字面陷阱 |
|------|------|----------|-------------|----------|
| 单元测试 | Unit Test | 测试单个函数/方法的逻辑，不涉及数据库、网络、文件系统等外部依赖。快、多、稳定。 | 步骤 3 | 不是"只测一个单元"——"单元"可以是一个函数，也可以是一个类的方法。关键是"不依赖外部"。 |
| 集成测试 | Integration Test | 测试多个模块协作的完整链路，如发 HTTP 请求 → 路由 → 中间件 → 数据库 → 返回响应。 | 步骤 3 | 不是"把系统集成起来测"——集成测试测的是"模块之间的接口"，不是整个系统。 |
| E2E 测试 | End-to-End Test | 端到端测试，模拟真实用户操作整个应用（打开浏览器 → 登录 → 操作 → 验证）。最慢，覆盖范围最大。 | 步骤 3 | 不是"从头到尾测一遍"——E2E 测试关注的是"用户视角的完整操作流程"，而非代码覆盖率。 |
| 测试金字塔 | Test Pyramid | 测试分层模型：底层单元测试（多、快），中层集成测试（中），顶层 E2E 测试（少、慢）。指导我们按比例分配测试资源。 | 步骤 3 | 不是"金字塔越高越好"——金字塔是"比例"的概念，不是"层级"的概念。越往上越少越慢。 |
| TDD | Test-Driven Development | 测试驱动开发：先写测试（红）→ 写最少代码让测试通过（绿）→ 优化代码（重构）。核心是"先想清楚怎么用，再写实现"。 | 想多一点 | 不是"边写测试边写代码"——TDD 要求**先写测试**，再写代码。顺序是严格的：红 → 绿 → 重构。 |
| 覆盖率 | Code Coverage | 测试覆盖了多少行代码的百分比。如覆盖率 80% 表示 80% 的代码行在测试中被执行过。覆盖率不等于质量——100% 覆盖率的代码也可能有 bug。 | 步骤 6 | 不是"覆盖率高就安全"——覆盖率只告诉你"哪些代码被执行了"，不告诉你"执行得对不对"。100% 覆盖率的代码也可能有 bug（断言写错了）。 |
| 回归测试 | Regression Test | 确保"改了 A 功能，B 功能没坏"的测试。每次修改代码后跑全部测试，就是在做回归测试。 | 步骤 1 | 不是"退回之前版本的测试"——回归是指"防止功能退化"（regression = 退化），不是"回去"（return）。 |

## 八、已知坑点与禁止事项

| 坑点 | 现象 | 原因 | 解决 |
|------|------|------|------|
| 以为"测试是浪费时间" | 不写测试，手动测了几个月，终于在某次上线后崩溃 | 只看到了写测试的短期成本，没看到长期收益 | 记住：写测试是一次性投资，改代码是高频操作。测试节省的是"每次改代码的验证时间"。 |
| 追求 100% 覆盖率 | 为每个 getter 函数写测试，测试代码比业务代码还多 | 覆盖率不等于质量——100% 覆盖率的代码也可能有 bug | 只测核心业务逻辑。问自己："这段代码出错，用户会发现吗？" |
| 测试和开发用同一个数据库 | 测试数据污染了开发数据，或者测试删除了重要数据 | 测试数据库和开发数据库没有隔离 | 永远用独立测试数据库（`test.db` 或 `:memory:`）。下一章会具体实现。 |
| 只测"正常路径"不测"异常路径" | 测试全绿，但上线后用户输错密码返回 500 | 只测了"密码正确"的情况，没测"密码错误"的情况 | 每个接口至少测：正常情况 + 至少一个异常情况（404、400、401、403） |
| 测试代码不维护 | 代码改了，测试没改，`npm test` 一直红，最后被注释掉 | 测试代码也是代码，也需要维护 | 改代码时同步改测试。如果测试红了，要么修代码，要么修测试——不要注释掉。 |
